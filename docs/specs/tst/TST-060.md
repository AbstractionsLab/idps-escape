# GUI: Deploy scenario on pre-existing SN Wazuh

This test verifies the correct deployment of scenarios on a pre-existing single node Wazuh instance.

## Preconditions and setup actions
- Same generic preconditions as [TST-055](./TST.html#TST-055).
- A single-node Wazuh v4.14 manager, indexer, and dashboard must already be running, independently of RADAR, before any RADAR step below is taken. If you don't already have one, bring up a single-node stack using [Wazuh's own official docker-compose files](https://github.com/wazuh/wazuh-docker/tree/v4.14.4).

## Test steps

1. On the controller host, prepare `.env` pointing it at the existing Wazuh stack's addresses.

2. Start the GUI:
```bash
./radar.sh gui
```

3. In the GUI, go to **Infrastructure**. Register the existing stack's components with their real container names:
    - **Manager**: host address, port `55000`, scheme `https`, container name matching `docker ps` on the Wazuh host (e.g. `<project>-wazuh.manager-1`).
    - **Indexer**: host address, port `9200`, scheme `https`, its real container name (e.g. `<project>-wazuh.indexer-1`).
    - **Dashboard**: host address, port `443`, scheme `https`, its real container name.

4. On the Infrastructure page, use **Test link** to check reachability between the components.

5. On the Wazuh host, confirm `volumes.yml` has an entry keyed by the manager's exact container name (from step 3). Each line has the form `<host path>:<container path>`. The left side is wherever the data actually lives on disk; the right side is the fixed path RADAR needs inside the container — the six right-hand paths below must all be present under your container's key:
    - `/var/ossec/etc`
    - `/var/ossec/logs`
    - `/var/ossec/integrations`
    - `/var/ossec/active-response/bin`
    - `/etc/filebeat`
    - `/usr/share/filebeat/module/wazuh/archives/ingest/pipeline.json`

If any mapping is missing, add it under the manager's container-name key, pointing at the actual host paths bind-mounted into that container (`docker inspect <manager_container> --format '{{json .Mounts}}'` on the Wazuh host shows the real paths in use).

6. In the GUI, go to **Deployment → Scenario Management**, select the scenario under test, and click **Deploy**. If prompted for the sudo password, enter it.

7. In the GUI, go to **Deployment → Agent Management**. Select the same scenario, click **Mint token**, and copy the printed `bootstrap-agent.sh` command.

8. On the agent host, download the `bootstrap-agent.sh` script and run the copied command exactly as printed, under `sudo`:
```bash
scp bootstrap-agent.sh <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x bootstrap-agent.sh
```

9. In the GUI, go to **Deployment → Group Management**. Enter the agent's IP/name, select the scenario under test, and click **Assign group**.

10. Continue with the remaining steps of the matching scenario's own test, run against the container names registered in step 3 above instead of the default names those tests use:
    - `suspicious_login` → [TST-055](./TST.html#TST-055), steps 7-8.
    - `geoip_detection` → [TST-056](./TST.html#TST-056), steps 7-9.
    - `scanning_detection` → [TST-057](./TST.html#TST-057), steps 7-9.
    - `log_volume` → [TST-058](./TST.html#TST-058), steps 7-11.

## Expected outcome

1. `.env` exists in the controller with the required variables set, pointing at the existing Wazuh stack.

2. The GUI is reachable in a browser.

3. Infrastructure page shows the manager, indexer, and dashboard registered with the existing stack's real container names.

3a. `WEBHOOK_INTERNAL_PORT`'s port is confirmed free before use, or a free alternative is chosen and both `WEBHOOK_INTERNAL_PORT`/`WEBHOOK_URL` and the registered webhook port match it.

4. **Test link** reports components are reachable.

5. `volumes.yml` has a complete entry for the manager's container name; none of the six required container paths are missing.

6. The **Deploy** command completes with `=== SUCCESS` in its output.

7. A ready-to-run `bootstrap-agent.sh` command is printed, carrying the group(s) for the scenario under test.

8. The command completes with `=== SUCCESS ===` in its output.

9. On the Wazuh Dashboard, open **Agents management → Summary**. The agent is assigned the scenario's group(s).

10. The remaining expected outcomes match those listed under the same step numbers of the matching scenario's own test referenced in step 10 above (no `FAIL` lines in the health check; the simulation script completes; and that scenario's rule, log, email, and optional FlowIntel checks all pass), read against the container names registered in step 3 above rather than the default ones those tests use.

## Cleanup

1. After finishing tests, clean up using **Deployment → Teardown** in the GUI. This only removes containers/data belonging to RADAR's own compose services (the webhook).

2. To clean the agent host:
```bash
scp uninstall-agent.sh <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x uninstall-agent.sh
sudo ./uninstall-agent.sh --purge-data
```

3. If the pre-existing Wazuh stack itself should also be torn down, that is done independently of RADAR, using whatever process was used to bring it up.
