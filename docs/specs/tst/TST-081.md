# RADAR GUI REST API contract

## Preconditions and setup actions

- Automated part (step 1): a repository checkout with `poetry install --with radar,test`. No RADAR stack, network or Docker is needed.
- Manual part (steps 2 to 10), on the RADAR host:
  - `radar/.env` exists and the user can run `sudo`. A deployed scenario is not needed except for step 9.
  - Back up `radar/scenarios/active_responses/ar.yaml` and `radar/.env`; restore both at the end.
  - Start the GUI from `radar/` with a short sudo idle period: `RADAR_SUDO_IDLE_MINUTES=1 ./radar.sh gui`. In a second shell, set `GUI=http://127.0.0.1:5000`, `TOKEN=<token part of ./radar.sh gui-url>` and `J='Content-Type: application/json'`. Every `curl` after step 3 uses the cookie jar: `curl -s -b jar -c jar ...`.

## Test steps

1. From `radar/`, run:
   ```
   PYTHONPATH=anomaly_detector:. poetry run pytest tests/py/test_gui_ar_config.py -v
   ```
2. **Host allowlist**: `curl -s -w ' %{http_code}\n' -H 'Host: evil.example:5000' "$GUI/api/scenarios"`.
3. **Login token**: request `$GUI/api/scenarios` without a cookie; then `$GUI/?token=wrong`; then log in with `curl -s -c jar -o /dev/null -w '%{http_code}\n' "$GUI/?token=$TOKEN"` and inspect `jar`; then request `$GUI/api/scenarios` with the jar.
4. **CSRF checks**: send `-X PUT -d '{}' $GUI/api/scenarios/suspicious_login/ar-config` three times: without `-H "$J"` (curl then sends a form content type); with `-H "$J" -H 'Sec-Fetch-Site: cross-site'`; with `-H "$J" -H 'Origin: http://evil.example'`.
5. **Scenarios**: `GET /api/scenarios`; `GET /api/scenarios/default`; `GET /api/scenarios/no_such_scenario`; `GET /api/scenarios/deploy-status`.
6. **Active-response partial update**: note `GET /api/scenarios/suspicious_login/ar-config`; `PUT` it with `{"delta_signature_minutes": 7}`; read it again. Then `PUT` it with `{"mitigations_tier2": ["nope.sh"]}`. Then `POST /api/scenarios/default/bind` with `{}`.
7. **Connectors**: `GET /api/connectors`; `POST /api/connectors/reveal` with `{"key": "OS_PASS"}`; with `{"key": "WEBHOOK_SHARED_SECRET"}`; `PUT /api/connectors/opensearch` with `{"os-url": "https://198.51.100.1:9200"}`; `POST /api/connectors/opensearch/test` and `POST /api/connectors/wazuh-api/test`.
8. **Sudo session**: `POST /api/sudo/unlock` with a wrong password, then `GET /api/sudo/status`; unlock with the correct password, `GET /api/sudo/status`, repeat the two reveal requests of step 7; wait two minutes without further requests and `GET /api/sudo/status` again.
9. **Streaming and preview**: `POST /api/deploy/preview` with `{"action": "health", "scenario": "all"}`; then `curl -N -b jar -X POST -H "$J" -d '{"scenario": "all"}' "$GUI/api/deploy/health"` and watch the output arrive; `POST /api/deploy/run` with `{"scenario": "no_such_scenario", "ingest": false}`; `POST /api/deploy/mint-token` with `{"groups": "default"}` while no sudo password is held.
10. **Logout**: unlock sudo again, then `POST /api/logout` with `{}`; check the response cookies, the GUI process, and `./radar.sh gui-url`.

## Expected outcome

1. All tests pass: the mitigation names offered and accepted are `firewall-drop` plus the catalog names; a partial `PUT .../ar-config` and a `bind` store normalised names; an unknown mitigation or a non-list value is refused with HTTP 400 and a message naming it, and leaves `ar.yaml` unchanged; a broken catalog is reported on the page; the GUI never writes the catalog.
2. HTTP 403 with `{"ok": false, "error": "Host 'evil.example:5000' is not allowed..."}`.
3. Without a cookie: HTTP 401 with `"ok": false`. Wrong token: HTTP 401 `Invalid login token.` (plain text, as `/` is a page). Correct token: HTTP 302, and the jar holds `radar_gui_auth` marked HttpOnly (`#HttpOnly_` prefix). With the jar: HTTP 200 and a JSON list.
4. HTTP 415, 403 and 403, each with `"ok": false`; `ar.yaml` unchanged.
5. The list holds every scenario with `gui_visible: true` in `radar/config.yaml`, each with `id`, `name`, `description`, `status`, `type` (`signature`, `anomaly` or `hybrid`), `rule_ids`, `bound`, `shared` and, when bound, a non-empty `ar_config`. `default` is returned with `bound: true`. The unknown scenario gives HTTP 404 `{"ok": false, "error": "not found"}`. Deploy status gives `{"ok": true, "active": {...}}` per scenario.
6. The first `PUT` returns `{"ok": true}`, and only `delta_signature_minutes` differs from the noted configuration. The unknown mitigation gives HTTP 400 naming `nope.sh`. Binding `default` gives HTTP 400.
7. The connector list contains no secret value, and `password_status` tells which secrets are set. Reveal without unlocked sudo: HTTP 403 with `need_sudo: true`; reveal of a key outside the five secret fields: HTTP 403 `key not allowed`. Changing `os-url` without a new password: HTTP 403 with `need_sudo: true`, `.env` unchanged. Each test answers `{"ok": true|false, ...}` reflecting whether the service is reachable with the saved settings.
8. Wrong password: HTTP 403 `sudo rejected this password`, status `{"unlocked": false}`. Correct password: `{"ok": true}`, status `{"unlocked": true}`, `OS_PASS` revealed, `WEBHOOK_SHARED_SECRET` still `key not allowed`. After two idle minutes, `{"unlocked": false}`.
9. Preview returns `{"ok": true, "cmd": ...}` listing the three health stages, and nothing runs. The health stream shows the `=== MANAGER (filesystem/container) ===` section before the later sections are produced. The invalid scenario yields a `text/plain` line starting with `[ERROR]`. Mint token without sudo: HTTP 403 with `need_sudo: true` before any output.
10. `{"ok": true, ...}`, both cookies deleted, the GUI process exits, and `gui-url` reports that the GUI is not running. A restarted GUI reports `{"unlocked": false}`.

The test passes when every expected outcome is observed. Restore `ar.yaml` and `.env` from the backup.
