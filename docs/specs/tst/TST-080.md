# RADAR manager-side enrichment

## Preconditions and setup actions

Automated part (steps 1–2):

- `poetry install --with radar,test`. No network access, Wazuh manager, GeoLite2 database or MaxMind licence key is needed: the tests replace the MaxMind readers with in-memory fakes and use temporary SQLite files.

Live part (steps 3–7, optional):

- RADAR built with the `suspicious_login` scenario, and for step 6 also `geoip_detection`, as in [TST-043](./TST.html#TST-043), with `MAXMIND_LICENSE_KEY` set in `radar/.env` so that deployment downloads the GeoLite2 City and ASN databases.
- A Linux endpoint onboarded into the groups `default`, `suspicious_login` and `radar_shared` (plus `geoip_detection` for step 6), with the simulation scripts of `radar/radar-test-framework/simulate/scenarios/` copied to it.

## Test steps

1. From the repository root, run the enrichment unit tests:
   ```
   poetry run pytest radar/tests/py/test_manager_enrichment.py -v
   ```
   They also run as part of the whole RADAR suite, `radar/tests/run-tests.sh`.
2. From the repository root, check that no GeoIP database is under version control:
   ```
   git ls-files | grep -i '\.mmdb$'
   ```
3. On the controller host, from `radar/`, run the health check:
   ```
   ./radar.sh health --scenario suspicious_login
   ```
4. On the endpoint, write the SSH cases of the `suspicious_login` simulation, then on the controller host read the enriched lines:
   ```
   sudo python3 suspicious_login.py -batch travel benign
   docker exec wazuh.manager tail -n 20 /var/ossec/logs/radar/enriched_auth.log
   ```
5. On the controller host, make the City database unavailable, run the health check again, then restore the database and run it once more:
   ```
   docker exec wazuh.manager mv /var/ossec/etc/radar/GeoLite2-City.mmdb /var/ossec/etc/radar/GeoLite2-City.mmdb.bak
   ./radar.sh health --scenario suspicious_login
   docker exec wazuh.manager mv /var/ossec/etc/radar/GeoLite2-City.mmdb.bak /var/ossec/etc/radar/GeoLite2-City.mmdb
   ./radar.sh health --scenario suspicious_login
   ```
6. With `geoip_detection` deployed, on the endpoint write the web cases, then read the enriched web lines:
   ```
   sudo python3 geoip_detection.py -batch web_ip web_private
   docker exec wazuh.manager tail -n 20 /var/ossec/logs/radar/enriched_web_access.log
   ```
7. Read the enrichment error log:
   ```
   docker exec wazuh.manager cat /var/ossec/logs/radar/enrichment_errors.log
   ```

## Expected outcome

1. All 25 tests pass. In particular:
   - the GeoIP lookup returns the ISO country code, region, city, coordinates and ASN, returns empty fields for an unknown address, and survives a failing reader;
   - accepted, failed and invalid-user `sshd` lines are parsed into time, user, source address and outcome; any other line, or a line without a syslog header, is ignored;
   - a user's first login has velocity 0 and no country change; a second login from another country sets the country change; two logins about 3,900 km apart one hour apart give a velocity above 900 km/h;
   - ASN novelty is kept per user, ASN history older than 90 days is dropped, and a missing ASN sets the placeholder flag;
   - two logins of the same user enriched for two different endpoints are evaluated against one shared history (country change, velocity above 900 km/h);
   - the state database survives a new store instance (restart), is created group-writable (0660), and an unknown user gets an empty state;
   - the appended tail is matched by the success, failure and invalid-user decoder expressions of `0310-ssh.xml`, which the tests reproduce.
2. The command prints nothing (exit status 1): no `.mmdb` file is tracked.
3. The health check reports `OK` for the integration files, both GeoLite2 databases and `maxminddb`, `OK` or, before any login has been enriched, `WARN` for `user_state.sqlite3`, and `OK - enrichment_errors.log empty/absent`.
4. Each simulated SSH line appears in `enriched_auth.log` followed by a `RADAR outcome='…' asn='…' … country='…' … geo_velocity_kmh='…' country_change_i='…' asn_novelty_i='…'` tail; for the `travel` case the second and third logins have `country_change_i='1'` and a velocity above 900 km/h, and for `benign` the second login has no country change. The corresponding rules of SRS-051 fire on the enriched lines.
5. With the City database missing, the health check reports `FAIL` for `GeoLite2-City.mmdb`; after restoring it, `OK` again.
6. The `web_ip` line appears in `enriched_web_access.log` with a `RADAR country="…" region="…" city="…" lat="…" lon="…"` tail; the `web_private` line is not enriched.
7. The error log has no entry written during the test, except for logins processed while the database was missing in step 5.

The web-access enrichment (`radar/manager-enrichment/web_enrichment.py`, `custom-radar-web-enrich`) has no automated test; step 6 is its only verification.
