# Validate detection of `linux_resource_utilization`

This test checks that RADAR raises an anomaly when CPU usage on a Linux agent goes far above its normal level. The detector is trained on baseline data that matches the agent's normal CPU and memory usage. A CPU load of 90% is then applied while memory stays at its normal level. The test passes if the detector reports an anomaly during the CPU load and the anomaly is caused only by CPU.

The detector `LINUX_RESOURCE_UTILIZATION_DETECTOR` checks each agent every minute, using four values: `cpu_usage_avg`, `cpu_usage_max`, `memory_usage_avg` and `memory_usage_max`. It raises an alert when `anomaly_grade` ≥ 0.01 and `confidence` ≥ 0.01.

Deployment and onboarding are validated by [TST-061](./TST.html#TST-061). This test repeats those steps in every run only to start from a clean state; the outcomes are not validated again.

## Preconditions and setup actions
- Same preconditions as [TST-061](./TST.html#TST-061).
- Successful execution of [TST-061](./TST.html#TST-061) with the same controller and agent host to be used in this test.
- `stress-ng` at least v0.19.02 is installed on the agent host (`sudo apt-get install -y stress-ng`).
- For the optional step, Flowintel is correctly configured and reachable from the controller host.

### Setup

The following steps are executed only once, before the first run of this test.

1. From the root of the project, copy the simulation script and the `radar-agent` folder (which holds `bootstrap-agent.sh` and `uninstall-agent.sh`) to the agent's host, and make the simulation script executable:

```bash
scp radar/radar-test-framework/simulate/scenarios/linux_resource_utilization.sh <user>@<agent-host>:~/
scp -r radar/radar-agent <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x linux_resource_utilization.sh
```

2. Run the following on the agent host while it is idle. It uses the same calculation as the RADAR collector `radar-linux-resource-utilization-metric.sh`, takes 5 samples 60 seconds apart, and prints their average:

```bash
for i in $(seq 1 5); do
  read -r t1 i1 < <(awk '/^cpu / {t=0; for(k=2;k<=NF;k++) t+=$k; print t, $5}' /proc/stat); sleep 1
  read -r t2 i2 < <(awk '/^cpu / {t=0; for(k=2;k<=NF;k++) t+=$k; print t, $5}' /proc/stat)
  awk -v dt=$((t2-t1)) -v di=$((i2-i1)) \
    '/^MemTotal:/{t=$2} /^MemAvailable:/{a=$2}
    END{printf "cpu=%.2f mem=%.2f\n", (1-di/dt)*100, (1-a/t)*100}' /proc/meminfo
  [ "$i" -lt 5 ] && sleep 59
done | tee /dev/stderr | awk -F'[= ]' '{c+=$2; m+=$4; n++} END{printf "average: cpu=%.2f mem=%.2f\n", c/n, m/n}'
```

3. On the controller host, set `baseline_cpu_pct` and `baseline_mem_pct` in the `ingest` part of the `linux_resource_utilization` section of `radar/config.yaml` to the printed averages. The other ingest values stay as they are.

4. On the controller host, prepare `.env` and start the GUI of RADAR as in steps 1-2 of [TST-061](./TST.html#TST-061).

### Assumptions

1. The baseline values in `config.yaml` have been set according to the agent's host normal usage metrics, as described in the Setup section.
2. Nothing runs on the agent's host other than the operating system, the Wazuh agent and the stress script.
3. Installing the agent causes a short CPU spike, which the detector may report as an anomaly.
4. Each run starts from a clean state, using the steps in Cleanup.

### Acceptance criteria

The test is run 10 times. It passes if, in every run:

1. An anomaly with `cpu_usage_max` ≥ 80% is reported.
2. That anomaly has `anomaly_grade` ≥ 0.8 and `confidence` ≥ 0.3.

In addition, the expected outcome of step 5 holds in the first run.

## Test steps

1. Deploy the scenario and onboard the agent, following steps 3-5 of [TST-061](./TST.html#TST-061):
    - In the GUI, go to **Deployment → Scenario Management → Deploy scenario**, select `Linux Resource Utilization`, and click **Deploy**.
    - In **Deployment → Agent Management → Onboard agent**, select `Linux Resource Utilization`, click **Mint token**, and run the printed `bootstrap-agent.sh` command on the agent host from inside `~/radar-agent`.

2. On the agent's host, start generating CPU stress (target CPU load 90%):
```bash
./linux_resource_utilization.sh --mode=cpu
```

3. Immediately after step 2 (while the CPU stress process is still running), go to the GUI's **Deployment → Anomaly Detector → Run Anomaly Detector** page, choose `Linux Resource Utilization`, **check** the ingest option box, and press **Run**. By selecting the ingest option, a sample of baseline data is generated based on the reference values added to `config.yaml` during the setup; the sample simulates logs received every 30 seconds during 240 minutes.

4. On the Wazuh dashboard, open **Explore → Anomaly Detection → Detectors → LINUX_RESOURCE_UTILIZATION_DETECTOR**. Wait up to 5 minutes, then record the `anomaly_grade` and `confidence` of the reported anomaly, along with the expected and observed values of the `cpu_usage_max`.

5. First run only: check the response to the anomaly.
    - On the controller, follow the active response log:
    `docker exec -it wazuh.manager bash -c 'tail -F /var/ossec/logs/active-responses.log'`
    - Check the inbox of the email address configured in `.env`.
    - (Optional) If DECIPHER is configured, open FlowIntel in the browser.

6. Run the steps in Cleanup.

## Cleanup

1. Bring down and remove the Wazuh stack from the GUI, using **Deployment → Teardown**.

2. Uninstall the agent from its host with:

```bash
cd ~/radar-agent
sudo ./uninstall-agent.sh --purge-data
```

Afterwards, verify that:

- `systemctl list-timers | grep radar-linux-resource-utilization` prints nothing
- `/usr/local/bin/radar-linux-resource-utilization-metric.sh` no longer exists
- `dpkg -l wazuh-agent` reports nothing.

## Expected outcome

1. Not checked in this test. If deployment or onboarding fails, the run is not counted: fix the setup and repeat [TST-061](./TST.html#TST-061).

2. The script runs without error, printing the CPU and memory lines and then `linux_resource_utilization simulation completed. Load released.`

3. The streamed output shows `Done` and contains the messages `[+] Created detector 'LINUX_RESOURCE_UTILIZATION_DETECTOR'` and `[✓] Started detector`. The "Output" screen does not show any errors.

4. Within 5 minutes, an anomaly meeting the Acceptance criteria is visible on the `LINUX_RESOURCE_UTILIZATION_DETECTOR` page of the Anomaly Detection dashboard of Wazuh.

5. Validate the following:

    - a. Active response messages are logged, including `Scenario identified {"scenario":"linux_resource_utilization","detection":"ad","rule_id":"100321","matched_by":"rule_id"}` and a computed `risk_score` of at least 0.21 (0.9 × 0.8 × 0.3, when DECIPHER returns no match).

    - b. An email with subject "[RADAR] linux_resource_utilization" is received at the email configured in `.env`; the email contains details about the alert and a link to a Flowintel case, if configured.

    - c. (Optional) A FlowIntel case titled `RADAR: abnormal CPU/memory utilization` is created and can be opened from the URL included in the email notification. The case contains the event, related MISP lookups, and the breakdown of the risk score including the assigned tier.

6. The cleanup validations described in "Cleanup" succeed.
