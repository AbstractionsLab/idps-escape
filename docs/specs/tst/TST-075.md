# RADAR: `suspicious_login` signature and anomaly fusion end to end

## Preconditions and setup actions

- Same generic preconditions as [TST-055](./TST.html#TST-055).
- `suspicious_login` deployed (rules, decoders including `0001-ad-common.xml`, active response), its off-hours monitors and detector created (`./radar.sh run suspicious_login`), and the agent bootstrapped with the `suspicious_login` group.
- The webhook running and reachable from the manager host (`http://127.0.0.1:8080/notify` by default), `WEBHOOK_SHARED_SECRET` set in `radar/.env`.
- `suspicious_login.py` and `inject_ad_alert.py` copied from `radar/radar-test-framework/simulate/scenarios/` to the agent host and the manager host respectively.

**Test data**: simulated SSH logins for users test01 and test02, and injected off-hour anomalies

## Test steps

1. Anomaly first: on the manager host run `python3 inject_ad_alert.py` (entity `test01`). Within 30 minutes, on the agent run `sudo python3 suspicious_login.py burst`.
2. Wait at least 30 minutes. Signature first: on the agent run `sudo python3 suspicious_login.py burst`, then within 5 minutes on the manager host run `python3 inject_ad_alert.py`.
3. Wait at least 30 minutes. Other user: set `entity` to `test02` in `inject_ad_alert.py`'s `CONFIG`, run it, then on the agent run `sudo python3 suspicious_login.py burst` (user `test01`).
4. For each step, inspect `/var/ossec/logs/active-responses.log` on the manager, the email, and (if DECIPHER is configured) the Flowintel case.

## Expected outcome

1. Rule 210040 fires for `test01` and its decision runs. The 210013 decision then logs `Fusion: counterpart matched` with `counterpart: ad` and the 210040 alert ID, and its risk score is higher than the 210013 score of step 3. With no CTI score: 0.168 alone, up to 0.384 with the default injected anomaly (grade 0.8 × confidence 0.9), less the further the burst is from the injected data window.
2. The 210040 decision logs `Fusion: counterpart matched` with `counterpart: signature` and a 210013 alert ID. It dispatches no `firewall-drop` and no `lock_user_linux.sh` (no source IP or Linux user in an anomaly alert), whatever its tier.
3. The 210013 decision logs `Fusion: no counterpart in window` and its risk score equals the single-alert score.
4. In steps 1 and 2, the email's scenario details and the case show the `fusion` match (alert ID, rule, gap, weight). Any mitigation of the 210013 decision targets only that alert's source IP and user `test01`.

## Cleanup

1. Restore `entity: "test01"` in `inject_ad_alert.py`.
2. If a mitigation ran, remove the firewall block and unlock `test01` on the agent.
