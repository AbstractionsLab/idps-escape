# Detection validation for Log volume abnormal growth

## Preconditions and setup actions
- RADAR is set up and run according to [TST-045](./TST.html#TST-045), and the detector has been running long enough to have a baseline for the endpoint (or history was seeded with `--ingest true`).

## Test steps
1. Copy `radar/radar-test-framework/simulate/scenarios/log_volume.py` to the endpoint. Edit its `CONFIG` if needed: `target_dir` (default `/var/log`), the growth (`start_bytes`, `growth_factor`, `steps`) and `cleanup_minutes`. The growth must be large enough to pass the detector's rules in `config.yaml` (deviations that are too small are ignored).
2. On the endpoint, run:
```bash
sudo python3 log_volume.py
```

## Expected outcome

2.1. The script ends with `log_volume simulation completed`.

2.2. The spike is visible on the endpoint:
```
tail -3 /var/log/radar/log_volume_metric.log
```

2.3. Within a few detector intervals, a line for the endpoint with trigger `LogVolume-Growth-Detected` is written to `/var/log/ad_alerts.log` in the webhook container, and in the Wazuh Dashboard Discover page rule 100309 is raised with `data.entity_keyword` set to the endpoint's agent name.

2.4. In the Wazuh manager, check the decision:
```bash
docker exec wazuh.manager grep -E "Scenario identified|Risk computed|Actions planned|Wazuh Active Response dispatched" /var/ossec/logs/active-responses.log | tail -20
```

   - The alert is identified as scenario `log_volume`, detection `ad`; the risk score is 0.9 × grade × confidence (no CTI source).
   - Expected `risk_score` range is between 0.0 and 1.0, and the tier follows the `tiers` boundaries of `log_volume` in `ar.yaml`.
   - If tier is:
      - Tier 0:
         - No email is received at `EMAIL_TO`.
         - No FlowIntel case is created.
         - No mitigation is dispatched (no `Wazuh Active Response dispatched` line for the decision).
      - Tier 1:
         - The email address specified in `EMAIL_TO` (from `.env`) receives a RADAR alert notification containing the risk score, its components and the tier.
         - A FlowIntel case is created when DECIPHER is reachable; its URL is in the email.
         - The FlowIntel case is tagged with low priority.
         - No mitigation is dispatched.
      - Tier 2:
         - Email and FlowIntel case as for Tier 1; the case is tagged with medium priority.
         - If `allow_mitigation` is true for `log_volume`, each command of `mitigations_tier2` is dispatched (`Wazuh Active Response dispatched`); otherwise `Actions planned` shows them under `would_be_mitigations` with `withheld_reason: mitigation_disabled`.
      - Tier 3:
         - Email and FlowIntel case as for Tier 1; the case is tagged with high priority.
         - If `allow_mitigation` is true for `log_volume`, each command of `mitigations_tier3` is dispatched; otherwise it is withheld as above.
   - Mitigation check on the agent:
      - `firewall-drop`: the alert's source IP is blocked.
      - `lock_user_linux.sh`: the alert's user is locked (never `root` or a protected user).
      - `terminate_service.sh`: the allowlisted service is stopped.

2.5. Verify that the spike file (`target_dir` / `spike_filename`) is removed after `cleanup_minutes` have elapsed (if `cleanup_minutes > 0`), or remove it manually if `cleanup_minutes` is set to 0.
