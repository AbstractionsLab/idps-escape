# RADAR: anomaly scenarios deployed together

## Preconditions and setup actions

- Same generic preconditions as [TST-055](./TST.html#TST-055).
- `log_volume` and `linux_resource_utilization` both deployed on the same manager, their detectors and monitors created, and an agent in both groups (optionally `suspicious_login` deployed as well).

**Test data**: log_volume and linux_resource_utilization simulations (inject mode for linux_resource_utilization)

## Test steps

1. Through the Wazuh server API, test a webhook line for each trigger with the location the rules require:
   ```
   PUT /logtest  {"event": "<webhook line>", "log_format": "syslog", "location": "/var/log/ad_alerts.log"}
   ```
   once with `OpenSearchAD LinuxResourceUtilization-Anomaly-Detected: entity="<agent>", …` and once with `OpenSearchAD LogVolume-Growth-Detected: entity="<agent>", …`.
2. Run the `linux_resource_utilization` simulation in inject mode on the agent, then the `log_volume` simulation, as in their own test specifications.
3. Inspect the alerts in the Wazuh dashboard and `/var/ossec/logs/active-responses.log`.

## Expected outcome

1. The resource-utilization line ends in rule 100321 and the log-volume line in rule 100309, each under the AD catch-all rule that matched first (100300 when `log_volume` is deployed).
2. Both simulations raise their trigger rule.
3. Both scenarios' active responses run and identify their own scenario (`linux_resource_utilization` for 100321, `log_volume` for 100309).
