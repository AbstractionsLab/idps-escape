# GUI: Unenroll, undeploy, and deregister the `log_volume` scenario

## Preconditions and setup actions
- Requires [TST-058](./TST.html#TST-058).

## Test steps

1. On the controller host, start the GUI (if not already running):
```bash
cd radar
./radar.sh gui
```
Open the GUI in a browser at the printed host:port.

2. On the Wazuh Dashboard, open **Agents management → Summary** and note the agent's current group membership before making any changes.

3. In the GUI, go to **Deployment → Group Management**. Enter the agent's IP/name, select scenario 'Log Volume Growth', and click **Unenroll from groups**.

4. On the Wazuh Dashboard, open **Agents management → Summary** again and check the agent's group membership.

5. In the GUI, go to **Deployment → Group Management** again. Enter the agent's IP/name, select scenario 'Log Volume Growth', and click **Assign group**, to re-enroll it before the next step.

6. In the GUI, go to **Deployment → Scenario Management**, open the **Undeploy scenario** sub-tab, select scenario 'Log Volume Growth', and click **Undeploy**.

7. In the GUI, open **Deployment → Status**, select scenario 'Log Volume Growth', and click **Run health check**.

8. On the manager host, confirm directly that the scenario's `ossec.conf` block is gone:
```bash
docker exec wazuh.manager grep -c "RADAR: log_volume" /var/ossec/etc/ossec.conf
```

9. On the Wazuh Dashboard, open **Agents management → Summary** once more and check the agent's group membership.

10. In the GUI, go to **Deployment → Agent Management**, open the **Deregister agent** sub-tab, enter the agent's name, and click **Deregister agent**.

11. On the Wazuh Dashboard, open **Agents management → Summary** and check whether the agent is still listed.


## Expected outcome

1. The GUI is reachable in a browser, with **Scenario Management**, **Agent Management**, **Group Management**, and **Status** tabs all present under **Deployment**.

2. The agent shows both the `default` and `log_volume` groups.

3. The streamed output ends with a JSON result and a success line, of the form:
```
=== SUCCESS: group unassignment for 'log_volume' completed ===
```

4. The agent now shows only the `default` group — `log_volume` has been removed, and `default` is untouched.

5. The streamed output ends with a JSON result and a success line, of the form:
```
=== SUCCESS: group assignment for 'log_volume' completed ===
```
and the agent is re-assigned to both `default` and `log_volume`.

6. The streamed output ends with:
```
=== SUCCESS: undo for 'log_volume' completed ===
```
with no `error` key present in either printed result.

7. Two items to verify:

  - (a) The four `wazuh-*` daemon checks, and the OpenSearch/Webhook checks at the bottom, all still report `OK`.
  - (b) The five checks for active-response wiring, group config, and the three decoder/rule files now report `FAIL`.

8. The command returns `0`.

9. The agent shows only the `default` group.

10. The streamed output ends with JSON result followed by success message:
```
=== SUCCESS: deregistration for '<agent-name>' completed ===
```

11. The agent no longer appears in the agents list at all.

## Cleanup

1. After finishing tests, clean up using the **Teardown** tab in the GUI.

2. The agent host is cleaned using the script:
```bash
scp uninstall-agent.sh <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x uninstall-agent.sh
sudo ./uninstall-agent.sh --purge-data
```
