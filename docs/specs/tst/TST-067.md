# SONAR anomaly sinks and Wazuh manager events

## Preconditions and setup actions

1. SONAR dependencies installed: `poetry install --with adbox,radar,test`.

## Test steps

1. From the repository root, run:
   ```
   poetry run pytest tests/sonartests/test_sinks.py tests/sonartests/test_realtime_delivery.py tests/sonartests/test_shipper.py -v
   ```

## Expected outcome

1. The SONAR event is one line of valid JSON with `integration: sonar`, `anomaly_grade`, `anomaly_confidence` (0.5 when the scenario sets none) and the `sonar` object (scenario, model, bucket start, severity, band, score, contributors); NaN values become null; the bands follow the configured boundaries.
2. The file transport appends one line per event, creates the directory, rotates by size keeping the configured number of files, and reports an unwritable file as a failed delivery.
3. The API transport authenticates once, sends at most 100 events per request to `POST /events` with the bearer token and the configured CA bundle, re-authenticates on 401, waits on 429 (honouring `Retry-After`) and gives up after repeated 429s, reports the accepted prefix when the manager rejects events, and takes the password from the environment when the configuration has none.
4. The rules file is well-formed, uses IDs 100500–100503 only, inside 100500–100519 and colliding with no rule under `radar/`; the base rule matches the event's `integration` value and the band rules its `sonar.severity_band` values; the rule group is the one alert searches exclude.
5. Alert searches exclude the `sonar` rule group by default, and not when the exclusion list is empty.
6. Sink selection: `wazuh` by default with watermarks; `--ship` adds the data stream; debug uses the debug sinks without watermarks; `--print-payloads` adds standard output; a dry run writes a JSON-lines file and ignores the watermarks; unknown sinks, fallbacks and transports are rejected; an `index` sink is refused in debug mode; an unset `anomaly_confidence` is warned about; the `output` section is read from YAML, nested sections included.
7. Each sink keeps its own watermark: a failed sink catches up on the next run while the others are not offered the anomalies again; a partial delivery advances over the accepted prefix only; the fallback takes what a sink rejected without moving the watermarks; the run fails only when every sink and the fallback failed.
8. `sonar wazuh install-rules` uploads the rules file with `PUT /rules/files/sonar_rules.xml?overwrite=true` as the given user, restarts the manager with `--restart`, and exits with 1 when the API refuses.
9. The data stream sink creates documents in bulk under their `anomaly_id`, counts existing ones as delivered and reports the accepted prefix; the ISM policy rolls over and deletes after the configured ages and attaches itself to `.ds-sonar_anomalies_*`, and an existing policy is kept; the per-scenario template has no feature component; anomaly documents carry no `rule` block.
10. A debug detection run prints SONAR events on standard output.
