# DECIPHER-RADAR detection validation for default rules

## Preconditions and setup actions
- RADAR is set up according to [TST-053](./TST.html#TST-053), with the endpoint's Wazuh vulnerability detection enabled (the manager default) and packages with known vulnerabilities installed on it.

## Test steps
1. Wait for the endpoint's package inventory to be collected and scanned (up to about 60 minutes after enrollment, depending on the syscollector and vulnerability detection intervals).
2. Optionally, on the endpoint, make repeated failed SSH logins for an existing user until a stock rule of the `authentication_failures` group fires.

## Expected outcome

1.1. At least one alert of rule IDs `23503`, `23504` or `23505` is raised for the endpoint (step 2: an alert in the `authentication_failures` group).

1.2. In the Wazuh manager, check the decisions:
```bash
docker exec wazuh.manager grep -E "Scenario identified|Risk computed|Actions planned|Wazuh Active Response dispatched" /var/ossec/logs/active-responses.log | tail -20
```

   - Each alert is identified as scenario `default` (matched by rule ID, or by the group `authentication_failures`), detection `signature`, unless its rule ID is mapped to another scenario (rule-ID matches take precedence over group matches).
   - The `default` scenario has no DECIPHER analysis endpoint, so the CTI score is 0 and, with the shipped `ar.yaml`, the risk score is `w_sig` 0.7 × likelihood × impact 0.5: 0.00035 (23503), 0.00175 (23504), 0.0035 (23505) and 0.105 (`authentication_failures`), all below `tier1_min` 0.15, so Tier 0. Only the PowerShell and command-shell rules 100401–100405 (Windows endpoints with Sysmon) score 0.21, Tier 1. No mitigation is configured.
   - Tier 0: no email, no FlowIntel case.
   - Tier 1: the email address specified in `EMAIL_TO` receives a RADAR alert notification with the risk score and tier; when DECIPHER is reachable, a FlowIntel case tagged with low priority is created and its URL is in the email.
