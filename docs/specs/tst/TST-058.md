# GUI: Build & validate `log_volume` scenario

## Preconditions and setup actions
- Same generic preconditions as [TST-055](./TST.html#TST-055).

## Test steps

1. On the controller host, prepare `.env`:
```bash
cd radar
cp env.example .env
```
Edit it with the values described in Preconditions (see [TST-055](./TST.html#TST-055)).

2. Start the GUI:
```bash
./radar.sh gui
```
This creates a Python virtual environment and installs dependencies automatically on first run. Open the GUI in a browser at the printed host:port.

3. In the GUI, go to **Deployment → Scenario Management** (default **Deploy scenario** sub-tab), select scenario `log_volume`, and click **Deploy**. If prompted for the sudo password, enter it.

4. In the GUI, go to **Deployment → Agent Management** (default **Onboard agent** sub-tab). Select scenario `log_volume`, click **Mint token**, and copy the printed `bootstrap-agent.sh` command.

5. On the agent host, download the `bootstrap-agent.sh` script and run the copied command exactly as printed, or by adding an `--agent-name` argument, under `sudo`:
```bash
scp bootstrap-agent.sh <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x bootstrap-agent.sh
```

6. In the GUI, go to **Deployment → Group Management**. Enter the agent's IP/name, select scenario `log_volume`, and click **Assign group**.

7. On controller host, adjust the agent name `agent_name` under ingest variables `ingest` of `log_volume` part in `radar/config.yaml`. The agent name should be the same as the agent name represented in Wazuh Dashboard.

8. In the GUI, go to **Deployment → Anomaly Detector** (card: **Run Anomaly Detector**), choose `Log Volume Growth`, check the ingest option, and press **Run**.

9. Check health of manager: in **Deployment → Status**, choose the Log Volume Growth scenario and press **Run health check**.

10. Wait 30 minutes for detector training, then copy the simulation script to the agent host and run it directly there:
```bash
scp radar-test-framework/simulate/scenarios/log_volume.py <user>@<agent-host>:~/
ssh <user>@<agent-host>
sudo python3 log_volume.py
```
This script is fully standalone.

11. (Optional) If DECIPHER is configured, open Flowintel in browser.

## Expected outcome

1. `.env` exists in the controller with the required variables set.

2. The GUI is reachable in a browser, and the **Deployment** page shows **Scenario Management**, **Agent Management**, **Group Management**, and **Anomaly Detector** tabs all present. On first run, a `.venv` directory is created under the RADAR root.

3. Two items to verify:

    - (a) The command completes with `=== SUCCESS` in its output.

    - (b) On the manager side (i.e. server node), confirm the index template was applied:

```bash
curl -u "$OS_USER:$OS_PASS" -k "$OS_URL/_index_template/radar-log-volume?pretty"
```

The template should be returned, not a 404.

4. A ready-to-run command of the form `sudo ./bootstrap-agent.sh --manager <address> --token <token> --group default --group log_volume` is printed.

5. The command completes with `=== SUCCESS ===` in its output.

6. On the Wazuh Dashboard, open **Agents management → Summary**. The agent should be assigned group `log_volume`.

7. N/A

8. Two items to verify:

    - (a) The streamed output completes without an `[ERROR]` line, and reports the detector was created and started. Checking the ingest option is required here — without it, the underlying index has no documents yet, and detector creation fails with an OpenSearch "Timestamp field... not found in index mapping" error.

    - (b) Confirm the index now has data:

```bash
curl -u "$OS_USER:$OS_PASS" -k "$OS_URL/_cat/indices/wazuh-ad-log-volume-*?v"
```

`docs.count` should be greater than `0`.

9. No `FAIL` lines should be present in the health check.

10. Three items to verify:

    - (a) `log_volume.py` is copied and runs on the agent host without error, printing "log_volume simulation completed".

    - (b) A spike or anomaly event is detected and visible on the log volume detector page of the Anomaly Detection dashboard of Wazuh.

    - (c) Active-response mitigation commands are logged in `active-responses.log`: `docker exec -it wazuh.manager bash -c 'tail -F /var/ossec/logs/ossec.log /var/ossec/logs/active-responses.log'`

    - (d) Confirm that rule `100309` (LogVolume-Growth-Detected) fires in Wazuh Dashboard (**Discovery**). And email notification is received.

11. (Optional) Items to verify:

    - (a) A FlowIntel case is created and can be accessed at the Flowintel URL included in the email notification.

    - (b) The FlowIntel case contains relevant information about the event, related events found in MISP, and a breakdown of the risk score including the assigned tier.


## Cleanup

1. After finishing tests, clean up using **Deployment → Teardown** in the GUI.

2. To clean agent host:
```bash
scp uninstall-agent.sh <user>@<agent-host>:~/
ssh <user>@<agent-host>
chmod +x uninstall-agent.sh
sudo ./uninstall-agent.sh --purge-data
```
