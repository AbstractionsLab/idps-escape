# Build suspicious login

## Preconditions and setup actions
- RADAR is set up according to [TST-041](./TST.html#TST-041): `radar/.env` filled in, Docker available on the controller host.
- A Linux endpoint reachable from the manager, with `sudo`.

## Test steps

1. On the controller host, the working directory is required to be `radar`:
```
cd radar
```

2. Build RADAR with the `suspicious_login` scenario (prefix with `sudo` if your user cannot run Docker):
```
./build-radar.sh suspicious_login
```
This brings up the core stack (indexer, manager, dashboard) and the webhook container, then deploys the scenario's manager-side files, agent group configuration, decoders, rules and lists.

3. Onboard the endpoint (see docs/manual/radar_docs/radar-getting-started.md, *Onboard an endpoint*):
```
sudo ./radar.sh mint-token default,suspicious_login,radar_shared 60
```
Copy the whole `radar/radar-agent/` folder to the endpoint and, from inside it, run the printed command, e.g.:
```
sudo ./bootstrap-agent.sh --manager <address> --token <token> --group default,suspicious_login,radar_shared
```

4. To clean up the test environment **only after** a _successful_ test execution **AND** a successful execution of [TST-046](./TST.html#TST-046):

- On the controller host: `./stop-radar.sh` (add `--purge` to also remove the volumes).
- On the endpoint, from the `radar-agent` folder: `sudo ./uninstall-agent.sh`.
## Expected outcome

### 2. Check the setup

#### In Wazuh Manager

Connect to the Wazuh manager to be able to perform the following verifications:
```
docker exec -it wazuh.manager bash
```
- **2.1** The RADAR-aware SSH decoders and the AD decoder are deployed:
```
ls -l /var/ossec/etc/decoders/0310-ssh.xml /var/ossec/etc/decoders/0001-ad-common.xml
grep -c 'with-radar' /var/ossec/etc/decoders/0310-ssh.xml
```
to ensure both files exist and `0310-ssh.xml` contains the `sshd-success-with-radar`, `ssh-failed-with-radar` and `ssh-invfailed-with-radar` decoders.

- **2.2** The stock SSH decoder file is excluded in `ossec.conf`:
```
grep '<decoder_exclude>0310-ssh_decoders.xml</decoder_exclude>' /var/ossec/etc/ossec.conf
```
to ensure the line appears once under `<ruleset>`.

- **2.3** The suspicious login rules are deployed:
```
grep -o 'rule id="[0-9]*"' /var/ossec/etc/rules/a3-suspicious-login.xml
```
to ensure rules 210013, 210020, 210021, 210022, 210030, 210031, 210039, 210040 and 210041 are present.

- **2.4** The rules are bound to the RADAR active response:
```
grep -A20 'RADAR: suspicious_login BEGIN' /var/ossec/etc/ossec.conf
```
to ensure the `radar_ar_suspicious_login` command runs `radar_ar.py` with `<location>server</location>` for `<rules_id>210013,210020,210021,210022,210030,210031,210040,210041</rules_id>`, and `lock_user_linux.sh` is declared.

- **2.5** The manager-side enrichment is installed and wired:
```
ls -l /var/ossec/integrations/custom-radar-enrich /var/ossec/integrations/radar_enrichment/
grep -A3 'custom-radar-enrich' /var/ossec/etc/ossec.conf
ls -l /var/ossec/etc/radar/
```
to ensure the integration script and its modules (`geoip.py`, `state_store.py`, `enrichment.py`) exist, the integration is declared for `authentication_success,authentication_failed` with a `localfile` for `/var/ossec/logs/radar/enriched_auth.log`, and `GeoLite2-City.mmdb` and `GeoLite2-ASN.mmdb` are present (downloaded when `MAXMIND_LICENSE_KEY` is set).

- **2.6** The agent group configuration is in place:
```
cat /var/ossec/etc/shared/radar_shared/agent.conf
```
to ensure it collects `/var/log/auth.log` as `syslog`.

- **2.7** The off-hours step is in the Filebeat archives pipeline:
```
grep -c 'radar-off-hours' /usr/share/filebeat/module/wazuh/archives/ingest/pipeline.json
```
to ensure the count is at least 1.

- **2.8** Active response files are in place:
```
ls -l /var/ossec/active-response/bin/radar_ar.py /var/ossec/active-response/bin/ar.yaml /var/ossec/active-response/bin/active_responses.env
```
to ensure all three exist.

- **2.9** The agent is registered with the manager:
```
/var/ossec/bin/agent_control -l
```
to ensure an active entry exists for the endpoint (and one for the webhook agent, `ad-webhook`).

- **2.10** Wazuh Manager is running after the deployment:
```
/var/ossec/bin/wazuh-control status
```
to ensure the status output indicates the manager is `running` with no error messages.
