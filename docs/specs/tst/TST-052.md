# Detection validation for scanning detection

## Preconditions and setup actions
- RADAR is set up according to [TST-051](./TST.html#TST-051).

## Test steps

1. Copy `radar/radar-test-framework/simulate/scenarios/scanning_detection.py` to the endpoint. Edit its `CONFIG` if needed: `log_path` (default `/var/log/suricata/eve.json`), `host`, `webdav_host` (a virtual host listed in `radar_webdav_apps`) and `fail_threshold` (must equal the `frequency` of rule 100825).
2. On the endpoint, run every case (they are spaced so that alerts stay attributable):
```bash
sudo python3 scanning_detection.py
```
or one case, e.g. `sudo python3 scanning_detection.py confirm_1_3`.

## Expected outcome

2.1. The script prints, for each case, the rules it expects and ends with `scanning_detection simulation completed`.

2.2. In the Wazuh Dashboard Discover page:

   - `i1_only` raises 100810 (level 3); `i2_only` 100825 (level 10); `i2_below` only 100815; `i3_only` 100820 and 100821 (level 6); none of them raises 100830.
   - `i2_spread`, `i3_excluded`, `webdav_app` and `legit` raise nothing above level 3.
   - `confirm_1_2`, `confirm_1_3` and `confirm_2_3` each raise 100830 (level 12) with the source IP; `confirm_split` does not.

2.3. In the Wazuh manager, check the decisions for 100830:
```bash
docker exec wazuh.manager grep -E "Scenario identified|Risk computed|Actions planned|Wazuh Active Response dispatched" /var/ossec/logs/active-responses.log | tail -20
```

   - Each 100830 alert is identified as scenario `scanning_detection`, detection `signature`; no other rule of the scenario produces a decision.
   - With the shipped `ar.yaml` the risk score is 0.378 + 0.3 × CTI score, so Tier 2 at least.
   - A source listed in `radar_scanning_allowlist` is still alerted, but its mitigation is declined: the audit entry in `/var/ossec/logs/active-responses.log` has `"result":"declined","reason":"allowlist"`.
   - Expected `risk_score` range is between 0.0 and 1.0, and the tier follows the `tiers` boundaries of `scanning_detection` in `ar.yaml`.
   - If tier is:
      - Tier 0:
         - No email is received at `EMAIL_TO`.
         - No FlowIntel case is created.
         - No mitigation is dispatched (no `Wazuh Active Response dispatched` line for the decision).
      - Tier 1:
         - The email address specified in `EMAIL_TO` (from `.env`) receives a RADAR alert notification containing the risk score, its components and the tier.
         - A FlowIntel case is created (DECIPHER reachable) and can be opened from the URL in the email. Its description contains the scenario, the alert, the risk score with its components and tier, the IOCs, and the MISP events DECIPHER found (`misp_events`).
         - The FlowIntel case is tagged with low priority.
         - No mitigation is dispatched.
      - Tier 2:
         - Email and FlowIntel case as for Tier 1; the case is tagged with medium priority.
         - If `allow_mitigation` is true for `scanning_detection`, each command of `mitigations_tier2` is dispatched (`Wazuh Active Response dispatched`); otherwise `Actions planned` shows them under `would_be_mitigations` with `withheld_reason: mitigation_disabled`.
      - Tier 3:
         - Email and FlowIntel case as for Tier 1; the case is tagged with high priority.
         - If `allow_mitigation` is true for `scanning_detection`, each command of `mitigations_tier3` is dispatched; otherwise it is withheld as above.
   - Mitigation check on the agent:
      - `firewall-drop`: the alert's source IP is blocked.
      - `lock_user_linux.sh`: the alert's user is locked (never `root` or a protected user).
      - `terminate_service.sh`: the allowlisted service is stopped.
