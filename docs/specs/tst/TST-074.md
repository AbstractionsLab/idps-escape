# RADAR: anomaly monitor, webhook and decoder contract

## Preconditions and setup actions

1. RADAR test dependencies installed (`pytest`, `responses`, `flask`, `pyyaml`).
2. RADAR's `radar/anomaly_detector` is importable as `anomaly_detector`: `run-tests.sh` sets this up. In an environment where another `anomaly_detector` package is installed (for example the SONAR dependency group), run the RADAR suite from an environment without it.

## Test steps

1. From the repository root, run:
   ```
   radar/tests/run-tests.sh
   ```

## Expected outcome

1. The monitor query returns up to `monitor_max_entities` results whose grade and confidence are both above their thresholds. Its message template renders to valid JSON carrying the top hit's keys (including `dataStart`/`dataEnd`) and an `anomalies` list with one entry per hit.
2. A deployed monitor whose stored payload fingerprint or detector differs is updated; one whose fingerprint matches is left alone. The detector ID is read from a stored monitor's nested query.
3. The webhook writes one line per entity, keeping the highest-graded hit, appends `data_start`/`data_end` in ISO UTC only when both are usable, still writes one line for a body without `anomalies`, skips invalid entries, and rejects a body whose entries are all invalid. Injection attempts in any field are rejected.
4. All copies of `0001-ad-common.xml` are identical, and both of its `opensearch_ad_detector` regexes match the line the webhook writes.
5. The trigger rules 100309, 210040, 210041 and 100321 attach to every AD catch-all rule (100300, 210039, 100320) through `if_group radar_ad_received`, and none uses `if_sid`.
6. The body built by `inject_ad_alert.py` is accepted by the webhook and produces a line for rule 210040.
