# Detection validation for GeoIP detection

## Preconditions and setup actions
- RADAR is set up according to [TST-043](./TST.html#TST-043); the GeoLite2 databases are installed on the manager. The endpoint runs Apache (or has `/var/log/apache2/access.log` monitored).

## Test steps
1. Copy `radar/radar-test-framework/simulate/scenarios/geoip_detection.py` to the endpoint. Edit its `CONFIG` if needed (`auth_log_path`, `web_log_path`, `hostname`).
2. On the endpoint, run every case:
   ```bash
   sudo python3 geoip_detection.py
   ```
   or one case, e.g. `sudo python3 geoip_detection.py ssh_non_whitelisted`.

## Expected outcome

2.1. The script prints, for each case, the rule it expects and ends with `geoip_detection simulation completed`.

2.2. In the Wazuh Dashboard Discover page, for the endpoint: `ssh_non_whitelisted` raises 100900 (level 10); `web_ip`, `web_domain`, `web_domainport` and `web_ip_ip` each raise 100902 (level 10) with `data.radar_country` decoded; `ssh_whitelisted`, `ssh_private`, `web_ip_whitelisted` and `web_private` raise none of them. 100902 requires the stock web rules to have raised a base alert for the request (the simulated status is 404).

2.3. In the Wazuh manager, check the decision for 100900:
```bash
docker exec wazuh.manager grep -E "Scenario identified|Risk computed|Actions planned|Wazuh Active Response dispatched" /var/ossec/logs/active-responses.log | tail -20
```

   - The alert is identified as scenario `geoip_detection`, detection `signature`. 100902 alerts produce no decision (not bound to the active response).
   - With the shipped `ar.yaml` the risk score is 0.54 (`w_sig` 1.0 × likelihood 0.9 × impact 0.6, no CTI) and the tier is 2.
   - Expected `risk_score` range is between 0.0 and 1.0, and the tier follows the `tiers` boundaries of `geoip_detection` in `ar.yaml`.
   - If tier is:
      - Tier 0:
         - No email is received at `EMAIL_TO`.
         - No FlowIntel case is created.
         - No mitigation is dispatched (no `Wazuh Active Response dispatched` line for the decision).
      - Tier 1:
         - The email address specified in `EMAIL_TO` (from `.env`) receives a RADAR alert notification containing the risk score, its components and the tier.
         - A FlowIntel case is created when DECIPHER is reachable; its URL is in the email.
         - The FlowIntel case is tagged with low priority.
         - No mitigation is dispatched.
      - Tier 2:
         - Email and FlowIntel case as for Tier 1; the case is tagged with medium priority.
         - If `allow_mitigation` is true for `geoip_detection`, each command of `mitigations_tier2` is dispatched (`Wazuh Active Response dispatched`); otherwise `Actions planned` shows them under `would_be_mitigations` with `withheld_reason: mitigation_disabled`.
      - Tier 3:
         - Email and FlowIntel case as for Tier 1; the case is tagged with high priority.
         - If `allow_mitigation` is true for `geoip_detection`, each command of `mitigations_tier3` is dispatched; otherwise it is withheld as above.
   - Mitigation check on the agent:
      - `firewall-drop`: the alert's source IP is blocked.
      - `lock_user_linux.sh`: the alert's user is locked (never `root` or a protected user).
      - `terminate_service.sh`: the allowlisted service is stopped.
