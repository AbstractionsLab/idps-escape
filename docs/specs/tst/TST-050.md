# Linux resource usage monitoring scenario

## Preconditions and setup actions

1. SONAR dependencies installed: `poetry install --with adbox,radar,test`.
2. `sonar/scenarios/linux_resource_monitoring.yaml` is present with `debug.enabled: false` (the `--debug` CLI flag is used instead).
3. The following local test data files exist:
   - `sonar/test_data/resource_monitoring/resource_monitoring_training.json` (24 hours, 1440 one-minute buckets)
   - `sonar/test_data/resource_monitoring/resource_monitoring_detection.json` (2 hours of normal context, then 6 hours with attacks at 01:00, 03:00 and 05:00 on 2024-12-15)

## Test steps

1. From the repository root, train the SONAR model for the Linux resource monitoring scenario using local debug data:
   ```
   poetry run sonar train --scenario sonar/scenarios/linux_resource_monitoring.yaml --debug
   ```

2. Verify the training log line `Fitting MVAD on ...` reports more than zero gradient steps, that training completes, and that a model directory is persisted under `sonar/models/` with the name matching the `model_name` field in the scenario YAML (`linux_resource_monitoring`).

3. From the repository root, run anomaly detection for the Linux resource monitoring scenario using the local debug detection data:
   ```
   poetry run sonar detect --scenario sonar/scenarios/linux_resource_monitoring.yaml --debug
   ```

4. Inspect the detection output and verify that anomalies are flagged inside each injected attack window: the CPU spike (01:00–01:45), the memory leak (03:00–04:00) and the fork bomb (05:00–05:08).

5. Verify that every reported anomaly belongs to a run of at least `min_consecutive` (4) consecutive anomalous 1-minute buckets, the scenario's calibrated sustained-anomaly criterion.

6. Verify that the derived features count the matching alerts per bucket: `is_cpu_high` counts alerts with `cpu_usage_% ≥ 80`, `is_memory_high` alerts with `memory_usage_% ≥ 80`, and `is_high_load` alerts with `1min_loadAverage ≥ 4.0`.

## Expected outcome

1. Training performs more than zero gradient steps and completes without error; a model directory named `linux_resource_monitoring` is persisted to disk.
2. Detection completes without error.
3. Anomalies are flagged inside each of the three attack windows.
4. Every reported anomaly is part of a run of at least four consecutive anomalous 1-minute buckets.
5. Derived features `is_cpu_high`, `is_memory_high`, and `is_high_load` hold per-bucket counts consistent with the raw metric thresholds applied to the detection data.
