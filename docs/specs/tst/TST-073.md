# RADAR: signature and anomaly fusion in the risk engine

## Preconditions and setup actions

1. RADAR test dependencies installed (`pytest`, `responses`, `pyyaml`).

## Test steps

1. From the repository root, run the RADAR suite:
   ```
   radar/tests/run-tests.sh
   ```
   or only these tests:
   ```
   cd radar && PYTHONPATH="$PWD/anomaly_detector:$PWD" pytest tests/py/test_radar_ar_fusion.py tests/py/test_radar_ar.py -v
   ```

## Expected outcome

1. Fusion is off unless a scenario enables it and has anomaly and signature rules with non-zero `w_ad` and `w_sig`. In the shipped `ar.yaml` only `suspicious_login` enables it, and no other shipped scenario queries the indexer for a counterpart.
2. Without a counterpart, an alert's risk score and components are exactly its single-alert ones. A counterpart raises only the component the alert does not carry and never lowers one.
3. A signature alert matches a trusted anomaly alert for the same user: weight 1 inside the anomaly's data window extended back by the lead, decreasing linearly to 0 at the window edge, falling back to the monitor period without a data window. Only the strongest counterpart counts. Anomaly alerts not written by the webhook agent from its log, and alerts for another user, are ignored.
4. An anomaly alert matches the scenario's signature alerts for the same user, with each rule's own likelihood, and never itself. Hybrid alerts are not fused.
5. A failing fusion lookup leaves the decision to proceed on the alert's own score; a match is reported in the decision's extras.
6. An anomaly alert yields no `firewall-drop` or `lock_user_linux.sh` target; `lock_user_linux.sh` targets only the users named in the alert, never context users. Hybrid alerts get their anomaly scores.
7. With the shipped calibration, `geoip_detection` rules 100900/100901/100903 reach T2 and 100902 stays T1; a `suspicious_login` signature alert alone keeps the tier it had with `tier2_max` 0.66, and reaches T3 only with a fused anomaly.
