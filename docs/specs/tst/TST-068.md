# Validate SONAR alerts in Wazuh through both transports

This test checks that SONAR anomalies become Wazuh alerts when SONAR runs on the manager host (`file` transport) and when it runs on a dedicated host without a Wazuh agent (`api` transport), that a RADAR scenario can act on them, and that SONAR does not read its own alerts.

SONAR's debug mode supplies the anomalies: with `output.debug_sinks: [wazuh]`, `--debug` scores the bundled resource-monitoring data and sends its anomalies to the manager. The injected CPU, memory and fork-bomb attacks reach a severity of about 0.45, so the lab configuration lowers the severity bands to make them `high`.

## Preconditions and setup actions

- A Wazuh 4.14.1 single-node stack, deployed with RADAR's core stack (`radar/docker-compose.core.yml` with `radar/volumes.yml`) on the controller host, with the indexer at `https://localhost:9200` and the server API at `https://localhost:55000`.
- Indexer credentials (`admin` and `$OS_PASS`) and an API administrator (`$WAZUH_AUTH_USER`, `$WAZUH_AUTH_PASS`, by default `wazuh-wui`).
- SONAR installed from the repository on the controller host (`poetry install --with adbox,radar,test`), and the resource-monitoring model trained:
  ```bash
  poetry run sonar train --scenario sonar/scenarios/linux_resource_monitoring.yaml --debug
  ```
- A second machine (the dedicated host) with network access to port 55000 of the controller, the repository and SONAR installed, and **no** Wazuh agent (`systemctl status wazuh-agent` reports no such unit).

### Setup

1. On the controller, create `sonar-lab.yaml` at the repository root:
   ```yaml
   wazuh:
     base_url: "https://localhost:9200"
     username: "admin"
     password: "<OS_PASS>"
     verify_ssl: false
   output:
     debug_sinks: [wazuh]
     wazuh:
       transport: file
       file_path: /srv/sonar/anomalies/anomalies.json
       severity_medium: 0.2
       severity_high: 0.3
   ```
2. Create the shared directory and let the manager read it, then add the `<localfile>` block of `sonar/wazuh/ossec-localfile.xml` to `/srv/wazuh/manager/etc/ossec.conf` (inside `<ossec_config>`, location `/var/log/sonar/anomalies.json`):
   ```bash
   sudo install -d -o "$USER" /srv/sonar/anomalies
   cat > /tmp/sonar-manager.yml <<'YAML'
   services:
     wazuh.manager:
       volumes:
         - /srv/sonar/anomalies:/var/log/sonar:ro
   YAML
   ```
   Recreate the manager with the overlay added to the compose files used for the stack (`-f /tmp/sonar-manager.yml`).
3. Install SONAR's rules and restart the manager:
   ```bash
   SONAR_WAZUH_ADMIN_PASSWORD="$WAZUH_AUTH_PASS" poetry run sonar wazuh install-rules --config sonar-lab.yaml --user "$WAZUH_AUTH_USER" --restart
   ```
4. Create the API user for the dedicated host, with a role that allows only `event:ingest`, as described in the setup guide (`docs/manual/sonar_docs/setup-guide.md`).

## Test steps

1. **Manager host, `file` transport.** On the controller run:
   ```bash
   poetry run sonar detect --scenario sonar/scenarios/linux_resource_monitoring.yaml --config sonar-lab.yaml --debug
   ```
   then, after one minute:
   ```bash
   curl -sk -u "admin:$OS_PASS" "https://localhost:9200/wazuh-alerts-*/_search?size=3" -H 'Content-Type: application/json' \
     -d '{"query":{"bool":{"filter":[{"term":{"rule.id":"100503"}},{"term":{"data.integration":"sonar"}},{"range":{"timestamp":{"gte":"now-15m"}}}]}}}'
   ```
2. **Dedicated host, `api` transport.** On the dedicated host, copy `sonar-lab.yaml`, set `output.wazuh.transport: api`, `api_url: https://<controller>:55000`, `api_username: sonar` and `wazuh.base_url` to the controller's indexer, export `SONAR_WAZUH_API_PASSWORD` with the `sonar` user's password, and run the command of step 1. Query the alerts as in step 1 and record, from one alert, `location`, `decoder.name`, `agent.name` and `full_log` if present.
3. **RADAR active response.** Add a test scenario to the lab copy of `radar/scenarios/active_responses/ar.yaml`:
   ```yaml
   sonar_anomaly:
     ad:
       rule_ids: ["100503"]
     w_ad: 1.0
     w_sig: 0.0
     w_cti: 0.0
     allow_mitigation: false
   ```
   deploy it with RADAR's usual procedure, repeat step 1, and inspect `/var/ossec/logs/active-responses.log` on the manager.
4. **No self-ingestion.** On the controller run:
   ```bash
   poetry run sonar detect --config sonar-lab.yaml --lookback-minutes 30 --dry-run
   curl -sk -u "admin:$OS_PASS" "https://localhost:9200/wazuh-alerts-*/_count" -H 'Content-Type: application/json' \
     -d '{"query":{"bool":{"filter":[{"range":{"timestamp":{"gte":"now-45m"}}}],"must_not":[{"terms":{"rule.groups":["sonar"]}}]}}}'
   ```
   and compare the `Fetched N of M matching alerts` line of the detection log with the count, which excludes SONAR alerts.

## Cleanup

1. Remove the `<localfile>` block, the overlay and `/srv/sonar/anomalies`; delete `sonar_rules.xml` (`DELETE /rules/files/sonar_rules.xml`) and the `sonar` API user, role and policy; restore `ar.yaml`; restart the manager.

## Expected outcome

1. Step 1 returns alerts of rule 100503 with `data.anomaly_grade` and `data.anomaly_confidence` numeric and `data.sonar.scenario` = `resource_monitoring`, within the period of the injected attacks (`data.sonar.bucket_start`).
2. Step 2 returns the same kind of alerts, sent from a host without a Wazuh agent with a user that can only ingest events; the recorded `location` and `decoder.name` show how API events are decoded (expected: decoded as JSON).
3. Step 3: `active-responses.log` shows RADAR handling a `sonar_anomaly` alert with the alert's grade and confidence, and no mitigation is executed.
4. Step 4: the number of matching alerts `M` equals the count that excludes the `sonar` rule group, although SONAR alerts exist in the window.
