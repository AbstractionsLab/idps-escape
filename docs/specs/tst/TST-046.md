# DECIPHER-RADAR detection validation for Suspicious login

## Preconditions and setup actions
- RADAR is set up according to [TST-042](./TST.html#TST-042), with DECIPHER reachable (`DECIPHER_BASE_URL`) and SMTP configured in `radar/.env`.

## Test steps
1. Copy `radar/radar-test-framework/simulate/scenarios/suspicious_login.py` to the endpoint. Edit its `CONFIG` if needed (`log_path`, default `/var/log/auth.log`; `hostname`).
2. On the endpoint, run every case (`burst`, `travel`, `failed_travel`, `composite`, `benign`):
   ```bash
   sudo python3 suspicious_login.py
   ```
   or one case, e.g. `sudo python3 suspicious_login.py burst`.

## Expected outcome

2.1. The script prints, for each case, the rules it expects and ends with `suspicious_login simulation completed`.

2.2. In the Wazuh Dashboard Discover page, for the endpoint: `burst` raises 210013 (level 8), `travel` 210021 (level 10), `failed_travel` 210020 (level 10), `composite` 210022 (level 12), and `benign` none of these rules.

2.3. In the Wazuh manager, check each decision:
```bash
docker exec wazuh.manager grep -E "Scenario identified|Risk computed|Actions planned|Wazuh Active Response dispatched" /var/ossec/logs/active-responses.log | tail -20
```

   - Each alert is identified as scenario `suspicious_login`, detection `signature`.
   - Expected `risk_score` range is between 0.0 and 1.0, and the tier follows the `tiers` boundaries of `suspicious_login` in `ar.yaml`.
   - If tier is:
      - Tier 0:
         - No email is received at `EMAIL_TO`.
         - No FlowIntel case is created.
         - No mitigation is dispatched (no `Wazuh Active Response dispatched` line for the decision).
      - Tier 1:
         - The email address specified in `EMAIL_TO` (from `.env`) receives a RADAR alert notification containing the risk score, its components and the tier.
         - A FlowIntel case is created (DECIPHER reachable) and can be opened from the URL in the email. Its description contains the scenario, the alert, the risk score with its components and tier, the IOCs, and the MISP events DECIPHER found (`misp_events`).
         - The FlowIntel case is tagged with low priority.
         - No mitigation is dispatched.
      - Tier 2:
         - Email and FlowIntel case as for Tier 1; the case is tagged with medium priority.
         - If `allow_mitigation` is true for `suspicious_login`, each command of `mitigations_tier2` is dispatched (`Wazuh Active Response dispatched`); otherwise `Actions planned` shows them under `would_be_mitigations` with `withheld_reason: mitigation_disabled`.
      - Tier 3:
         - Email and FlowIntel case as for Tier 1; the case is tagged with high priority.
         - If `allow_mitigation` is true for `suspicious_login`, each command of `mitigations_tier3` is dispatched; otherwise it is withheld as above.
   - With the shipped `ar.yaml`, a signature alert alone scores at most 0.468 and never reaches Tier 3: Tier 2 needs a CTI score of at least 0.54 (210013, 210022) or 0.73 (210020, 210021). Tier 3 with fusion is covered by [TST-075](./TST.html#TST-075).
   - Mitigation targets are only the alert's own source IP and users.
   - Mitigation check on the agent:
      - `firewall-drop`: the alert's source IP is blocked.
      - `lock_user_linux.sh`: the alert's user is locked (never `root` or a protected user).
      - `terminate_service.sh`: the allowlisted service is stopped.
