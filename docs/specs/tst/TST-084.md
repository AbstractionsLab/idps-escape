# RADAR scenario group delivery and undo

## Preconditions and setup actions

- Automated part (step 1): a repository checkout with `poetry install --with radar,test`. No RADAR stack, network or Docker is needed. The automated tests cover deployment and assignment; undo is covered by the manual part only.
- Manual part (steps 2 to 9):
  - A RADAR host with `radar/.env`, `sudo`, and the core stack running (`sudo ./build-radar.sh --core-only`); no scenario deployed.
  - One endpoint, `endpoint-a`, enrolled in group `default` only ([TST-082](./TST.html#TST-082)). No SSH or other access from the RADAR host to the endpoint is configured or used.
  - In a shell in `radar/`: export `WAZUH_API_URL`, `WAZUH_AUTH_USER` and `WAZUH_AUTH_PASS` with the values from `.env`, and define
    ```
    T=$(curl -sk -u "$WAZUH_AUTH_USER:$WAZUH_AUTH_PASS" -X POST "$WAZUH_API_URL/security/user/authenticate?raw=true")
    groups() { curl -sk -H "Authorization: Bearer $T" "$WAZUH_API_URL/agents?name=endpoint-a&select=group"; }
    confs() { docker exec wazuh.manager sh -c 'sha256sum /var/ossec/etc/shared/*/agent.conf'; }
    files() { docker exec wazuh.manager ls /var/ossec/etc/decoders /var/ossec/etc/rules; }
    ```

## Test steps

1. From `radar/`, run:
   ```
   PYTHONPATH=anomaly_detector:. poetry run pytest tests/py/test_scenario_ops.py tests/py/test_ruleset.py tests/py/test_manager_config.py tests/py/test_wazuh_api.py -v
   ```
2. **Deploy one shared scenario**: `confs > before.txt`; `sudo ./build-radar.sh suspicious_login`; `confs > after.txt`; `diff before.txt after.txt`.
3. **Delivery without endpoint access**: `./radar_deploy/manager-assign-agent-group.sh --scenario suspicious_login --agent-name endpoint-a`; `groups`. After the next agent keep-alive (about one minute), on the endpoint: `sudo grep -c /var/log/auth.log /var/ossec/etc/shared/agent.conf`.
4. **Deploy a second shared scenario**: `confs > before.txt`; `sudo ./build-radar.sh geoip_detection`; `confs > after.txt`; `diff before.txt after.txt`; `./radar_deploy/manager-assign-agent-group.sh --scenario geoip_detection --agent-name endpoint-a`; `groups`; `files`.
5. **Repeat deploy**: `sudo ./build-radar.sh geoip_detection` again; note the JSON result of the `deploy-manager-config` stage.
6. **Undo while the other shared scenario is deployed**: `confs > before.txt`; `./radar_deploy/manager-undo-scenario.sh geoip_detection`; `confs > after.txt`; `diff before.txt after.txt`; `groups`; `files`; `docker exec wazuh.manager grep -c 'RADAR: suspicious_login BEGIN' /var/ossec/etc/ossec.conf`; `./health-radar.sh --scenario suspicious_login --agent-name endpoint-a`.
7. **Repeat undo**: `./radar_deploy/manager-undo-scenario.sh geoip_detection` again.
8. **Undo the last shared scenario**: `./radar_deploy/manager-undo-scenario.sh suspicious_login`; `groups`; `files`; `docker exec wazuh.manager cat /var/ossec/etc/shared/radar_shared/agent.conf`.
9. **Never-deployed scenario**: `confs; files`; `./radar_deploy/manager-undo-scenario.sh scanning_detection`; `confs; files`.

## Expected outcome

1. All tests pass. In particular: shared scenarios get `default`, their own group and `radar_shared`, others only `default` and their own group; deploying a shared scenario writes both its own group and `radar_shared`, a non-shared one only its own; empty or whitespace-only snippets are not uploaded; hosts are resolved by IP before name and unresolved hosts are reported without stopping the others; ruleset files are uploaded only when their content differs; a second `deploy_manager_config` changes nothing and does not restart; the whitelist and scenario lists are deployed only for the scenarios that own them; marked blocks are inserted, replaced and kept idempotent.
2. Only the `agent.conf` of `suspicious_login` and `radar_shared` differ (or are new); `default` and the other groups are unchanged.
3. The assignment succeeds; `groups` lists `default`, `suspicious_login` and `radar_shared`. The endpoint's merged `agent.conf` contains `/var/log/auth.log` (count of at least 1), although nothing connected to the endpoint.
4. Only `geoip_detection` changes (`radar_shared` already carries the same snippet). `groups` adds `geoip_detection`. `0310-ssh.xml`, `0375-web-accesslog.xml` and `a2-geoip-detection.xml` are present.
5. The build completes without error, and the `deploy-manager-config` result reports no changed file or block and `"restart_triggered": false`.
6. Only the `agent.conf` of `geoip_detection` changes (reset to an empty `<agent_config>`). `groups` no longer lists `geoip_detection` but still lists `default`, `suspicious_login` and `radar_shared`. `a2-geoip-detection.xml` and `0375-web-accesslog.xml` are gone; `0310-ssh.xml`, still used by `suspicious_login`, is present. The `suspicious_login` block is still in `ossec.conf` (count 1), and the health check reports no `FAIL`.
7. Completes without error and without a manager restart.
8. `groups` lists only `default`. `a3-suspicious-login.xml` and `0310-ssh.xml` are gone. `rules/radar_rules.xml` (the `default` rules) is present. The `radar_shared` group has no member any more; its `agent.conf` is left in place and therefore reaches no agent.
9. Completes without error, and nothing on the manager changes (`confs` and `files` as after step 8).

The test passes when every expected outcome is observed.
