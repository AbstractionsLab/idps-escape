# RADAR deployment health check

As a security engineer or operator, I want a single-command tool that verifies the completeness and operational readiness of a RADAR deployment, so that misconfiguration, missing artifacts, or broken connectivity can be identified quickly after deployment or after infrastructure changes, without manually inspecting each component.

## Scope

**Tool coverage**: This requirement applies to RADAR deployments whose Wazuh manager node(s) run as Docker containers on the RADAR host and are registered in `radar/infra.yaml`, across all scenarios listed in `radar/config.yaml`. It covers every registered manager node, the indexer and webhook as seen from the manager side, and, when named agents are supplied, those agents' status as reported by the Wazuh management API.

**Invocation**: The health check shall be executable through a single entry-point script (`health-radar.sh`, also `radar.sh health` and the GUI's Status tab) that runs a manager-side check (container and file presence, reachability from inside the containers), a manager-side API check (Wazuh management API, OpenSearch, and the alert webhook, all over HTTP), and, only if named agents are supplied, an agent check via the Wazuh management API.

**Output**: Check results shall be printed as each section completes: manager checks, then manager API checks, then (if requested) named-agent checks. Each check line is marked `OK`, `WARN`, `FAIL` or, for a reachability check whose source container is not running, `SKIP`.

**Scope exclusions**: The health check is a validation tool. It shall not change the deployment's configuration, restart services, or remediate detected issues, with the single exception stated in requirement 4.

## Requirements

1. **Single entry point**: A single script shall be the sole invocation interface:

    - Accept a `--scenario <name|all>` argument and an optional `--agent-name <name1,name2,...>` argument. Manager nodes are always addressed through their containers and the Wazuh management API, never over SSH.
    - Run the manager checks, then the manager API checks, and, only if agent names are supplied, the named-agent checks.
    - Return a non-zero exit code if any underlying check fails to run.

2. **Manager checks**: Executed against each registered manager node's container, these shall verify:
    - **Container health**: the manager container and the alert-webhook container are running.
    - **Key file presence and ownership**: the active-response script, its configuration, and its environment file are present with the correct group ownership, along with the manager's core configuration files (a missing configuration file of the baseline agent group is reported as a warning, not a failure). Scenario-specific checks shall be verified as well:
        - For `suspicious_login` or `geoip_detection`: the manager's Python runtime and GeoIP library are available.
        - For `suspicious_login`: the manager-side enrichment files and GeoIP reference databases are present, the per-user enrichment state store exists and is writable (a store not yet created is a warning), and the enrichment error log is empty or absent.
        - For `log_volume`: the log-ingestion pipeline has the routing update it needs for log-volume metrics.
    - **Reachability**: OpenSearch, and DECIPHER when it is configured, are reachable from inside the manager container; for `log_volume` and `linux_resource_utilization`, the configured webhook endpoint is reachable from inside the indexer container.

    Separately, a check against the Wazuh management API shall verify:
    - **Core daemon status**: the manager's core processes are reported running, per cluster node when the manager runs as a cluster.
    - **Active-response wiring and scenario group configuration**: for each target scenario, the corresponding `ossec.conf` active-response block and agent-group configuration are present.
    - **Ruleset files**: the decoder and rule files each target scenario depends on are present; for `geoip_detection`, the country whitelist is additionally checked.
    - **Scenario agent state**: the agents assigned to all of each target scenario's group(s) and their connection status are reported; no such agent is a failure.
    - **Connectivity**: OpenSearch is reachable and its cluster health status is reported; for `log_volume`, the OpenSearch index template is additionally checked; the configured webhook endpoint responds (an unreachable webhook is a warning).

3. **Agent checks**: When agent names are supplied, a check against the Wazuh management API shall verify, with no direct connection made to the agent endpoint itself:

    - The named agent is registered and its connection status is active (a status of "never connected" is reported as a failure).
    - The agent's group membership includes the baseline group and, unless all scenarios were requested, the named scenario's group.

4. **Non-destructive execution**: No check defined by this requirement shall write to or modify any configuration file, ruleset, group or agent on the manager or on any agent. The single exception: before checking, the tool revokes an enrollment token whose expiry has passed but which is still active (which restarts the manager), so that an expired token never stays usable.

5. **Ordered output**: The tool shall print the manager section, then the manager API section, then (if requested) the agent section, each clearly labelled, so the full result is visible as a single, ordered output.

6. **Scenario filtering**: When a specific scenario is named, scenario-specific checks (ruleset file presence, `log_volume` pipeline/index-template checks, `geoip_detection` whitelist check, enrichment checks, expected agent group membership) shall be scoped to that scenario only. When all scenarios are requested, checks shall cover every scenario listed in `radar/config.yaml`.

## Rationale

Manual post-deployment verification of a RADAR stack requires inspecting container state, file presence and permissions, Python environments, and scenario-specific artifacts across multiple nodes. Without automation this is error-prone and time-consuming, and failures are typically discovered only when an alert fails to trigger rather than at deployment time. A single-command health check that surfaces all misconfiguration after deployment reduces mean time to operational readiness and provides a repeatable baseline for regression testing after infrastructure changes.

## Acceptance criteria

A complete health check run against a correctly deployed RADAR stack with at least one agent in the scenario's groups must complete without any `FAIL`, covering manager checks, manager API/OpenSearch/webhook checks, and (when requested) agent checks, using only the health check tool's `--scenario` and `--agent-name` options.

- The manager section, the manager API section, and (if requested) the agent section shall each print in full and in order; no section shall be silently skipped or interleaved with another.
- Against a deployment where a scenario's ruleset files, group configuration or active-response block are missing, the corresponding checks shall report `FAIL`.
