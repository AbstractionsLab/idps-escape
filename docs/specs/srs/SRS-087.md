# SONAR container image contains only SONAR

As an operator, I want to run SONAR as a standalone container that holds SONAR and its runtime dependencies only, so that deploying it never ships credentials or other subsystems and its models and outputs stay on the host.

## Scope

The SONAR image built from `sonar/Dockerfile.sonar` with the repository root as build context (`docker build -f sonar/Dockerfile.sonar -t sonar:v0.8 .`, also run by `build.sh sonar`), its build-context rules in `sonar/Dockerfile.sonar.dockerignore`, and the two ways the repository runs it: `sonar/sonar.sh` and the compose overlay `sonar/wazuh/docker-compose.sonar.yml`. The dependency groups are declared in `pyproject.toml`.

The per-Dockerfile ignore file is read by BuildKit, the default builder since Docker 23. The legacy builder reads the root `.dockerignore`, which the ADBox images share. See: docs/manual/sonar_docs/setup-guide.md#docker-deployment

## Requirements

1. **Content.** The image SHALL contain, under `/home/alab/soar`, only `pyproject.toml`, `poetry.lock`, `README.md`, the `sonar/` package (code, default configuration, example scenarios, debug datasets and the Wazuh rule and integration files) and ADBox's package file `adbox/__init__.py`, which the project's package declaration requires to exist (it is not importable without the rest of ADBox; SONAR never imports it). It SHALL contain no other ADBox file and no RADAR file. The Dockerfile SHALL copy these paths explicitly and never the whole build context.
2. **No secrets or local state.** Built with BuildKit, the build context SHALL be an allowlist of the paths above, and SHALL exclude, also inside `sonar/`: every `.env` file, every pickled file (`*.pkl`), the payload directory `sonar/payloads`, the delivery watermarks `sonar/models/state`, and Python caches. `adbox/assets/secrets` SHALL NOT be in the image with any builder.
3. **Dependencies.** The image SHALL install only the `main` and `sonar` Poetry dependency groups, which together declare everything SONAR imports, and none of the `adbox`, `radar`, `test`, `docs` or `plot` groups. It SHALL be based on Python 3.10.12.
4. **Process.** SONAR SHALL run as the unprivileged user `alab`, in `/home/alab/soar`, with the `sonar` console script as entry point and `--help` as default command, so that arguments given to the container are SONAR's command line.
5. **State on the host.** `sonar/sonar.sh` SHALL mount the host's `sonar/models`, `sonar/test_data`, `sonar/scenarios` and `sonar/default_config.yaml` over their places in the image, and the directory `$SONAR_ANOMALIES_DIR` (default `/srv/sonar/anomalies`) at `/var/log/sonar`, where the `wazuh` sink's file transport writes for the Wazuh manager to read. The compose overlay SHALL mount the same model, scenario, configuration and anomaly directories.

Model directories present in `sonar/models/` of the build context are copied into the image (only pickles and `state/` are excluded); the mount of `sonar/sonar.sh` hides them at run time.

### Rationale

The ADBox images need `adbox/assets/secrets`, which the shared root `.dockerignore` therefore lets through. A SONAR image built with `COPY .` would bake those secrets and any `.env` file into an image meant for distribution. ADBox's dependencies, including a git-hosted package, would enlarge the image and require git at build time for code SONAR never imports. A delivery watermark baked into the image would make a fresh container believe anomalies had already been delivered and suppress them. Keeping models, scenarios, configuration and anomaly files on the host lets a container be replaced without retraining or losing state, as a standalone process would ([MRS-041](../mrs/MRS-041.md)).

### Acceptance criteria

1. The Dockerfile copies only `pyproject.toml`, `poetry.lock`, `README.md`, `sonar/` and `adbox/__init__.py`, and installs `--only main,sonar`; the ignore file excludes everything else and the listed secret and state paths.
2. In a built image, `/home/alab/soar` holds only the paths of requirement 1; no `.env`, `*.pkl`, `sonar/payloads`, `sonar/models/state` or `adbox/assets` path exists; the SONAR dependencies are installed, and no package that only the `adbox`, `radar`, `test` or `docs` groups require is (for example `tabulate`, `ansible-core`, `selenium`, `pytest-cov` or `doorstop`).
3. The image runs as `alab`; `docker run --rm sonar:v0.8` prints SONAR's help and exits with 0.
4. Through `sonar/sonar.sh`, a debug-mode scenario run trains and detects, and the model it trains appears in the host's `sonar/models/`.
