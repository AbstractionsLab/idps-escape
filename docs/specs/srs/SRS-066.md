# RADAR scenario: web scanning detection

As a security engineer,
I want RADAR to detect web-layer scanning by combining three indicators that are each individually evadable but not all at once — scanner tool signatures, failed-request rate, and HTTP method abuse — and to apply automated response only where two or more agree on the same source.

## Scope

This requirement applies to detection of automated web-layer scanning against monitored HTTP servers, via three indicators: a known scanner signature in the User-Agent, an abnormal rate of failed requests, and use of HTTP methods a normal client would not send. Automated response is scoped to fire only when two or more indicators agree on the same source within a short window; a single-indicator match remains a detection-only alert and is out of scope for automated response.

Payload-level detection (SQLi, XSS, path traversal in request parameters) is out of scope for this scenario — that is a WAF function, handled separately.

## Requirements

1. RADAR shall evaluate the HTTP events of Suricata's `eve.json` on the monitored host (Wazuh group `ids`, Suricata `http.*` fields), read through the `scanning_detection` agent group. Every indicator rule attaches to the `ids` group and keys on the source IP field `src_ip`. Rules: `radar/scenarios/rules/scanning_detection/a4-scanning-detection.xml`.

2. RADAR shall fire **Indicator 1 — tool signature (100810, level 3)** when a request's User-Agent matches a known scanning tool: sqlmap, nikto, nmap, masscan, nuclei, gobuster, dirb/dirbuster, ffuf, feroxbuster, wfuzz, wpscan, joomscan, openvas, nessus, acunetix, burp, w3af, whatweb, arachni, skipfish, zgrab.

3. RADAR shall fire **Indicator 2 — failed-request rate**: rule **100815** (level 3, not bound to any response) records each 404/401/403 response; rule **100825** (level 10) fires when 100815 matches 20 times from the same source IP within 70 seconds. The threshold is to be calibrated per deployment.

4. RADAR shall fire **Indicator 3 — method abuse** (level 6): rule **100820** on TRACE, TRACK and CONNECT, and rule **100821** on the WebDAV set (PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK, SEARCH) for any virtual host (`http.hostname`) not listed in the CDB list `radar_webdav_apps`. OPTIONS is excluded (CORS preflight is legitimate high-volume traffic); PUT, DELETE, and PATCH are excluded (normal REST semantics). Virtual hosts that serve WebDAV natively (SharePoint, Nextcloud, CalDAV, SVN-over-HTTP, macOS Finder mounts) must be listed in `radar_webdav_apps`.

5. RADAR shall fire **Scan confirmation (100830, level 12)** when two or more of Indicators 1–3 match the same source IP within 300 seconds. Each ordered pair of indicators has its own low-level anchor rule (level 3, not bound to any response: 100826, 100827, 100828, 100829, 100831, 100832) that fires on an indicator when a different indicator matched the same source in the previous 300 seconds; 100830 is the child of all six. 100830 is the sole trigger for notification and active response.

6. Repeated matches of a single indicator alone shall never satisfy the confirmation rule: every anchor rule requires a prior match of a different indicator group.

7. RADAR shall enforce an allowlist only at the active-response handler, not in the detection rules, so an allowlisted source still raises alerts. A matching source's active response shall be declined and recorded in an audit entry (`decision_id, rule_id, source_ip, action, tier, result, reason`), with `reason: allowlist`.

8. RADAR shall raise operational alert **100835** (level 12, no attacker source IP or ATT&CK technique) and decline the active response if the allowlist cannot be read, rather than fail open. A declined block is recoverable; an executed block against unverified infrastructure is not, within its timeout. 100835 is raised from the audit entry itself (rule 100840 under the stock active-response log rule 650).

9. RADAR shall score 100830 as a signature alert (SRS-061; `ar.yaml` block `scanning_detection`: `w_sig` 0.7, `w_cti` 0.3, `signature_impact` 0.6, `signature_likelihood` 0.9), so a confirmation alone reaches Tier 2 and Tier 3 needs a high CTI score. The CTI score comes from the DECIPHER `suspicious_nt_scanning` analysis endpoint, sent the source IPs, URIs, methods, User-Agents, target host and the chain of rules that fired. Tier 2 and Tier 3 run `firewall-drop` against the source IP when `allow_mitigation` is true (false as shipped). `X-Forwarded-For` shall be used for the source IP only when the request came through an address listed in `trusted_proxies`.

See: docs/manual/radar_docs/radar-scenarios/scanning_detection_explained.md

## Planned extensions

> **Status: planned.** Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

- Deduplication of each indicator to at most one contributing event per confirmation window (a 300-second same-source `ignore` on 100810, 100820/100821 and 100825), so that one ongoing scan fires 100830 at most once per window.


## Rationale

Automated web scanning is the reconnaissance phase that typically precedes web application exploitation (ATT&CK T1595.002/T1595.003, OWASP OAT-014): before committing to an actual exploit, an attacker's tooling systematically probes an application to map its attack surface — which paths exist, which methods are accepted, which technologies are running. Detecting this phase gives defenders a chance to respond before exploitation begins, rather than only after a breach.

Since there are sophisticated detection evasion techniques, two indicators raises precision:

| Evasion applied | I1 tool signature | I2 failed-request rate | I3 method abuse |
|---|---|---|---|
| Spoof/randomize User-Agent | defeated | fires | fires |
| Mask request rate (`--delay`) | fires | defeated | fires |
| Distribute across many source IPs | fires | defeated | fires |
| Restrict to GET/POST only | fires | fires | defeated |


## Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

**Detection**:

1. **Indicator 1 fires** — one request carrying a scanner User-Agent fires 100810 at level 3, and the alert carries the matched User-Agent value.
2. **Indicator 1 does not escalate** — 100810 from one source, at any repetition count, produces no notification and no active response.
3. **Indicator 2 above threshold** — the calibrated count of failed responses from one source within the window fires 100825 at level 10.
4. **Indicator 2 below threshold** — one event fewer in the same window fires 100815 and does not fire 100825.
5. **Indicator 2 does not escalate** — 100825, at any repetition count, produces no notification and no active response. Confirms that notification and response bind by rule ID rather than by alert level.
6. **Indicator 2 source isolation** — the threshold count distributed across distinct sources fires 100825 for none of them.
7. **Indicator 3 fires** — one TRACE request and one PROPFIND request, each carrying a common browser User-Agent, each fire 100820 at level 6. Establishes that detection does not depend on the User-Agent value.
8. **Indicator 3 exclusions** — sustained OPTIONS traffic and routine PUT, DELETE, and PATCH requests fire nothing. Where the WebDAV subset is disabled for an application, PROPFIND fires nothing.
9. **Two-indicator confirmation** — two distinct indicators matching the same source within 300 s fire 100830 at level 12, carrying source IP, agent name, and ATT&CK technique. All three pairings verified.
10. **Single-indicator non-escalation** — one indicator alone, at any volume, does not fire 100830. Includes a sustained failed-request case spanning more than one Indicator 2 window.
11. **Confirmation source isolation** — two distinct indicators matching two different sources within 300 s do not fire 100830.
12. **Legitimate traffic** — a representative normal session, sustained CORS preflight traffic, and uptime-monitor and CI smoke-test traffic each produce no alert above level 3. A verified search-engine crawl including failed requests produces no alert above level 3 where the calibrated threshold exceeds its failure rate; where it does not, the crawl may fire 100825 at level 10 but shall not fire 100830 and shall not notify.

**Response**:

13. **Response binding** — 100830 is the only rule bound to active response; any indicator rule present in the binding fails this criterion.
14. **Mitigation executed** — a tier 2 risk score with `allow_mitigation` enabled blocks the source at the enforcement point (verified by inspecting enforcement state, not the handler's exit status), audited as `executed`/tier 2, and the block is gone after its configured timeout (verified the same way).
15. **Mitigation withheld** — an out-of-tier-2 risk score, or `allow_mitigation` disabled, alerts at level 12 with no change to enforcement state, recorded in the audit log.
16. **Allowlist guard** — an allowlisted target still alerts at 100830, but the handler declines before acting, enforcement state is unchanged, and the audit entry records `declined`/`allowlist`.
17. **Allowlist unreadable** — the handler declines, raises 100835 at level 12 naming the failure, enforcement state is unchanged, and the audit entry records `declined`/`allowlist_unreadable`.
