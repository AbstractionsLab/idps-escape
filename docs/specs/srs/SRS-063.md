# RADAR SOAR web interface: REST API

As a security engineer,
I want a REST API that exposes RADAR's scenario and active-response configuration, connector settings, infrastructure registration, and deployment actions as structured HTTP resources, so that the RADAR web interface can read and write configuration and trigger operational actions without directly editing files or invoking scripts on the Wazuh manager host.

## Scope

**API coverage**: This requirement defines the REST API that backs the RADAR web interface (`radar/gui/app.py`). It covers six groups of endpoints under `/api/`: scenario configuration (list, detail, active-response settings, bind/unbind, deployment status), connector configuration (external service settings, secret reveal and connection tests), infrastructure registration (dashboard, manager and indexer nodes, reachability tests), the sudo credential session, logout, and deployment actions (scenario deploy/undeploy, anomaly detector, agent onboarding and lifecycle, enrollment window, health checks, teardown, preview).

**Relationship to SRS-070**: The deployment action endpoints exist to back the interface described in SRS-070. This requirement defines their existence, request/response shape, and streaming behaviour; SRS-070 defines what each action does operationally and how it is presented to the user.

**Persistence backend**: Scenario and active-response configuration is stored in `ar.yaml`, connector configuration in the RADAR `.env` file, and infrastructure registration in `infra.yaml`, each read and written directly by the API process. None is a database, and none is presented to the frontend as one.

## Requirements

### Access control

1. Every request shall be refused unless its `Host` header names an allowed host (the loopback names on the GUI port, the configured bind address, and any host listed in `RADAR_GUI_ALLOWED_HOSTS`).
2. Unless authentication is explicitly disabled (`RADAR_GUI_AUTH=off`), every request shall be refused unless it carries the login token generated at server start (or set in `RADAR_GUI_TOKEN`). Opening the login URL with the token sets an HttpOnly, SameSite=Strict cookie that authenticates later requests.
3. State-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) shall be refused unless they are sent as JSON and are not cross-site or cross-origin.
4. A logout endpoint shall stop the GUI's running jobs, clear every stored sudo credential, clear the cookies, and shut the server down.

### Scenario endpoints

5. A scenario list endpoint shall return every scenario the interface is allowed to show (`gui_visible` in `radar/config.yaml`), each with an identifier, display name, description, status, detection type (signature, anomaly, hybrid, derived from the scenario's risk weights), and its rule IDs, plus whether it is currently bound and whether it is a shared scenario. For each bound scenario, its active-response configuration shall be included inline.

6. A scenario detail endpoint shall return the same record for a single named scenario, or a not-found error if the scenario does not exist. The baseline `default` scenario shall be returned as always bound.

7. An active-response configuration endpoint shall support reading a scenario's active-response configuration on its own, and separately updating it. An update shall accept a partial set of fields and merge them into the existing configuration; it shall not require the caller to resend the full configuration. Mitigation names not listed in the active-response catalog (`radar/radar-agent/ar-scripts.yaml`, plus the built-in `firewall-drop`) shall be rejected.

8. Bind and unbind endpoints shall add a scenario's active-response block to, or remove it from, `ar.yaml`. The `default` scenario and scenarios with status `demo` cannot be bound or unbound.

9. A deployment-status endpoint shall report, for each scenario, whether it is recorded as deployed.

### Connector endpoints

10. A connector list endpoint shall return the current value of every connector field except secret-bearing fields, plus, for each secret-bearing field, whether a value is currently set.

11. A per-connector save endpoint shall accept and persist a connector's fields. Changing an endpoint address that receives a stored secret (for example the OpenSearch or Wazuh API URL) without supplying a new secret in the same request shall require an unlocked sudo credential.

12. A reveal endpoint shall return the current value of a single secret-bearing field, restricted to a fixed set of fields, and only while the caller's sudo credential is unlocked.

13. A per-connector test endpoint shall attempt a live connection check for the named connector using its currently saved fields, and report whether it succeeded.

### Infrastructure endpoints

14. Endpoints shall read, create, update and delete the dashboard registration and the manager and indexer node registrations (container name, host, port, scheme), set the primary node of a role, detect the GUI host's own address, and test reachability between two registered components.

### Credential-session endpoints

15. Status, unlock and lock endpoints shall manage the host sudo password for the caller's session. Unlock shall verify the password with `sudo` before storing it. The password shall be associated with the session through a single session cookie, held in the server's memory, dropped after an idle period (`RADAR_SUDO_IDLE_MINUTES`, default 15 minutes), and never persisted; a privileged action receives it through an owner-only temporary file deleted when the action ends.

### Deployment action endpoints

16. Each deployment action (build, undo scenario, run anomaly detector, health check, mint token, assign and unassign agent group, deregister agent, enrollment window, teardown) shall have its own endpoint taking a JSON specification, and shall stream the action's output as plain text while it runs rather than only on completion. An action that needs host privileges and has no unlocked sudo credential shall be refused with a response that tells the frontend to prompt for it.

17. A preview endpoint shall return the commands a deployment action would run without executing them.

### Error handling

18. Every JSON endpoint's error responses shall indicate failure and include a human-readable message, and shall use standard HTTP status codes to distinguish a refused request, a missing resource, an invalid request and a server-side failure. Streaming endpoints report errors in the stream as lines starting with `[ERROR]`.

## Rationale

RADAR's configuration and operational actions are otherwise only reachable by editing files or running scripts directly on the RADAR host. A REST API layer gives the web interface a stable way to read and change that configuration and to trigger deployment actions, without requiring direct host access or knowledge of the underlying file formats and scripts. Because these actions include privileged ones on the host, the API is reachable on the loopback interface by default and is protected by a login token, a host allowlist and cross-site request checks.

## Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

1. **Access control**: a request with a disallowed `Host`, without the login token, or a cross-site state-changing request is refused; a request with the token cookie succeeds.
2. **Scenario list and detail**: the list endpoint returns every visible scenario with its identifier, name, description, status, detection type, rule IDs, bound state and shared state, bound scenarios include their active-response configuration, and the detail endpoint returns a not-found error for an unknown scenario.
3. **Active-response read and update**: a partial update changes only the supplied fields, and an unknown mitigation name is rejected.
4. **Connector list, save and reveal**: the list endpoint omits secret values while indicating which are set, a connector's fields can be saved, and a secret can be revealed only for an allowed field and only with an unlocked sudo credential.
5. **Connector test**: the test endpoint reports success or failure for each connector type based on its currently saved fields.
6. **Credential sessions**: a wrong sudo password is not stored; a stored one is dropped after the idle period and on logout.
7. **Deployment action streaming**: a long-running deployment action streams its output progressively rather than only on completion.
8. **Preview**: the preview endpoint returns the commands a deployment action would run without executing it.
9. **Error handling consistency**: failure responses are distinguishable from success, carry a human-readable message, and use an HTTP status code appropriate to the failure type.
