# RADAR automated test framework

As a security engineer,
I want the RADAR test workflow to be scripted end to end for reproducibility, from bringing up the stack and feeding scenario data to exercising detections and active responses and collecting results, so that a test run does not depend on hand-made steps.

## Scope

**Framework coverage**: This requirement applies to the test workflow for the RADAR detection scenarios listed in `radar/config.yaml` (`suspicious_login`, `geoip_detection`, `log_volume`, `scanning_detection`, `linux_resource_utilization`). The workflow has four phases: setup, ingest, simulate and evaluate.

**Phase ownership**: Setup and ingest reuse the deployment tooling rather than test-only code: setup is `build-radar.sh` (or the GUI's Scenario Management) plus endpoint onboarding with `radar-agent/bootstrap-agent.sh`, and ingest is `run-radar.sh <scenario> --ingest true` (or the GUI's Anomaly Detector tab). Simulation is the RADAR Automated Test Framework proper (`radar/radar-test-framework/`, SRS-059). Evaluation is not implemented yet (see planned extensions).

**Execution environment**: Tests run against a real RADAR deployment (Wazuh manager, indexer, dashboard and webhook containers on the RADAR host) and real enrolled Linux endpoints, so that the tested path is the production path.

## Requirements

1. **Scripted environment setup**: The full RADAR stack and one scenario shall be deployable from a defined baseline with one command, using the project's standard deployment tooling:

   - Bring up the Wazuh core stack and the webhook with Docker Compose, and apply the scenario's manager-side configuration (decoders, rules, lists, `ossec.conf` blocks, active-response files, enrichment) from the repository.
   - Onboard a test endpoint with one command run on the endpoint.
   - Verify component health and readiness with the deployment health check (SRS-060) before simulating.

2. **Scripted data ingest**: For anomaly-detection scenarios that ship an ingest script (`log_volume`, `suspicious_login`, `linux_resource_utilization`), the detector's baseline history shall be loadable without manual steps:

   - Write synthetic history into the indices the scenario's detector reads, in the format the detector expects, with parameters taken from the scenario's `ingest` section in `radar/config.yaml`.
   - Create and start the detector and monitor after ingest, so the detector trains on the seeded history.

3. **Scripted threat simulation**: Every scenario shall have a simulation that produces, on a monitored endpoint, the artefacts the scenario detects, as specified in SRS-059. Simulations shall cover cases that should raise an alert and cases that should not, and shall print the rule IDs expected for each case.

4. **Live checks**: Where a detection depends on cluster-side processing that cannot be observed on the endpoint (currently the off-hours marking pipeline, rule mode and model mode of `suspicious_login`), scripted checks run from the RADAR host against the indexer shall report pass or fail per case.

## Rationale

Manual test execution of multi-component security systems is error-prone and difficult to reproduce. Scripting each phase with the same tooling used in production gives identical environment state and data flow across runs, and provides a regression baseline for detection behaviour.

## Acceptance criteria

Successful validation according to the corresponding test case specification. For at least one detection scenario, a run must be demonstrable in which setup, ingest (where the scenario has an ingest script) and simulation are each performed by a single scripted command, and the expected alert and active response are observed.

## Planned extensions

> **Status: planned.** Not implemented as of v2.2.0. The extensions below specify intended behaviour; no code implements them yet.

- **Automated evaluation**: compare detection results with the expected outcome of each simulated case (true positive, false positive, false negative, true negative); compute detection rate, false positive rate, response latency and active-response success rate; write a structured, machine-readable report that can be archived and compared across runs.
- **Single orchestrated run**: one entry point that runs setup, ingest, simulation and evaluation in sequence, from a clean environment to a report, with no manual intervention.
- **Audit trail**: persist test execution steps, ingested datasets, simulation parameters, detection results and evaluation metrics as test artefacts.
