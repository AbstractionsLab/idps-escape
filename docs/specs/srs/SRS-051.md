# RADAR scenario: suspicious login

As a security engineer,
I want RADAR to detect suspicious login activity (failed-login bursts, impossible travel, Office 365 brute force, and off-hours activity) and apply the RADAR risk policy to contain the attack.

## Scope

**Signature side**:

- SSH authentication on Linux endpoints, read from `/var/log/auth.log` through the agent configuration shared by the `radar_shared` group (`radar/scenarios/agent_configs/_shared/`). The stock Wazuh rules 5715 (success) and 5760 (failure) and the groups `authentication_success` / `authentication_failed` are the base events.
- Office 365 login failures received through the Wazuh Office 365 module (stock parent rule 91545).

**Enrichment**: the manager-side RADAR enrichment integration (SRS-068, `custom-radar-enrich`) appends GeoIP and velocity fields to each SSH authentication line; the RADAR-aware decoders in `radar/scenarios/decoders/suspicious_login/0310-ssh.xml` (which replace the stock `0310-ssh_decoders.xml`) extract `radar_country`, `radar_geo_velocity_kmh`, `radar_country_change_i`, `radar_asn_novelty_i` and related fields.

**Anomaly side**: off-hours activity against declared working hours (SRS-062), delivered as anomaly alerts through the RADAR webhook.

## Requirements

1. **Signature rules** (`radar/scenarios/rules/suspicious_login/a3-suspicious-login.xml`). RADAR shall raise:

   - **210013** (level 8), failed-login burst: repeated stock failures (5760) for the same user within 60 seconds (`frequency` 5).
   - **210020** (level 10, failed login) and **210021** (level 10, successful login), impossible travel: the enriched `radar_geo_velocity_kmh` is above 900 km/h.
   - **210022** (level 12), credential compromise: an impossible-travel success (210021) for a user who had repeated failures (5760, `frequency` 4) within the previous 300 seconds.
   - **210030** (level 5), Office 365 login failure (`UserLoginFailed` under 91545), and **210031** (level 10), Office 365 brute force: repeated 210030 for the same `office365.UserId` within 300 seconds (`frequency` 3).

   These rules need no training period.

2. **Anomaly rules**. Off-hours activity alerts (SRS-062) shall reach Wazuh through the RADAR webhook and the shared `opensearch_ad` decoder, under the catch-all 210039, as **210040** (model mode) and **210041** (rule mode). Both carry the user as `entity_keyword` and are scored as the scenario's anomaly side.

3. **Response binding**. Rules 210013, 210020, 210021, 210022, 210030, 210031, 210040 and 210041 shall be bound to the RADAR active response on the manager (`radar/scenarios/ossec/radar-suspicious-login-ossec-snippet.xml`), and mapped to the `suspicious_login` scenario in `ar.yaml` (signature rules under `signature.rule_ids`, 210040/210041 under `ad.rule_ids`).

4. **Risk scoring** (SRS-061, `ar.yaml` block `suspicious_login`):

   - $R = w_{ad} \cdot A + w_{sig} \cdot S + w_{cti} \cdot T$ with the shipped weights 0.3 / 0.4 / 0.3, `signature_impact` 0.7, and per-rule `signature_likelihood` (0.6 for 210013, 210022, 210030, 210031; 0.4 for 210020, 210021).
   - $T$ is the score returned by the DECIPHER `suspicious_login` analysis endpoint. The request names the user of the alert itself, else the anomalous user of an anomaly alert, else the first user in the context events.
   - Signature and anomaly alerts for the same user shall be combined by fusion (SRS-061 requirement 7; shipped window 30 minutes, lead 10 minutes).
   - Shipped tier boundaries 0.15 / 0.33 / 0.55: a signature alert alone scores at most 0.468 and so never reaches Tier 3; Tier 3 needs a signature alert combined with an anomaly.

5. **Context**. For a signature alert the context is the alert agent's events in the last `delta_signature_minutes`; for an anomaly alert it is the named user's events on any agent in the last `delta_ad_minutes` (`SuspiciousLogin` in `radar/scenarios/active_responses/radar_ar.py`).

6. **Mitigation** (only when `allow_mitigation` is true):

   - Tier 2: `firewall-drop` of the alert's own source IP.
   - Tier 3: `firewall-drop` and `lock_user_linux.sh` for the Linux users named in the alert itself, never `root`, never an account listed in `protected_users` or the agent's protected-users file.
   - An anomaly alert names no source IP or Linux user, and an Office 365 alert names no Linux user, so they block or lock nothing.

7. **Audit**. Every decision shall be recorded per SRS-061 (decision ID, risk components, tier, planned and withheld actions, outcomes).

See: docs/manual/radar_docs/radar-scenarios/suspicious_login_explained.md, docs/manual/radar_docs/radar-tuning.md

## Planned extensions

> **Status: planned.** Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

- Impossible-travel rules that also require a country change (`radar_country_change_i` = 1). The field is decoded, but rules 210020/210021 check only the velocity, although their descriptions mention a country change.
- Further protocols: RDP, web-application and database logins.
- SSO account lockout (Keycloak/LDAP), host isolation, ITSM tickets and submission of indicators to MISP/OpenCTI.

## Rationale

Failed-login bursts indicate brute-force or credential stuffing (MITRE ATT&CK T1110); impossible travel indicates stolen credentials used from unauthorized locations. Deterministic signature rules give sub-minute detection without training; off-hours anomalies add behavioural evidence, and fusion lets the two together, but neither alone, reach the most intrusive response.

## Acceptance criteria

Successful validation according to the corresponding test case specifications, which shall verify:

1. **Failed-login burst**: six failed SSH logins for one user within 60 seconds fire 210013.
2. **Impossible travel**: successful logins Poland → USA → Australia fire 210021; failed logins France → USA → Australia fire 210020.
3. **Credential compromise**: a failed-login burst followed within 300 seconds by an impossible-travel success for the same user fires 210022.
4. **No false positive**: two successful logins from the same region one hour apart fire none of these rules.
5. **Scoring**: for known inputs the risk score matches the formula and shipped weights, and a signature alert alone never reaches Tier 3.
6. **Fusion**: a signature alert and an off-hours anomaly for the same user within the window combine, in either order; an anomaly for another user does not.
7. **Targets**: any `firewall-drop` targets only the alert's source IP and any `lock_user_linux.sh` only the alert's own users, never `root`.
