# RADAR GUI deployment interface

As a security engineer or operator,
I want a single browser-based interface to deploy, undeploy, onboard, unenroll, deregister, and health-check RADAR scenarios and agents, so that the full operational lifecycle of a RADAR deployment can be managed without typing commands on the RADAR host.

## Scope

This requirement covers the RADAR web interface's Deployment page (`radar/gui/templates/deploy.html`, `radar/gui/orchestrator/deploy.py`): scenario deployment and its reversal, agent onboarding and deregistration, agent group assignment and its reversal, agent enrollment window control, anomaly detector creation, deployment health checking, and stack teardown. It also covers the credential handling shared across the actions on this page that require elevated host privileges. Registering the infrastructure components the actions target is done on the Infrastructure page (SRS-064).

## Requirements

1. The interface shall allow deploying a named scenario, or bringing up the underlying Wazuh stack with no scenario applied, and shall stream the operation's output to the user as it is produced. The interface shall show which scenarios are currently recorded as deployed.

2. The interface shall allow reversing a previously deployed scenario's configuration, streaming its output as it is produced, safe to invoke whether or not the scenario is currently deployed.

3. The interface shall allow minting a short-lived enrollment token for a selected scenario, scoped to the `default` group, the scenario's group and, for shared scenarios, `radar_shared`, automatically opening the agent enrollment window for the token's duration. It shall present the resulting onboarding command (`bootstrap-agent.sh`, run from the `radar-agent` folder on the endpoint) as a distinct element the user can copy directly, separate from the general streamed log output.

4. The interface shall allow removing an agent's registration from the manager entirely.

5. The interface shall allow assigning an already-enrolled agent to a scenario's group(s), and separately allow unenrolling it from them while leaving its `default` membership untouched, without requiring direct access to the agent endpoint for either action.

6. The interface shall allow opening, closing, and checking the status of the agent enrollment window independently of minting a token.

7. The interface shall allow creating and starting the anomaly detector and monitor for a scenario that uses one, with an option to first ingest a training dataset. Only such scenarios shall be offered.

8. The interface shall allow running the deployment health check scoped to a single scenario or to all scenarios, optionally including specific named agents, and shall stream the result.

9. The interface shall allow stopping the locally managed stack after explicit confirmation, with an explicit, separately presented option to also permanently delete its data (the containers' named volumes and the manager's host-side directories listed in `volumes.yml`); the default action shall not delete data, and scenarios stay recorded as deployed.

10. Actions that require elevated host privileges (bringing up the stack and deploying a scenario, minting a token, enrollment window control, and teardown) shall share a single credential prompt per browser session. The credential shall be checked with `sudo` before it is accepted, held in the server process's memory, dropped after an idle period, on logout and when the server process stops, and never stored in a configuration or session file; while a privileged action runs, it is handed to `sudo` through an owner-only temporary file that is deleted when the action ends.

11. Every action defined above that runs for longer than an immediate response shall stream its output to the user progressively as it is produced, rather than presenting a result only after the action completes, and shall allow the user to stop following that output before the action itself finishes.

## Rationale

A single interface surfacing all the mentioned actions, with a low-friction credential prompt for the ones that need elevated privileges, lowers the skill and access barrier for routine operational tasks without changing what those tasks actually do underneath: each action runs the same scripts and `wazuh_api` calls as the command line.

## Dependencies

- **SRS-069**: Scenario-scoped agent group configuration delivery. Backs the scenario deploy/undeploy and group assign/unenroll actions this interface exposes.
- **SRS-067**: Secure agent enrollment and automated onboarding. Backs the token-minting and enrollment window actions and produces the installer command this interface presents.
- **SRS-060**: RADAR deployment health check. Backs the health check action this interface exposes.
- **SRS-063**: REST API through which every action is invoked.

## Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

1. A scenario can be deployed, and separately undeployed, entirely from the interface, with streamed output visible for each, and its deployment state is shown accordingly.
2. An agent can be onboarded by minting a token in the interface and running the resulting, separately presented command on the target endpoint, with no manual construction of that command by the operator.
3. An agent can be deregistered from the interface, and no longer appears as a registered agent afterward.
4. An agent's group membership can be assigned and separately unenrolled from the interface, with the change visible in the agent's group membership afterward.
5. The enrollment window can be opened, closed, and its status checked from the interface independently of minting a token.
6. The anomaly detector for a scenario can be created and started from the interface, including the training-dataset-ingestion option.
7. A health check can be run from the interface scoped to one scenario, to all scenarios, and to named agents, with the result streamed to the user.
8. The stack can be torn down from the interface with data preserved by default, and permanently deleted only when the explicit data-deletion option is selected.
9. A privileged action prompts for a credential once per session; a wrong password is rejected; a second privileged action in the same session does not prompt again; restarting the interface's server process requires the credential to be entered again.
10. A long-running action's output is visible to the user progressively while the action is still in progress, and the user can stop following it before the action completes.

## Planned extensions

> **Status: planned.** Not implemented as of v2.2.0. The extensions below specify intended behaviour; no code implements them yet.

- Deregistering an agent from the interface with an option to keep its name and address reserved instead of freeing them immediately for reuse. The command line already offers this (`radar_deploy/manager-deregister-agent.sh --no-purge`); the interface always frees them.
