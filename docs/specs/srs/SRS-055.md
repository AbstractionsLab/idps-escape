# RADAR scenario: Geo-IP AC via whitelisting

As a security engineer,
I want RADAR to enforce access control by detecting access from non-whitelisted countries and applying the RADAR active response, so that connections from not approved geographies are detected and can be blocked.

## Scope

**Authentication events**: any successful authentication classified by Wazuh under the group `authentication_success`. The GeoIP fields are produced for SSH authentication lines (`sshd` success and failure) read from `/var/log/auth.log` through the `radar_shared` agent group.

**Web access logs**: Apache access logs (`/var/log/apache2/access.log`, `other_vhosts_access.log`) classified under `accesslog`. Detection depends on the stock Wazuh web ruleset first producing a base alert for the request (level > 0); a plain 2xx/3xx request stays at level 0, never reaches the enrichment integration, and is not checked, whatever its source country.

**GeoIP data source**: the manager-side RADAR enrichment integration (SRS-068), using the MaxMind GeoLite2 City and ASN databases. Country values are ISO 3166-1 alpha-2 codes (for example `LU`).

**Private addresses**: private and other non-routable source addresses are never matched against the whitelist: the web enrichment skips them, and the GeoLite2 lookup of an authentication line returns no country for them, so `radar_country` stays empty and the list-based rules cannot fire.

## Requirements

1. **Whitelist**. RADAR shall keep the approved countries in the Wazuh CDB list `whitelist_countries` (one `CODE:` entry per line; the shipped list holds `LU`, `DE`, `FR`, `BE`), deployed to the manager as `etc/lists/whitelist_countries` and declared in `ossec.conf`. Changing the list shall need no code change, only a redeployment of the scenario.

2. **Enrichment**. The manager shall enrich matching alerts with GeoIP fields and re-ingest them:

   - `custom-radar-enrich` (authentication path) appends a `RADAR ...` tail with `radar_outcome`, `radar_asn`, `radar_asn_placeholder_flag`, `radar_country`, `radar_region`, `radar_city`, `radar_geo_velocity_kmh`, `radar_country_change_i` and `radar_asn_novelty_i` to `/var/ossec/logs/radar/enriched_auth.log`, decoded by the `*-with-radar` decoders of `radar/scenarios/decoders/geoip_detection/0310-ssh.xml`.
   - `custom-radar-web-enrich` (web path) appends `country`, `region`, `city`, `lat` and `lon` to `/var/ossec/logs/radar/enriched_web_access.log`, decoded by the `web-accesslog-*-radar` decoders of `radar/scenarios/decoders/geoip_detection/0375-web-accesslog.xml` into `radar_country`, `radar_region` and `radar_city`. Region and city are often empty and shall not prevent decoding.
   - Both are standard Wazuh `<integration>` hooks run by the manager's integrator once per matching alert; there is no separate enrichment service. The stock decoders they replace (`0310-ssh_decoders.xml`, `0375-web-accesslog_decoders.xml`) are excluded in `ossec.conf`.

3. **Detection rules** (`radar/scenarios/rules/geoip_detection/a2-geoip-detection.xml`, all level 10 unless stated):

   - **100900**: an `authentication_success` event whose non-empty `radar_country` is not in the whitelist.
   - **100901**: an `authentication_success` event whose `srcgeoip` is not Luxembourg, France, Germany or Belgium. A fallback only: `srcgeoip` is populated only by a Wazuh build with legacy GeoIP support (`USE_GEOIP`) and its database; its country list is written in the rule, not read from the whitelist.
   - **100902**: an `accesslog` event whose non-empty `radar_country` is not in the whitelist.
   - **100903** (level 12): 300 matches of 100902 within 300 seconds.

4. **Response** (SRS-061):

   - Rules 100900, 100901 and 100903 shall be bound to the RADAR active response (`radar/scenarios/ossec/radar-geoip-detection-ossec-snippet.xml`). Rule 100902 only feeds 100903.
   - Scoring with the shipped `ar.yaml` block `geoip_detection`: `w_sig` 1.0, `w_cti` 0 (there is no DECIPHER analysis endpoint for this scenario, so $T = 0$), `signature_impact` 0.6, `signature_likelihood` 0.9 for 100900, 100901, 100903 and 0.1 for 100902. The bound rules therefore score 0.54, Tier 2 with the default boundaries 0.0 / 0.33 / 0.66.
   - Tier 2 and Tier 3 run `firewall-drop` against the alert's own source IP when `allow_mitigation` is true (the shipped value), never against an address in `global.never_block`, loopback, link-local or the manager's own addresses.
   - Tier 1 and above send the email and, if DECIPHER is reachable, create a Flowintel case.

5. **Audit**. Every decision shall be recorded per SRS-061.

See: docs/manual/radar_docs/radar-scenarios/geoip_detection_explained.md

## Planned extensions

> **Status: planned.** Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

- Periodic update of the GeoLite2 databases. Today they are downloaded once, at scenario deployment, when missing and `MAXMIND_LICENSE_KEY` is set.
- A DECIPHER analysis endpoint for this scenario, so that the CTI term contributes.

## Rationale

Country-based access control reduces exposure to high-risk regions and supports GDPR and export-control compliance. Deterministic rules give immediate detection without a training period and complement the behavioural detection of credential compromise (SRS-051).

## Dependencies

- **SRS-068**: manager-side enrichment (provides `radar_country`).
- **SRS-061**: tiered active response.
- Wazuh CDB lists (`<list>` in rules and `ossec.conf`).

## Related requirements

- **SRS-051**: suspicious login (shares the authentication enrichment and the `radar_shared` agent group).

## Acceptance criteria

Successful validation according to the corresponding test case specifications, which shall verify:

1. SSH login from a whitelisted country: no rule fires.
2. SSH login from a non-whitelisted country: 100900 fires at level 10.
3. SSH login from a private address: no rule fires.
4. Web request from a non-whitelisted country, in each supported access-log format (IP; domain and IP; host:port and IP; IP and IP): `radar_country` is decoded and 100902 fires at level 10.
5. Web request from a whitelisted country or a private address: 100902 does not fire.
6. After a country is added to the list and the scenario redeployed, a login from it no longer fires 100900.
7. A 100900 alert scores 0.54 (Tier 2); with `allow_mitigation` true the source IP is blocked on the agent, and with it false the planned `firewall-drop` is logged as withheld.
