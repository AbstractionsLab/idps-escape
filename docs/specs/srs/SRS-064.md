# RADAR SOAR web interface: frontend

As a security engineer,
I want a browser-based interface for RADAR that lets me configure active-response behaviour for bound scenarios, manage the external services and infrastructure components RADAR connects to, and drive deployment and agent lifecycle actions, so that I can operate RADAR without editing files or typing commands on the RADAR host.

## Scope

**Interface coverage**: This requirement applies to a web interface (`radar/gui/templates/`, `radar/gui/static/`) with four pages: a RADAR Scenarios page for configuring active-response behaviour, a Connectors page for external service configuration, an Infrastructure page for registering the core components, and a Deployment page for scenario and agent lifecycle actions. The Deployment page's behaviour is specified separately in SRS-070.

**Deployment model**: The interface is served by the GUI's own Flask process (`./radar.sh gui`) as server-rendered pages with accompanying stylesheets and scripts; no separate build step is required to serve or modify a page. The process listens on the loopback interface by default and is opened through a login URL that carries a session token (SRS-063).

**User persona**: Primary users are security engineers and SOC operators who understand RADAR concepts (scenarios, risk tiers, active-response weights).

**Integration boundary**: The frontend integrates exclusively through the REST API defined in SRS-063. It shall not communicate directly with Wazuh, OpenSearch, or any RADAR subsystem.

## Requirements

### Shared navigation

1. Every page shall render an identical navigation bar with four entries, RADAR Scenarios, Connectors, Infrastructure and Deployment, plus a Log out control. The entry for the currently viewed page shall be visually distinguished from the others.

2. The application's default landing page shall be the RADAR Scenarios page.

### RADAR Scenarios page

3. The interface shall present the baseline `default` scenario and the currently bound scenarios as a list the user can select from, each marked with its deployment state and detection type, and shall show, for the selected scenario, its name, description, and its active-response configuration, editable in place:

    - Its three risk weights, together with a live-updating total so the user can see whether they sum to 1.0 before saving; saving shall be blocked if they do not.
    - Scoring inputs appropriate to the scenario's detection type: signature-based scoring inputs when the scenario is signature-driven, an indication that scoring inputs are supplied at runtime by the anomaly detector when it is anomaly-driven, and both when it is a hybrid of the two.
    - The look-back windows used when correlating an alert against anomaly-detection and signature-based context.
    - The four response tiers T0 to T3, with their three boundaries (`tier1_min`, `tier1_max`, `tier2_max`) editable; the interface shall block saving unless the boundaries are in non-decreasing order within [0, 1].
    - Per-tier mitigation actions for the tiers where mitigations apply, added and removed from the list of known actions, which is `firewall-drop` plus the active-response catalog `radar/radar-agent/ar-scripts.yaml`.
    - A single control for allowing automatic mitigation execution, separate from configuring which mitigations would run.
    - The scenario's associated rule IDs, shown for reference only.

4. Saving a scenario's active-response configuration shall update it in place without a full page reload, and shall show the user whether the save succeeded or failed.

5. The baseline `default` scenario shall always be listed, so the page always has a configuration to show even when no other scenario is bound.

### Connectors page

6. The interface shall present one configuration card per external connector RADAR uses: the search/analytics backend (OpenSearch), the Wazuh management API, the analytics dashboard, outbound email (SMTP), the incident-case system (DECIPHER), the GeoIP database provider (MaxMind), and the inbound alert webhook. Each card shall show that connector's fields, with any secret-bearing field masked by default and revealable on demand only for fields the API allows revealing.

7. Each card shall provide a way to save its fields independently of the others, and a way to test that connector's current configuration and show whether the test succeeded.

8. The interface shall provide a single action that tests every configured connector at once, in addition to the per-card test action.

### Infrastructure page

9. The interface shall let the user register the dashboard and one or more manager and indexer nodes (container name, host, port, scheme), mark a primary node, fill the host field with the GUI host's detected address, and test reachability between two registered components.

### Deployment page

10. The interface shall provide a Deployment page covering the scenario and agent lifecycle actions specified in SRS-070, organized into distinct tabs for scenario management, anomaly-detector setup, agent management, group management, status/health checking, and teardown. The behaviour of each tab is defined in SRS-070; this requirement only establishes that the page exists and is reachable from the shared navigation.

### Credential prompt

11. When an action needs the host sudo password and none is held for the session, the interface shall prompt for it, submit it, and retry the action once.

### Visual and UX requirements

12. The interface shall follow a consistent colour convention for state badges and risk tiers across all pages.

## Rationale

RADAR's active-response behaviour, connector configuration and infrastructure registration are otherwise only reachable by editing files on the RADAR host. A focused interface — one page for tuning how a scenario responds, one for the services RADAR talks to, one for the components it deploys to, and one for the deployment actions covered by SRS-070 — lowers the skill and access barrier for routine operational tasks without requiring the operator to understand the underlying file formats.

## Dependencies

- **SRS-063**: RADAR SOAR web interface: REST API. All data displayed and all mutations performed by the frontend are mediated through the API contract defined there.
- **SRS-070**: GUI deployment interface. Defines the behaviour of the Deployment page referenced in requirement 10.
- **SRS-051, SRS-055, SRS-056, SRS-066, SRS-071**: scenarios that contribute rule IDs and active-response configuration shown on the RADAR Scenarios page.

## Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

1. **Navigation**: all four pages are reachable from the shared navigation, the active page is visually indicated, and the default landing page is the RADAR Scenarios page.
2. **Scenario selection and display**: selecting a scenario shows its active-response configuration, correctly reflecting its detection type in which scoring inputs are shown, and switching between scenarios updates the displayed configuration accordingly.
3. **Only the baseline bound**: when no scenario other than `default` is bound, the page shows the `default` scenario's configuration.
4. **Weight validation**: the interface blocks saving when the three risk weights do not sum to 1.0, and the running total updates as the user edits them.
5. **Tier validation**: the interface blocks saving when the tier boundaries are not in non-decreasing order within [0, 1].
6. **Mitigation configuration**: a mitigation action from the catalog can be added to and removed from a tier's list, and automatic mitigation execution can be toggled independently of which mitigations are configured.
7. **Save behaviour**: saving a scenario's configuration updates it without a full page reload and clearly indicates success or failure.
8. **Connector configuration**: each connector's fields can be saved independently, secret fields are masked by default and revealable only where permitted, and a per-connector test and the test-all action both report success or failure accurately.
9. **Infrastructure registration**: a manager node can be added, edited, made primary and removed, and a reachability test between two registered components reports its result.
10. **Deployment page presence**: the Deployment page is reachable and organized into the tabs defined in SRS-070.
