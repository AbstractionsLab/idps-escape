# RADAR default baseline rules

As a security engineer,
I want a small baseline of detection rules and response bindings to be active on the RADAR manager whatever scenario is deployed, so that suspicious Windows command interpreter use, known package vulnerabilities and repeated authentication failures reach the RADAR risk policy without deploying a dedicated scenario.

## Scope

- **Rules**: the RADAR rules 100400–100405 in `radar/scenarios/rules/default/radar_rules.xml` (group `radar_default`), and the stock Wazuh rules and groups the `default` block of `radar/scenarios/active_responses/ar.yaml` binds to the RADAR active response.
- **Events**: Windows Sysmon process-creation events (stock group `sysmon_event1`), Wazuh vulnerability detection alerts, and stock rules of the group `authentication_failures` (for example the `sshd` repeated-failure rules 5712, 5720 and 5763).
- **Response**: scoring and tiering by `radar/scenarios/active_responses/radar_ar.py` under the scenario name `default` (SRS-061).
- **Out of scope**: collection of Sysmon events on Windows endpoints. RADAR ships no agent configuration for the `default` agent group; a Windows endpoint must forward its Sysmon channel by other means for rules 100400–100405 to fire. `default` is not a scenario that can be deployed on its own.

## Requirements

1. **PowerShell invocation** (`radar_rules.xml`). RADAR shall raise:
   - **100400** (level 8, ATT&CK T1059.001) for a Sysmon process-creation event whose command line invokes `powershell.exe`;
   - **100401** (level 10, T1059.001) as a child of 100400 when the command line does not match the list of legitimate activities (`LEGIT_ACTIVITIES` variable in the same file);
   - **100402** (level 10, T1059.001) as a child of 100400 when the parent command line does not match that list.

2. **Windows command shell invocation**. RADAR shall raise:
   - **100403** (level 8) for a Sysmon process-creation event whose command line invokes `cmd.exe` or a script or shortcut file (`.bat`, `.cmd`, `.lnk`, `.pif`, `.vbs`, `.vbe`, `.js`, `.wsh`);
   - **100404** and **100405** (level 10) as children of 100403 or of the stock rule 92058 (Application Compatibility Database launched) when, respectively, the command line or the parent command line does not match the list of legitimate activities.

   The rules shall not copy the full log into the alert (`no_full_log`). Changing the list of legitimate activities shall need no change other than to the variable.

3. **Stock rules relied on**. The `default` block shall bind, in addition to 100401, 100402, 100404 and 100405:
   - the stock vulnerability detection rules **23503** (low severity), **23504** (medium or untriaged) and **23505** (high severity). The critical-severity rule 23506 is not bound;
   - every stock rule of the group **`authentication_failures`**, by group.

   The base rules 100400 and 100403 shall not be bound.

4. **Deployment with every scenario**. Deploying any scenario (`build-radar.sh <scenario>` or the GUI, both through `deploy_manager_config` in `radar/wazuh_api/scenario_ops.py`) shall also:
   - upload every file of `radar/scenarios/rules/default/` to the manager's rule directory, only when its content differs;
   - insert `radar/scenarios/ossec/radar-default-ossec-snippet.xml` into the manager's `ossec.conf` as a marked `default` block. The snippet declares the command `radar_ar_default` (`radar_ar.py`) and two active responses run on the manager (`location` `server`): one for the rule IDs of requirement 3, one for the group `authentication_failures`.

   Undoing a scenario shall leave the default rule file and the `default` block in place. Every agent assigned to a scenario shall also be in the Wazuh agent group `default`.

5. **Scenario resolution**. `radar_ar.py` shall identify an alert as the `default` scenario when its rule ID is listed in the block's `signature.rule_ids`, or, when no scenario of `ar.yaml` lists its rule ID, when one of its groups is in `signature.rule_groups`. Because `default` is listed first in `ar.yaml`, it shall win any group match shared with a later scenario. The detection type is always `signature`.

6. **Scoring and tiers** (shipped `default` block, SRS-061):
   - $R = w_{sig} \cdot S + w_{cti} \cdot T$ with $w_{sig}$ 0.7, $w_{cti}$ 0.3, $w_{ad}$ 0, `signature_impact` 0.5 and `signature_likelihood` 0.6 for 100401, 100402, 100404, 100405; 0.001 for 23503; 0.005 for 23504; 0.01 for 23505; 0.3 for the group `authentication_failures`.
   - There is no DECIPHER analysis endpoint for `default`, so $T = 0$.
   - Tier boundaries 0.15 / 0.33 / 0.66. The resulting scores are 0.21 (Tier 1) for 100401, 100402, 100404 and 100405; 0.105 for `authentication_failures` and at most 0.0035 for the vulnerability rules, all Tier 0 (logged only).
   - No mitigation is configured and `allow_mitigation` is false, so no tier runs a mitigation; each decision is logged with the withheld reason.

7. **Context**. The context of a `default` decision shall be the alert agent's events in the `delta_signature_minutes` (5) before the alert.

8. **Audit**. Every decision shall be recorded in `/var/ossec/logs/active-responses.log` per SRS-061.

See: docs/manual/radar_docs/radar-rules.md, docs/manual/radar_docs/radar-tuning.md

### Rationale

A baseline that ships with every scenario gives each RADAR deployment a minimum of coverage, and exercises the email, case and audit path of the active response, without a scenario of its own. Windows command interpreters are the most common execution technique (ATT&CK T1059); only invocations outside known legitimate tools are bound to the response. Vulnerability and authentication-failure alerts are frequent, so their likelihoods keep them at Tier 0 by default: they are scored and logged, and an operator raises their weight in `ar.yaml` to be notified.

### Acceptance criteria

Successful validation according to the corresponding test case specifications, TST-053 and TST-054, which shall verify:

1. After building RADAR with any scenario, the manager has rules 100400–100405, the `default` block of `ar.yaml` lists the rule IDs and group of requirement 3, and `ossec.conf` binds them to `radar_ar_default` on the server.
2. A vulnerability alert (23503, 23504 or 23505) and an `authentication_failures` alert are identified as scenario `default`, detection `signature`, with the risk scores of requirement 6 and Tier 0: no email and no case.
3. An alert of 100401–100405 scores 0.21, Tier 1: an email is sent and, when DECIPHER is reachable, a low-priority case is created; no mitigation runs.
