# RADAR scenario: log size change

As a security engineer,
I want RADAR to detect unusual log volume growth on each endpoint, judged against that endpoint's own normal behaviour, and then apply the RADAR risk policy to decide how to react.

## Scope

**Measured quantity**: the total size in bytes of `/var/log` on each monitored Linux endpoint. Individual log files are not analysed separately.

**Endpoints**: Linux agents enrolled in the `log_volume` agent group.

**Detection method**: an OpenSearch Anomaly Detection (RCF) detector with the categorical field `agent.name`, so each endpoint is scored against its own history.

**Alert delivery**: anomaly result → OpenSearch alerting monitor → RADAR webhook → `/var/log/ad_alerts.log` → Wazuh rule → `radar_ar.py`.

## Requirements

1. **Collection**. Each endpoint in the group shall measure the size of `/var/log` every 30 seconds with a local collector installed by `bootstrap-agent.sh` as a systemd timer (`radar/radar-agent/collectors/log_volume/`), and append one line `<timestamp> <hostname> log_volume_metric: /var/log <bytes>` to `/var/log/radar/log_volume_metric.log` (rotated daily, 7 files kept). The group's agent configuration reads this file.

2. **Decoding and indexing**. The manager shall decode the line (`log_volume_metric` decoder: `data.log_path`, `data.log_bytes`) and the Filebeat archives pipeline shall route these events to the daily index `wazuh-ad-log-volume-YYYY.MM.DD`, whose index template `radar-log-volume` maps `@timestamp` as date, `agent.name` as keyword and `data.log_bytes` as long. Optionally, `run-radar.sh log_volume --ingest true` seeds a synthetic history so the detector has a baseline at once.

3. **Detection** (`config.yaml`, `scenarios.log_volume`; created by `radar/anomaly_detector/detector.py`):

   - Detector `LOG_VOLUME_DETECTOR` on `wazuh-ad-log-volume-*`, result index `opensearch-ad-plugin-result-log-volume`.
   - Feature `log_volume_max` = max of `data.log_bytes` per interval; categorical field `agent.name`.
   - Interval 1 minute, window delay 1 minute, shingle size 8.
   - Detector rules that ignore deviations too small to matter (ratio conditions on `log_volume_max`).

4. **Notification** (`radar/anomaly_detector/monitor.py`, `radar/webhook/ad_alerts_webhook.py`):

   - Monitor `LogVolume-Monitor`, run every detector interval, reports up to `monitor_max_entities` (default 5) entities whose anomaly grade and confidence reach the configured thresholds (shipped 0.01 / 0.01), with trigger `LogVolume-Growth-Detected`.
   - The webhook (`POST /notify`, shared-secret header) writes one line per entity to `/var/log/ad_alerts.log` with the entity (agent name), the monitor period, the anomaly's data window, grade and confidence.

5. **Wazuh rules** (`radar/scenarios/rules/log_volume/a1-log-volume.xml`): the catch-all **100300** (level 5) matches any decoded AD alert read from `/var/log/ad_alerts.log` and tags it `radar_ad_received`; **100309** (level 12) matches the trigger name within that group. 100309 is the only rule bound to the active response.

6. **Response** (SRS-061, `ar.yaml` block `log_volume`):

   - The alert is scored as an anomaly: $A$ = grade × confidence, $R = 0.9 \cdot A + 0.1 \cdot T$. There is no DECIPHER analysis endpoint for this scenario, so $T = 0$ and $R \le 0.9$.
   - Tier boundaries 0.0 / 0.33 / 0.66 (defaults); Tier 1 and above send the email and, if DECIPHER is reachable, create a Flowintel case; Tier 3 runs `terminate_service.sh` when `allow_mitigation` is true.
   - `terminate_service.sh` stops only a service found in the context and listed both in the scenario's `terminable_services` (empty by default) and on the agent; core services are never stopped.
   - The context is the anomalous agent's (`entity_keyword`) events in the monitor period, capped at `delta_ad_minutes`.
   - Only AD alerts read by the webhook agent from its own log are acted on.

7. **Audit**. Every decision shall be recorded per SRS-061.

See: docs/manual/radar_docs/radar-scenarios/log_volume_explained.md

## Rationale

Log volume spikes can signal log flooding, verbose malware error loops, or log injection to hide activity. Per-endpoint baselines accommodate the wide variance in normal log rates across heterogeneous hosts, and identify anomalous volume regardless of log content.

## Dependencies

- OpenSearch with the Anomaly Detection and Alerting plugins.
- The RADAR webhook service and its Wazuh agent.
- **SRS-061**: tiered active response.

## Related requirements

- **SRS-071**: Linux resource utilization (the same anomaly pipeline and context handling).

## Acceptance criteria

Successful validation according to the corresponding test case specifications, which shall verify:

1. **Baseline**: with stable log volume for a training period, the detector does not flag normal behaviour.
2. **Moderate spike**: growing the monitored directory to a moderate multiple of its baseline is flagged within a few detection intervals.
3. **Severe spike**: growing it to a much larger multiple is flagged with high grade.
4. **Webhook delivery**: the monitor posts the anomaly and the webhook writes a line with grade, confidence, entity and time window.
5. **Wazuh ingestion**: the line is matched by the catch-all AD rule and by 100309.
6. **Risk score**: for a known grade and confidence, the risk score and tier match the formula and shipped weights.
7. **Response**: a Tier 3 decision sends the email, and `terminate_service.sh` runs only for a service in both allowlists; otherwise the withheld or refused mitigation is logged.
8. **Audit**: the decision in `/var/ossec/logs/active-responses.log` carries the decision ID, scenario, detection type, risk components, tier, planned actions and outcomes.
