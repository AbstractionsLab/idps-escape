# RADAR anomaly alert relay contract

As a security engineer,
I want anomaly alerts from OpenSearch to reach the RADAR active response only through one authenticated, validated relay, with one Wazuh event per anomalous entity, so that a forged or malformed anomaly alert cannot trigger a response and every reported entity is scored on its own.

## Scope

- **Producers**: the OpenSearch Alerting monitors of the anomaly-based scenarios: `log_volume` and `linux_resource_utilization` (`radar/anomaly_detector/monitor.py`), and the off-hours rule-mode and model-mode monitors of `suspicious_login` (`radar/anomaly_detector/off_hours.py`). The notification channel they post to is created by `radar/anomaly_detector/webhook.py`.
- **Relay**: the RADAR webhook service `radar/webhook/ad_alerts_webhook.py`, its container and Wazuh agent (`radar/webhook/`, `radar/docker-compose.webhook.yml`).
- **Consumer**: the shared decoder `0001-ad-common.xml` (shipped under `radar/scenarios/decoders/log_volume/`, `linux_resource_utilization/` and `suspicious_login/`), the AD catch-all and trigger rules, and `radar/scenarios/active_responses/radar_ar.py`.
- **Out of scope**: TLS on the webhook port (plain HTTP; a reverse proxy is needed for TLS) and rate limiting, neither of which is implemented.

## Requirements

1. **Authentication.** The webhook shall accept notifications only as `POST /notify` carrying the header `X-RADAR-Webhook-Token` equal to the shared secret `WEBHOOK_SHARED_SECRET`, compared in constant time. A missing or wrong token shall be refused (401). Without a configured secret every request shall be refused, and the webhook container shall not start without one. The notification channel shall send the header with the secret.

2. **Size and form.** A body larger than 16 KiB shall be refused (413). A body that is not a JSON object shall be refused (400). The body `{"ping": true}` shall be answered as a connectivity check and write nothing.

3. **Validation.** Every value written shall first be validated; an invalid required value rejects the entry:
   - trigger name and entity: 1 to 128 characters from `[A-Za-z0-9._:-]`;
   - monitor period start and end: ISO 8601 timestamps;
   - anomaly grade and confidence: numbers in [0, 1].

   Optional values (the anomaly's data window; the off-hours event count and schedule group) shall be written only when usable: the data window only when both bounds are valid and ordered, rewritten in ISO 8601 UTC; the count and group only together. An unusable optional value shall be dropped without rejecting the entry. No other value from the body shall be written.

4. **Several entities per notification.** A monitor run shall report up to `monitor_max_entities` entities (default 5, bounded to 1–50; `model_mode.max_entities` for the off-hours model mode) whose grade and confidence reach the configured thresholds, highest grade first, as an `anomalies` list. The webhook shall:
   - read at most 50 entries, each inheriting the trigger name and monitor period of the notification;
   - skip invalid entries, and refuse the notification (400) only when no entry is usable;
   - write one line per entity, keeping the highest-graded entry of an entity reported twice;
   - for a notification without an `anomalies` list, write the single line of its top-level values.

5. **Line format.** Each line shall be appended, under a lock, to the anomaly alert log (`AD_ALERTS_LOG`, default `/var/log/ad_alerts.log`) in syslog form with the program name `ad_alert`, the marker `OpenSearchAD`, the trigger name, and the quoted fields `entity`, `start`, `end`, `anomaly_grade`, `anomaly_confidence`, then the optional `data_start`, `data_end` and `off_hours_count`, `schedule_group`. The response shall state the number of lines written.

6. **Decoder contract.** The decoder `opensearch_ad` (program name `ad_alert`, prematch `OpenSearchAD`) and its children shall extract `detector_name`, `entity_keyword`, `period_start`, `period_end`, `anomaly_grade`, `anomaly_confidence`, and, when present, `data_start`, `data_end`, `off_hours_count`, `schedule_group`. A line without the optional fields shall still decode. All copies of `0001-ad-common.xml` shall be identical, and the line format and decoder shall change together.

7. **Delivery and rules.** The Wazuh agent in the webhook container, enrolled as `WEBHOOK_AGENT_NAME` (default `ad-webhook`), shall read the anomaly alert log as syslog (`radar/webhook/ad-ossec.conf`) and forward it to the manager. Each AD scenario shall ship a catch-all rule on the `opensearch_ad` decoder that sets the group `radar_ad_received` (100300, 210039, 100320), and trigger rules that match the trigger name under that group with `if_group`, never `if_sid` (100309, 210040, 210041, 100321), so that a trigger rule fires whichever catch-all matched first.

8. **Origin check in the active response.** `radar_ar.py` shall act on an alert identified as an anomaly alert (rule ID in a scenario's `ad.rule_ids`) only when it comes from the webhook agent (`agent.name` equal to `WEBHOOK_AGENT_NAME`, default `ad-webhook`) and from the anomaly alert log (`location` equal to `AD_ALERTS_LOCATION`, default `/var/log/ad_alerts.log`, possibly prefixed by the agent's address). Any other such alert shall be logged as rejected and dropped without context collection, scoring, notification or mitigation (`AdAlertOrigin` in `radar_ar.py`). Fusion shall count only alerts that pass the same check as anomaly evidence (SRS-061 requirement 7).

See: docs/manual/radar_docs/radar-run-ad.md

### Rationale

The webhook turns HTTP notifications into log lines that the active response trusts as detector output. Anyone who can write such a line could make RADAR notify, open cases or, with mitigation enabled, act. The shared secret protects the HTTP side; the origin check protects the Wazuh side, where a forged `ad_alert` line could otherwise arrive from any agent or file. Strict validation of each written value prevents log injection through entity or trigger names. A monitor run can find several anomalous entities at once; one line per entity lets each be decoded, scored and attributed separately instead of only the top hit.

### Acceptance criteria

Successful validation according to the corresponding test case specification, TST-074, which shall verify:

1. The monitor query returns at most `monitor_max_entities` hits above both thresholds, and its message renders to valid JSON with one `anomalies` entry per hit.
2. The webhook writes one line per entity, keeps the highest-graded hit per entity, writes the data window only when both bounds are usable, skips invalid entries, rejects a body whose entries are all invalid, and rejects injection attempts in every field.
3. All copies of `0001-ad-common.xml` are identical, and their regexes match the line the webhook writes.
4. Every AD trigger rule attaches to every AD catch-all through `if_group radar_ad_received`.
5. An anomaly alert from another agent or another file is rejected by `radar_ar.py` without scoring or action.
