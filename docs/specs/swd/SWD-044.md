# SONAR paths, model naming and model directory format

Training saves a model and detection loads it ([LARC-019](../larc/LARC-019.md), [LARC-020](../larc/LARC-020.md)). Both must find the same files whatever directory SONAR is started from, and loading a model must not run code from it ([SRS-079](../srs/SRS-079.md)). This item specifies where SONAR keeps its files, how a model is named, and the on-disk format of a model.

**Implementation**: `sonar/paths.py` (SONAR home, resolution, slugs), `sonar/config.py` (`PipelineConfig.model_path`), `sonar/cli.py` (`_resolve_file_paths`, `apply_scenario_to_config`, `apply_agent`, `_get_scenario_id`, `_state_dir`), `sonar/engine.py` (model directory), `sonar/backends/*.py` (backend state files).

## Locations

**SONAR home.** `$SONAR_HOME` if set; otherwise, when `pyproject.toml` sits next to the package (a source checkout, including the Docker image), the package directory `sonar/`; otherwise `~/.sonar` (an installed wheel).

| Location | Default | Set by |
|---|---|---|
| Configuration | `sonar/default_config.yaml` in the package | `--config` |
| Models | `<home>/models` | `models_dir` |
| Delivery watermarks | `state/` next to the model, i.e. `<models_dir>/state` | `output.state_dir` |
| Debug data | the packaged `sonar/test_data/synthetic_alerts/` | `debug.data_dir` |
| `jsonl` sink file | `<home>/anomalies.jsonl` | `output.jsonl_path` |
| Saved payloads (`--dry-run`, `--print-payloads`) | `<home>/payloads` | `--payload-dir`, `detection.payload_dir` |
| Example scenarios | packaged in `sonar/scenarios/` | a scenario path that does not exist is looked up there by name |

**Relative paths.** A relative path in a configuration or scenario file is resolved against the directory of **that file**, never against the working directory: `models_dir`, the deprecated `model_path`, `debug.data_dir`, `output.state_dir`, `output.jsonl_path`, `output.wazuh.file_path` and, in a scenario, `detection.payload_dir`. A new path key must be added to that resolution. Paths given on the command line keep their usual meaning, relative to the shell's directory; `--payload-dir` wins over the scenario's `detection.payload_dir`. No module of the package uses a `./` path literal or the working directory (`tests/sonartests/test_paths.py` scans for both).

## Model naming

A model is the directory `<models_dir>/<model_name>/`. The name is decided in this order, each step overriding the previous:

1. `model_name` of the configuration file (default `sonar`);
2. a scenario's `model_name`, or else the slug of its `name`, so that training and detection of a scenario use the same model without configuration;
3. `--model-name` of `sonar train`;
4. `--agent <name>`, which appends `-<slug(agent)>` (one model per host), in every command.

A slug is the lower-cased text with every run of characters outside `[a-z0-9_-]` replaced by `_`, and leading and trailing `_` and `-` removed (`sonar` if nothing remains). Names carry no timestamp, so training a scenario again replaces its model; a new `model_name` keeps the old one. The name `state` is reserved for the watermark directory unless `output.state_dir` is set. Setting `model_path` (deprecated) splits it into `models_dir` and `model_name`, dropping a `.pkl` suffix.

**Scenario ID.** `shipping.scenario_id` if set (with the agent suffix under `--agent`), otherwise the slugged model name. It names the data stream (`sonar_anomalies_mvad_<scenario_id>`), the watermark file (`<state_dir>/<scenario_id>.json`) and the namespace of every `anomaly_id` ([SWD-046](SWD-046.md)), so renaming a model without an explicit scenario ID starts a new stream and new watermarks.

## Model directory

| File | Content | Written by |
|---|---|---|
| `metadata.json` | Format, versions, backend, feature contract, training record | `ModelEngine.save` |
| `mvad_config.json` | The MVAD library's configuration, threshold, training score range, variables (JSON) | `mvad` backend |
| `mvad_weights.pt` | The network's weights as a plain tensor dictionary | `mvad` backend |
| `pca_state.json` | Window, settings, columns, scales, mean, components, eigenvalues, noise variance, score scale | `pca` backend |
| `ewma_state.json` | Settings, columns, per-feature median and scale | `ewma` backend |

`metadata.json` (example of an MVAD model, lists shortened):

```json
{
  "format_version": 1,
  "sonar_version": "<SONAR version>",
  "backend": "mvad",
  "feature_schema_version": 2,
  "feature_config": {"numeric_fields": ["data.cpu_usage_%"], "bucket_minutes": 1, "alert_filter": null, "...": "..."},
  "vocabulary": {"categories": {"agent.name": ["web-server-01", "..."]}},
  "columns": ["alert_count", "data.cpu_usage_%", "...", "agent.name__other"],
  "training_samples": 1440,
  "mvad_library": "time-series-anomaly-detector",
  "mvad_library_version": "0.4.0",
  "mvad_params": {"sliding_window": 120, "device": "cpu", "interval": 1},
  "training_plan": {"samples": 1440, "input_size": 60, "threshold_window": 60, "batches_per_epoch": 8, "...": "..."},
  "gradient_steps": 800,
  "library_threshold": 0.0178,
  "train_score_min": 0.0022,
  "train_score_max": 0.1396
}
```

The first eight keys are common to every backend; the rest is the backend's `metadata` ([SWD-043](SWD-043.md)): `pca` records its settings, components, dimensions, noise variance and training points, `ewma` its settings and training points. `feature_config`, `vocabulary` and `columns` are the feature contract ([SWD-023](SWD-023.md)): detection adopts the stored configuration, builds columns with the stored vocabulary, and refuses to predict on other columns.

## Saving

The model is written to a new staging directory `.<model_name>.<random>` next to the target, metadata first, then the backend's state. Only when both are complete is it swapped in: an existing model is renamed to `.<model_name>.previous`, the staging directory renamed to the target, and the previous one deleted. If writing fails, the staging directory is removed and the existing model stays in place. Both renames stay within one directory, so each is atomic on one file system.

## Loading

1. Without `metadata.json` in the model directory: if a file `<model_name>.pkl` exists (the former pickle format), loading fails with a request to retrain, **without opening the file**; otherwise the model is missing.
2. A `feature_schema_version` other than the one SONAR builds, or a `format_version` other than 1, fails with a request to retrain.
3. The backend named in `backend` rebuilds itself from its state files. MVAD's configuration is read from JSON and rebuilt with the library's own configuration and network classes (`MultiADConfig`, `NormalizeBase`, `MultivariateGraphAttnDetector` of library 0.4.0); its weights are loaded with `torch.load(weights_only=True)` on the CPU, which accepts tensors only. A library upgrade that changes those classes therefore breaks loading and requires retraining, by design.
4. An MVAD model that records fewer than one gradient step is loaded with a warning that it is untrained.

Detection maps these failures to exit status 1, with the reason in the log.

## Design rationale

- **No pickle.** Unpickling runs code chosen by whoever wrote the file; with JSON and tensor-only weights, a model file can mislead detection but cannot execute code. Model files remain inputs to trust: `models_dir` needs the same protection as the configuration.
- **File-relative paths and stable names.** SONAR used to resolve models and data against the working directory, so it worked only from the repository root, and timestamped model names made training and detection look for different files.
- **Staged swap.** Retraining overwrites the model in place; without staging, an interrupted save would leave a partial model that detection then loads.
