# RADAR deployment control plane

This document specifies the design of the RADAR deployment control plane: the
entry-point scripts, the manager-side shell backbone, and the Wazuh API
integration layer that together apply, verify, and reverse a scenario
deployment. It supersedes SWD-031, which specified an Ansible role architecture
no longer present in the codebase.

Scope excludes the risk engine (SWD-026), the active response script (SWD-027),
and the web interface (SWD-041), all of which are consumers of this layer.

## Design rationale

The control plane replaced an Ansible-based implementation. Three properties
drove the change:

- **No control-node dependency.** Deployment targets the manager's own REST API
  rather than SSH into hosts, so no inventory, no vault, and no controller-side
  credential store is required.
- **Single privileged host.** The manager containers run on the same host as
  the entry-point scripts, either brought up by `build-radar.sh` or pre-existing
  and registered in `infra.yaml` (one or more manager nodes). `sudo` is needed
  only to bring up the containers, for the bind-mounted directories under
  `/srv/wazuh/` and for the host firewall rule governing enrollment.
- **Endpoints are self-onboarding.** An endpoint is enrolled by running one
  script on it with a short-lived token, rather than by being pushed to from a
  central controller.

## Module structure

```
radar.sh                        Single entry point; dispatches to the scripts below and starts the GUI
├── build-radar.sh              Bring up the core stack and webhook, apply one scenario
├── run-radar.sh                Ingest, create detector, create monitor (radar-cli container)
├── health-radar.sh             Deployment verification (SWD-040)
├── stop-radar.sh               Stop the stack, optionally purging named volumes
└── radar_deploy/               Manager-side shell backbone
    ├── _lib.sh                     Shared helpers: env loading, dexec, hostpath, manager containers
    ├── manager-apply-scenario.sh   Filesystem-level scenario application on one manager node
    ├── manager-apply-scenario-all.sh  The above on every manager node registered in infra.yaml
    ├── manager-undo-scenario.sh    Reverse of the scenario configuration (API-side)
    ├── manager-harden-enrollment.sh  authd hardening and cluster key
    ├── manager-mint-token.sh       Short-lived enrollment token, revocation timer, window opening
    ├── manager-revoke-token.sh     Replace the enrollment password (on expiry or on demand)
    ├── manager-enrollment-window.sh  Port 1515 firewall window
    ├── manager-ensure-certs.sh     Certificate generation
    ├── manager-rotate-credentials.sh  Rotate the generated indexer/API passwords
    ├── manager-repair-permissions.sh  Restore ownership and modes on the bind mounts
    ├── manager-health.sh           Manager filesystem, container and reachability checks
    ├── manager-assign-agent-group.sh / manager-unassign-agent-group.sh
    └── manager-deregister-agent.sh

radar-agent/                    Copied whole to each endpoint
├── bootstrap-agent.sh          Install, enroll, join groups, install AR scripts and collectors
├── uninstall-agent.sh          Remove collectors, AR scripts and the agent package
├── ar-scripts.yaml             Catalog: active-response name -> versioned script
├── active_responses/           Versioned active-response scripts (lock_user_linux_v1.sh, ...)
├── collectors/<group>/         Metric collectors (systemd service and timer) per scenario group
├── helpers/                    ar-mapping.sh, ar-dispatch.sh, collectors.sh
└── packaging/wazuh.repo        Wazuh yum repository definition

wazuh_api/                      Wazuh REST API integration layer
├── client.py                   Authenticated session, retry, error mapping
├── cli.py                      Subcommand surface invoked by the shell scripts
├── config.py                   config.yaml and volumes.yml accessors
├── infra.py                    infra.yaml registry and runtime address resolution
├── credentials.py              Per-deployment password generation and rotation
├── envfile.py                  Safe .env parsing and atomic updates
├── ar_env.py                   Filtered environment for active_responses.env
├── filebeat_pipeline.py        Archives pipeline patching
├── ruleset.py                  Upload/delete decoder, rule, and CDB list files
├── manager_config.py           ossec.conf read/modify/write, marked-block edits
├── scenario_ops.py             Scenario deploy/undo orchestration
├── groups.py                   Agent group and agent lifecycle
├── fleet.py                    Fleet state tracking
└── health.py                   API-side health checks
```

The division of responsibility is deliberate. Operations expressible through the
Wazuh REST API are implemented in `wazuh_api/`; operations that require direct
filesystem or container access — placing integration scripts, GeoIP databases,
Filebeat configuration — are implemented in `radar_deploy/`. `build-radar.sh`
sequences the two (LARC-024); the GUI's Deploy action runs the same sequence
(SWD-041). Everything installed on endpoints lives in `radar-agent/`, which has
no dependency on the rest of the repository.

## Requirements

### Path resolution

1. The control plane shall resolve manager filesystem paths from `volumes.yml`
   rather than assuming a fixed layout, so that an existing Wazuh installation
   with different bind mounts can be targeted without code changes.

2. The following container paths shall be resolvable; deployment shall abort
   with a diagnostic naming the missing mount if any is absent:

   | Container path | Purpose |
   |---|---|
   | `/var/ossec/etc` | `ossec.conf`, decoders, rules, CDB lists |
   | `/var/ossec/logs` | Alert, audit, and enrichment output |
   | `/var/ossec/integrations` | Enrichment integration scripts |
   | `/var/ossec/active-response/bin` | `radar_ar.py` and mitigation scripts |
   | `/etc/filebeat` | Filebeat configuration |
   | `/usr/share/filebeat/module/wazuh/archives/ingest/pipeline.json` | Archive ingest pipeline |

### Scenario application

3. Applying a scenario shall be idempotent: re-running `build-radar.sh` for an
   already-deployed scenario shall converge to the same state without
   duplicating configuration blocks or restarting services unnecessarily.

4. `ossec.conf` shall be modified only through delimited blocks of the form
   `<!-- RADAR: <name> BEGIN -->` … `<!-- RADAR: <name> END -->`. A block whose
   marker already exists shall be replaced in place; a block whose marker is
   absent shall be inserted at a named anchor. Configuration outside RADAR
   markers shall never be modified, with the exception of the `<logall>`,
   `<logall_json>`, and indexer `<host>` values, which are set by tag.

5. Each scenario deployment shall apply, in order: manager-side filesystem
   artifacts (on every registered manager node, the primary first), agent group
   configuration, ruleset files, `ossec.conf` blocks. The API stage shall restart
   the manager at most once, and only if something changed; the filesystem stage
   shall restart the manager container only when it changed the Filebeat
   configuration or archives pipeline.

6. Ruleset deployment shall install the `default` ruleset alongside the
   scenario's own ruleset, since every scenario inherits the baseline rules.

7. Deployment shall verify before uploading that every CDB list referenced by a
   scenario's rules is present in the repository, and abort naming the missing
   list rather than installing a ruleset that cannot load.

### Reversal

8. Undeploying a scenario shall reverse only that scenario's own contributions:
   its `ossec.conf` block, its group's `agent.conf`, its agents' membership of
   that group, and any decoder, rule, or CDB list file it ships that no other
   currently-deployed scenario still requires.

9. Undeploy shall leave in place artifacts that are shared irrespective of any
   single scenario's state: the `default` and shared enrichment `ossec.conf`
   blocks, the enrichment and active-response scripts, and the agent groups
   themselves. The `radar_shared` group's configuration shall be cleared only
   when no other shared scenario still requires it.

10. Undeploy shall be idempotent and shall treat a scenario that was never
    deployed as already reversed, not as an error.

### Agent enrollment

11. Enrollment shall require a credential. The manager shall be configured with
    `use_password=yes`, and unauthenticated `agent-auth` attempts shall be
    refused.

12. Duplicate enrollment shall be refused, not silently accepted. The manager
    shall be configured with `purge=no` so that an enrollment presenting an
    already-registered agent name fails rather than overwriting the existing
    registration.

13. The enrollment port (1515) shall be closed by default via a host firewall
    rule, and shall be opened only for a bounded interval. The interval shall
    close automatically on expiry without operator action.

14. Minting an enrollment token shall open the enrollment window for the token's
    own lifetime, so that the common case requires no separate action.

15. An enrollment token shall be single-purpose and time-bounded. It shall be
    revoked automatically on expiry by replacing it with an undisclosed value.
    Minting a new token shall immediately invalidate the previous one.

16. Endpoint onboarding shall be achievable by a single command executed on the
    endpoint from the copied `radar-agent` folder, taking the manager address, a
    token, and one or more groups. It shall install every active-response script
    in the catalog and the collectors of the target groups, and shall be safe to
    re-run on an already-enrolled endpoint.

17. The webhook container shall enroll as an agent with a token minted for it on
    its first start, and shall reuse its stored agent key afterwards without a
    new token.

### Failure behaviour

18. Every script shall fail fast: a non-zero exit from any step shall abort the
    sequence rather than continue against a partially configured manager.

19. Deployment shall wait for the Wazuh API and for OpenSearch to become
    reachable before attempting operations against them, with a bounded timeout
    and a diagnostic on expiry.

20. Where a required credential is absent — for example a MaxMind license key
    for a scenario that needs GeoIP enrichment — deployment shall emit a warning
    naming the affected capability and continue, rather than failing the whole
    deployment for an optional enrichment path.

## Acceptance criteria

1. **Idempotency**: applying the same scenario twice produces no second
   `ossec.conf` block, no duplicated ruleset entry, and no restart on the second
   run.
2. **Path resolution**: with a `volumes.yml` missing a required mount,
   deployment aborts naming that mount and makes no partial modification.
3. **Marker discipline**: a hand-added configuration block outside RADAR markers
   survives a deploy/undeploy cycle unmodified.
4. **Selective reversal**: with two shared scenarios deployed, undeploying one
   leaves the shared group configuration intact; undeploying the second clears
   it.
5. **Enrollment refusal**: an `agent-auth` attempt with no token, an expired
   token, and a duplicate agent name are each refused, with distinguishable
   diagnostics.
6. **Window auto-close**: an enrollment window opened for *n* minutes is closed
   at expiry with no operator action.
7. **Re-run safety**: `bootstrap-agent.sh` re-run against an enrolled endpoint
   exits successfully without re-enrolling or duplicating the registration.
8. **Multi-node**: with two manager nodes registered, the manager-side files of a
   scenario are applied to both, and a failure on the second node is reported
   without stopping the deployment.
