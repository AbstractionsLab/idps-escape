# RADAR health check software design

This document specifies the design of the RADAR deployment health check tool (SRS-060). It supersedes the previous version of this document, which specified a two-play Ansible design (`health-check.yml`, `tasks/check_manager.yml`, `tasks/check_agents.yml`, timestamped summary files under `/tmp/`) that is not present in the codebase. The actual tool is a three-stage shell-and-Python script with no orchestrator, no summary files, and no `--manager`/`--agent`/`--ssh-key` arguments.

## Purpose

The health check validates that a RADAR deployment is complete and operational. It reads state from the target environment without changing its configuration, and prints its findings as they are produced rather than collecting them into a report file.

## Module inventory

| Module | Type | Responsibility |
|--------|------|----------------|
| `health-radar.sh` | Bash | Entry point; runs the three stages below in order (also `radar.sh health`) |
| `radar_deploy/manager-health.sh` | Bash, via `docker exec` | Manager container, file and reachability checks, per registered manager node |
| `wazuh_api.cli manager-health-api` | Python | Wazuh API, ruleset, group, agent, OpenSearch and webhook checks |
| `wazuh_api.cli agent-health` | Python | Per-named-agent status and group membership |

The GUI's Status tab (`gui/orchestrator/deploy.py`, `stream_health`) runs the same three stages directly, not through `health-radar.sh`, and streams their output.

## Entry point (`health-radar.sh`)

```bash
./health-radar.sh [--scenario <name|all>] [--agent-name name1,name2]
```

| Argument | Required | Values | Default |
|----------|----------|--------|---------|
| `--scenario` | No | a scenario name, or `all` | `all` |
| `--agent-name` | No | comma-separated agent names | — |

There is no `--manager`/`--agent` mode selection and no SSH key argument: the manager containers always run on the RADAR host, addressed through `docker exec` for the filesystem checks and through the Wazuh REST API for everything else.

## Execution flow

```
health-radar.sh
  │
  ├── [1] radar_deploy/manager-health.sh <scenario>          "=== MANAGER (filesystem/container) ==="
  │       revoke an expired enrollment token, then for each manager node in infra.yaml:
  │       docker exec <node> <checks>, printed directly to stdout
  │
  ├── [2] python3 -m wazuh_api.cli manager-health-api         "=== MANAGER (Wazuh API / OpenSearch / webhook) ==="
  │       one HTTP round-trip per check, printed directly to stdout
  │
  └── [3] python3 -m wazuh_api.cli agent-health                "=== AGENTS ===" (only if --agent-name given)
          one HTTP round-trip per named agent, printed directly to stdout
```

Each stage prints its own section header and its lines as it completes; there is no intermediate file and no final aggregation step. Every line is prefixed `OK`, `WARN`, `FAIL` or `SKIP`.

## Stage 1: manager filesystem/container checks

Resolves the scenario list from `wazuh_api.cli list-scenarios` when `--scenario all` is given, and the manager nodes from `infra.yaml` (no registered node is a `FAIL` and ends the stage). Before checking, it runs `manager-revoke-token.sh --if-expired`, so an enrollment token whose expiry passed while no revocation timer ran is revoked.

| Check | Applies to |
|---|---|
| Webhook container (`WEBHOOK_CONTAINER_NAME`, default `ad-webhook`) running | Always |
| Manager node container running | Each registered manager node |
| `radar_ar.py`, `ar.yaml`, `active_responses.env`, `ossec.conf` present, group-owned `wazuh` | Each node |
| `agent.conf` of the `default` group present (WARN, not FAIL, if absent) | Each node |
| Wazuh framework Python present; `maxminddb` importable | Each node, `suspicious_login` or `geoip_detection` selected |
| Filebeat archives pipeline patched with `log_volume_metric` | Each node, `log_volume` selected |
| `custom-radar-enrich` and its modules present; GeoLite2 databases present; `user_state.sqlite3` present and writable (WARN if not created yet); `enrichment_errors.log` empty of recent entries | Each node, `suspicious_login` selected |
| OpenSearch `_cluster/health` reachable from inside the manager container | Each node, when the indexer address resolves |
| DECIPHER `/health` reachable from inside the manager container | Each node, when `DECIPHER_BASE_URL` is set |
| Webhook URL reachable from inside the indexer container (`SKIP` if that container is not running) | `log_volume` or `linux_resource_utilization` selected, when `WEBHOOK_URL` is set |

**Known coverage gap**: the manager-enrichment file and database checks are gated on `suspicious_login` only, even though `geoip_detection` depends on the same manager-side enrichment (its web enrichment integration `custom-radar-web-enrich` and the same GeoLite2 databases). Running `health-radar.sh --scenario geoip_detection` without `suspicious_login` verifies none of this.

## Stage 2: Wazuh API checks

Runs over the Wazuh REST API and HTTP, with no host or container access.

| Check | Applies to |
|---|---|
| Core Wazuh daemons running (`wazuh-analysisd`, `wazuh-remoted`, `wazuh-logcollector`, `wazuh-db`), per cluster node when clustering is enabled | Always |
| `<!-- RADAR: <scenario> BEGIN -->` marker present in `ossec.conf`, per cluster node when clustering is enabled | Each selected scenario |
| Scenario's agent group has non-empty configuration (or, for a shared scenario, `radar_shared` does) | Each selected scenario |
| Scenario's decoder and rule files registered with the manager | Each selected scenario |
| `whitelist_countries` list registered | `geoip_detection` selected |
| Agents assigned to all of the scenario's groups, with their status (FAIL if none) | Each selected scenario |
| OpenSearch cluster reachable, with its status | If `OS_URL` is set |
| `radar-log-volume` index template present | `log_volume` selected and `OS_URL` set |
| Webhook endpoint responds (WARN if not) | If `WEBHOOK_URL` is set |

## Stage 3: agent checks (only with `--agent-name`)

For each named agent: status via the Wazuh API (`never_connected` is a FAIL, other non-active states a WARN), and membership in `default` plus the selected scenario's group (`all` checks `default` only). The stage exits non-zero when any agent check fails.

## Requirements

1. The health check shall not modify manager or agent configuration, restart a service for a check, or remediate a failure. The only state change allowed is the revocation of an expired enrollment token before Stage 1, which restarts the manager.
2. Every check result shall be classified `OK`, `WARN`, `FAIL` or `SKIP`, printed on its own line as the check completes.
3. Stage 1 and Stage 2 shall run for every invocation; Stage 3 shall run only when `--agent-name` is supplied.
4. A check specific to a scenario shall run only when that scenario is included in the effective scenario list (the explicit `--scenario` value, or every scenario in `config.yaml` when `all` is given).
5. An unreachable dependency (OpenSearch, the webhook, DECIPHER) shall be reported as `FAIL` or `WARN` for that specific check and shall not abort the remaining checks.

## Acceptance criteria

1. **No configuration change**: running the health check against a fully deployed scenario, with no expired token pending, produces no change in the manager's `ossec.conf`, ruleset, or running containers.
2. **Scenario scoping**: `--scenario log_volume` reports on the Filebeat pipeline patch and the index template; it does not report on GeoIP databases or `whitelist_countries`.
3. **Partial dependency failure**: with `WEBHOOK_URL` unset, the webhook checks are skipped rather than failing the whole run; with `OS_URL` set but OpenSearch unreachable, that check reports `FAIL` and every other check still runs.
4. **Agent stage gating**: omitting `--agent-name` produces no `=== AGENTS ===` section.
