v2.2.0

November 2026
New feature

Signature and anomaly evidence, combined over time

RADAR used to score every alert on its own. A signature alert carried no anomaly evidence and an anomaly alert carried no signature evidence, so the two were never combined. Now, with fusion enabled for a scenario, each alert looks back for the strongest alert of the other kind on the same user or host, and uses it for the term it cannot carry itself. Its weight is 1 inside the anomaly's data window and falls linearly to 0 at window_minutes from it. Nothing waits: whichever alert arrives second gets the combined score.

Fusion only fills the missing term, using the scenario's existing weights. Without a counterpart the score is exactly what it was before, so existing calibrations stay valid. A missing anomaly never lowers a score, and a counterpart never changes what is blocked or locked: targets come only from the alert being decided. Fusion is opt-in per scenario (a fusion: block in ar.yaml) and enabled for suspicious_login, whose new off-hours activity detection (below) supplies its anomaly side, wired end to end through rules 210039 to 210041, the active-response binding and the anomaly decoder.

New feature

Off-hours activity against declared working hours

suspicious_login's off-hour detector learned each user's average login time. One night-time login among a day of normal work barely moves an average, so it missed exactly the event it was meant to catch. Working hours are now declared per schedule group in config.yaml: a time zone, the weekdays a shift starts on, and a start and end time, with shifts that cross midnight and summer time handled. An ingest pipeline marks every archived event of a listed user as on or off hours, both for events from agents and for history marked by a backfill.

Each group picks a mode. Rule mode (rule 210041) is for staff whose normal off-hours activity is zero: it reports the start of each off-hours burst once, from the first event and without training, with the number of events, their times and the group. Model mode (rule 210040) is for administrators and on-call staff: a per-user detector learns their usual number of off-hours events and reports an unusual one. Both are scored as the scenario's anomaly side and fused with the user's signature alerts. Users who aren't listed are not evaluated unless a default group is set.

off_hours.py radar-off-hours pipeline rule 210041 rule 210040 SRS-062

Synthetic history and live checks

The suspicious_login ingest script works again: it crashed on missing imports and dated the after-midnight part of night shifts to the wrong day. Its history now includes an administrator with evening work and one burst at 02:00, for model mode. New checks run against a live cluster: the marking pipeline on a shared case table, rule mode replayed at chosen times without waiting, and model mode analysed over the synthetic history.

wazuh_ingest.py radar-test-framework/checks TST-077 to TST-079

Risk engine and anomaly alert chain fixes

lock_user_linux.sh now targets only the users named in the alert itself. It used to target every user found in the agent's logs in the context window, so a bystander, such as an admin who ran sudo that minute, could be locked. suspicious_login now asks DECIPHER about the user named in the alert, not the alphabetically first user on the host. Alerts listed as both signature and anomaly now get their anomaly score.

The anomaly monitor reports up to monitor_max_entities (default 5) anomalous hosts or users per run instead of only the top one, and forwards each anomaly's own data window. linux_resource_utilization alerts now fire when log_volume is deployed on the same manager; before, rule 100321 never fired. geoip_detection, which has no CTI source, now puts its full weight on the signature, so rules 100900, 100901 and 100903 reach T2 and run firewall-drop.

lock_user_linux.sh monitor_max_entities radar_ad_received geoip_detection behaviour change
New feature

SONAR: pluggable detectors and an evaluation tool

SONAR's detector is now selectable: mvad (the default, unchanged), pca, a probabilistic PCA over short windows that trains in well under a second, and ewma, a per-feature baseline. The new sonar evaluate command trains a scenario on one file and scores labelled test data: event-level precision, recall and F1, detection delay and false alarms per day. With a validation split it calibrates the scenario's threshold and min_consecutive, and it can score other detectors' results on the same labelled data.

First runs on synthetic data from SONAR's own generators, with only a few attacks per scenario, were used to set the bundled scenarios' detection settings. They are preliminary and not yet independently reviewed, so they say little about which detector is better on real traffic; the records are kept in the SONAR evaluation folder. A rigorous comparison on labelled lab data, against the RCF detectors RADAR uses and other mechanisms, remains future work.

sonar evaluate mvad · pca · ewma calibration sonar export

SONAR anomalies as Wazuh alerts, delivered once

SONAR now reports anomalies to the Wazuh manager, which raises them as alerts (rules 100500 to 100503), so rules, integrations and RADAR scenarios can act on them. Outputs are configurable sinks (wazuh, datastream, index, jsonl, stdout), each with its own delivery watermark.

Each anomaly is delivered once: before, realtime polling stored the same anomaly about 288 times over a 24-hour window. Alert searches now page through every matching alert instead of stopping at 10,000, every indexer request has a timeout, and realtime mode retries failed polls with backoff.

rules 100500–100503 output.sinks delivery watermark point-in-time search

SONAR model quality and packaging

SONAR no longer saves models that were never trained. Alert volume and quiet periods are now visible to the model (feature schema 2), the categorical vocabulary is fixed at training, and lookback_minutes scores every bucket in the period. detection.threshold is now a 0–1 severity. Models are directories without pickle, SONAR runs from any directory as a standalone package, and the sonar:v0.8 image contains only SONAR, no longer the whole repository.

feature schema 2 no pickle standalone wheel sonar:v0.8

Linux resource utilization and the radar-agent folder

A new RADAR scenario detects anomalous CPU and memory use on Linux endpoints, from collector to active response, with simulation and seeding scripts. SONAR gets a matching scenario that reads the same events and trains one model per host (--agent).

Everything installed on endpoints now lives in radar/radar-agent/. Active-response scripts are versioned in ar-scripts.yaml, every endpoint receives all of them, and the GUI's mitigation list is read from the same file.

linux_resource_utilization radar-agent ar-scripts.yaml --agent

Specifications and manuals aligned with the code

The specifications and the SONAR and RADAR user manuals now describe the system as it is in this release. Outdated items were rewritten or retired, features not built yet are marked as planned, new items cover parts that had no specification, and traceability from requirements to tests is more complete. Diagrams are now written as code.

v2.1.0

September 2026
Security hardening

Active response & platform hardening

Active response scripts now validate every mitigation target (usernames, service names, IPs) instead of trusting alert fields an attacker could forge. terminate_service.sh only stops explicitly allow-listed services, kills connections by exact address, and can no longer be tricked into running arbitrary executables via path traversal. lock_user_linux.sh no longer unlocks accounts on malformed input, and protects system/service accounts.

The GUI now binds to 127.0.0.1 only (reach it via SSH tunnel), requires a login token and re-confirms the sudo password before revealing or redirecting stored secrets. New deployments get unique, randomly generated credentials, and sudo ./radar.sh rotate-credentials rotates them for existing ones. The anomaly-detection webhook now requires a shared secret and only accepts alerts from its own log.

Upgrading: re-run bootstrap-agent.sh on suspicious_login/log_volume endpoints and redeploy ar.yaml; run ./radar.sh run log_volume once so the webhook notification channel picks up the new shared secret.

terminate_service.sh lock_user_linux.sh GUI access control credential rotation webhook shared secret breaking change

Infrastructure-aware IP resolution

Connection address resolution (webhook, manager–indexer, and other core stack links) now falls back to the registered container name when the declared host is unreachable, instead of failing outright. Adds support for existing single-node and multi-node Wazuh instances, with a new Infrastructure page in the manuals.

IP resolution fallback existing Wazuh support Infrastructure page

Active response targeting scope & manager hardening

IP-based mitigations now act only on the alert's own source IP, never on addresses found elsewhere in the logs, with a new global.never_block allowlist and proxy-aware X-Forwarded-For handling for scanning_detection. Manager builds no longer leave mounted directories world-writable, and expired enrollment tokens are revoked even across manager restarts.

never_block trusted_proxies repair-permissions enrollment token revocation

Simulation coverage & documentation

Simulation scripts were matched to the acceptance criteria in SRS-051 and SRS-055, with updated unit tests. Documentation was refreshed for the IP resolution fallback and infrastructure-aware architecture, and the README gained a "Security assumptions and recommendations" section covering firewall ports and SSH-tunnel access to the GUI.

SRS-051 SRS-055 security assumptions

v2.0.0

August 2026
New feature

Manager-centric enrichment architecture

Enrichment logic has moved out of the endpoints and into the Wazuh manager. A new manager-enrichment package (enrichment.py, web_enrichment.py, geoip.py, state_store.py) centralizes GeoIP and web enrichment processing, integrated directly with manager workflows and web endpoints.

Agents now ship raw /var/log/auth.log directly instead of running a per-endpoint enrichment helper, venv, and systemd service. This also fixes per-user velocity/ASN state, which was previously tracked separately per endpoint instead of centrally.

Migrating an existing deployment: set MAXMIND_LICENSE_KEY in the manager's .env, redeploy with sudo ./build-radar.sh suspicious_login / geoip_detection, then re-run bootstrap-agent.sh on every existing endpoint. Manager and agent updates must land together per endpoint.

manager-enrichment enrichment.py web_enrichment.py geoip.py state_store.py breaking change

Manager APIs, CLI, and deployment orchestration

A major API redesign supports the new manager-centric enrichment flow, with a new wazuh_api module providing programmatic and CLI access to manager operations. Manager-side helper scripts under radar_deploy (apply-scenario, assign-agent-group, ensure-certs, health, local-agent, mint-token) are now driven by top-level radar.sh and bootstrap-agent.sh entrypoints.

Enrollment hardening & agent lifecycle management

New scripts secure and manage Wazuh agent enrollment end to end: manager-harden-enrollment.sh enforces password-protected enrollment with purge disabled and cluster key management; manager-enrollment-window.sh opens and closes time-limited enrollment windows via firewall rules on port 1515. Webhook deployment now mints a short-lived registration token when needed and persists agent state.

The scenario ships with full documentation (scanning_detection_explained.md — objectives, detection methodology, manual setup, and deployment instructions), a formal system requirement specification with acceptance criteria and test specification, and a test report execution for the scanning_detection scenario.
