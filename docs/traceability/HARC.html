1.0 SONAR High-Level Architecture

High-level architecture requirements for SONAR (SIEM-Oriented Neural Anomaly Recognition) subsystem.

1.1 SONAR subsystem context HARC-009

The diagram below depicts the system context of the SONAR (SIEM-Oriented Neural Anomaly Recognition) subsystem within the IDPS-ESCAPE architecture.

SONAR is a multivariate anomaly detection engine that analyzes Wazuh security alerts to identify unusual patterns that may indicate security threats. It reads alerts (or, for scenarios such as radar_linux_resource_utilization, archived events) from the Wazuh Indexer (OpenSearch), scores them with a trainable detector backend, and reports each anomaly to the Wazuh manager as an event, so that Wazuh rules raise SONAR alerts that active responses, including RADAR's, can act on. It can also store anomaly documents in the indexer for dashboards.

SONAR runs on the Wazuh manager host or on a dedicated machine, never on monitored endpoints, whose resources may be limited; no Wazuh agent is needed on the SONAR host.

System boundary

Key interfaces

Interface Direction Protocol Purpose
Wazuh Indexer API Inbound HTTPS/REST Alert retrieval (SONAR's own alerts excluded); for sonar export, also RADAR's anomaly detection results
Wazuh manager log file Outbound JSON lines read by <localfile> Anomaly events, SONAR on the manager host
Wazuh server API POST /events Outbound HTTPS/REST, JWT Anomaly events, SONAR on a dedicated host
Wazuh server API PUT /rules/files Outbound HTTPS/REST, JWT Installation of SONAR's rules (sonar wazuh install-rules)
Wazuh Data Streams, anomalies index Outbound HTTPS/REST Anomaly documents for dashboards (optional)
Local file system Local Files Model directories, per-scenario delivery watermarks, evaluation reports, debug datasets

RADAR has no direct interface with SONAR: it acts on the Wazuh alerts that SONAR's events raise, reading data.anomaly_grade and data.anomaly_confidence like for any other anomaly scenario. For comparisons only, sonar export reads the results of RADAR's detectors from the indexer and sonar evaluate scores them with SONAR's own metrics.

SONAR runs as a command-line process, from a Python installation or from the SONAR container image (sonar/Dockerfile.sonar, started with sonar/sonar.sh).

1.3 SONAR data flow architecture HARC-011

The diagram below illustrates the high-level data flow through the SONAR subsystem for training and detection operations.

Training data flow

Training fetches the scenario's history, builds the feature matrix, fits the scenario's detector backend (mvad by default, or pca, ewma) and stores the model directory. With the data stream enabled, it also prepares the scenario's index templates and ISM policy.

Detection data flow

Detection fetches the scored window plus the context the model needs, builds features with the model's feature contract, scores each bucket, selects anomalies and delivers each new anomaly once to every configured sink.

Evaluation data flow

sonar evaluate trains a scenario's backend on a training file and scores labelled validation and test files, or scores another detector's exported results (for example RADAR's, written by sonar export), with the same metrics and the same decision rule as detection.

Data transformations

Stage Input Output Transformation
Ingestion Wazuh alerts (JSON) from the indexer or a local file Raw alert list Time range, scenario alert_filter, optional agent filter, exclusion of SONAR's own alerts; only the fields the features read
Feature Engineering Raw alerts Time-series matrix Regular time grid, per-bucket counts and means, categorical vocabulary
Detector backend Time-series matrix One verdict per bucket is_anomaly, severity (0–1), raw score, feature contributions
Post-Processing Verdicts Anomaly documents Minimum severity, minimum run length, deterministic anomaly_id, model and scenario metadata
Delivery Anomaly documents SONAR events, indexed documents, local lines Per-sink watermark filtering, Wazuh event derivation, create-only indexing
Evaluation Detections, label files Report Alarm-level scoring, calibration of threshold and run length

2.0 RADAR High-Level Architecture

High-level architecture requirements for RADAR (Real-time Alert Detection and Automated Response) subsystem.

2.1 RADAR architecture HARC-004

RADAR (Risk-aware Anomaly Detection-based Automated Response) is a security orchestration subsystem within IDPS-ESCAPE that combines signature-based detection with anomaly detection, and drives both into a single risk-scored, tiered automated response.

Core technologies

  • Wazuh (4.14.1 images in radar/docker-compose.core.yml): manager, agents, indexer and dashboard; the manager's decoders, rules, integrations and active-response framework carry every RADAR scenario.
  • OpenSearch plugins of the Wazuh indexer: the Anomaly Detection plugin (Random Cut Forest) for the anomaly-based scenarios, and the Alerting plugin, whose monitors notify RADAR's webhook.
  • Docker / Docker Compose: the core stack (indexer, manager, dashboard), the webhook container (radar/docker-compose.webhook.yml), and the short-lived radar-cli image (radar/Dockerfile.radar-cli) that creates detectors and monitors and seeds history.
  • MaxMind GeoLite2 City and ASN databases, downloaded by the manager at deployment, for manager-side enrichment.
  • Optional external services: SATRAP-DL DECIPHER (CTI score, and Flowintel case creation through its incident endpoint) and an SMTP server for notifications. RADAR runs without either.

Design principles

Modularity. Each detection use case is packaged as a scenario — decoders, rules, CDB lists, agent and manager configuration snippets, an optional detector/monitor definition, active-response bindings and risk parameters — that can be deployed independently of the others and coexists with them on the same manager. Artifacts are grouped by type, then by scenario (radar/scenarios/<artifact type>/<scenario>/). A new scenario is added without modifying the core framework (SWD-034, SWD-027).

Idempotency. Deployment goes through the Wazuh REST API and idempotent Docker operations (SWD-042): rule, decoder and list files are uploaded only when their content differs, marked configuration blocks are replaced rather than appended, and detectors and monitors are looked up by name before being created. Re-running a deployment step produces the same end state.

Separation of concerns. The architecture separates data collection (Wazuh agents and RADAR's metric collectors), data enrichment (manager-side, for the scenarios that need it — SWD-030), detection logic (rules and anomaly detectors — SWD-026, SWD-028, SWD-034), response execution (SWD-027), and orchestration (SWD-042, SWD-041).

Hybrid detection. Signature-based rules give fast, deterministic matching for known patterns without a training period; anomaly detection gives behavioural coverage for patterns no rule anticipates. A scenario may use either or both; the risk engine (HARC-012) combines whichever sources a scenario configures, and for a scenario with a fusion block it combines a signature alert with an anomaly alert for the same entity that arrived within a time window.

Configuration-driven deployment. Scenario parameters — index patterns, features, thresholds, detector settings, off-hours schedules, ingest settings — are centralised in radar/config.yaml; risk weights, tiers, fusion and mitigations in radar/scenarios/active_responses/ar.yaml. Neither requires a code change to retune (SWD-032).

System architecture

RADAR consists of the following components:

Component Role Key functions
Wazuh agents Endpoint monitoring Log collection, RADAR metric collectors (log_volume, linux_resource_utilization), execution of dispatched active-response scripts
Wazuh manager Central control Decoding, manager-side enrichment, rule evaluation, radar_ar.py risk scoring and response dispatch
Wazuh indexer (OpenSearch) Data platform Storage of alerts and archived events, ingest pipelines, anomaly detectors (RCF) and monitors
Webhook container Alert routing Receives a monitor's HTTP notification and writes it as a log line that its own Wazuh agent forwards to the manager
radar-cli jobs Detector lifecycle Create or update detectors, monitors and the off-hours pipeline; seed detector history
RADAR scripts / GUI Orchestration Deployment automation, scenario and agent lifecycle management, connector configuration
DECIPHER (external, optional) CTI and case management CTI score for the risk engine; Flowintel case creation (SWD-038)

Module structure

Wazuh agent. Collects logs and executes dispatched active-response commands. Agents forward logs unmodified; enrichment, where a scenario needs it, happens centrally on the manager, not on the endpoint (SWD-030, HARC-014). Everything RADAR installs on an endpoint — metric collectors, versioned active-response scripts and their catalogue — lives in radar/radar-agent/ and is installed by radar/radar-agent/bootstrap-agent.sh.

Wazuh manager. The central control plane: manager-side enrichment integrations (SWD-030) for suspicious_login and geoip_detection, decoders and rules (SWD-034), and the active response radar_ar.py, which scores every RADAR alert and dispatches the tier's actions (SWD-026, SWD-027). Anomaly alerts re-enter the manager through the webhook (below).

Wazuh indexer. Storage and search for alerts and archived events, and the Anomaly Detection plugin used by the anomaly-based scenarios (SWD-028). The Filebeat archives pipeline routes log_volume metrics to wazuh-ad-log-volume-* and calls the radar-off-hours ingest pipeline that flags off-hours activity. Detector and monitor lifecycle for a scenario is managed by run-radar.sh and the radar/anomaly_detector/ modules (detector.py, monitor.py, webhook.py, off_hours.py) it runs inside the radar-cli container.

Webhook endpoint. A small HTTP service (radar/webhook/) that receives an OpenSearch monitor's POST notification, authenticated by a shared secret, and writes one log line per anomalous entity to a file monitored by the Wazuh agent installed in the same container. The manager decodes and evaluates that line like any other event, closing the loop from anomaly detection back into the rule engine and, from there, into active response. radar_ar.py accepts anomaly alerts only from that agent and file. Brought up by build-radar.sh alongside the rest of the stack.

Deployment control plane. The entry-point scripts (radar.sh, build-radar.sh, run-radar.sh, health-radar.sh, stop-radar.sh in radar/, and radar/radar-agent/bootstrap-agent.sh on endpoints), the radar/radar_deploy/ manager-side scripts, the radar/wazuh_api/ Wazuh REST API layer and CLI, and the GUI (radar/gui/). Specified in SWD-042 and SWD-041.

Scenarios

Five scenarios and a default rule set ship in the current codebase (radar/config.yaml, radar/scenarios/active_responses/ar.yaml):

Scenario Detection Configured mitigations
geoip_detection Signature, on manager-enriched SSH and web-access events (country whitelist) firewall-drop (tiers 2 and 3)
suspicious_login Signature (failed-login bursts, impossible travel on manager-enriched SSH events, Office 365 login failures) and anomaly (off-hours activity: rule mode or per-user RCF model mode), fused per user firewall-drop (tier 2); firewall-drop and lock_user_linux.sh (tier 3)
scanning_detection Signature (web-layer scanning) firewall-drop (tiers 2 and 3), disabled by default
log_volume Anomaly (RCF on log growth, per agent) terminate_service.sh (tier 3)
linux_resource_utilization Anomaly (RCF on CPU and memory use, per agent) terminate_service.sh (tier 3)
default Signature (selected stock Wazuh rules and RADAR rules 100400–100405) none; notification and case only

Every tier at or above tier 1 sends an email and, when DECIPHER is reachable, creates a Flowintel case. Mitigations run only for a scenario whose allow_mitigation is true, and terminate_service.sh and lock_user_linux.sh are further bounded by allowlists and protected-user lists on manager and endpoint.

Earlier design material referenced additional demo scenarios (insider threat, DDoS detection, C2 malware communication). Their archived code was removed in v2.0.0 (CHANGELOG), and none of them can be deployed.

2.2 RADAR Automated Test Framework architecture HARC-005

The RADAR Automated Test Framework (RATF, radar/radar-test-framework/) validates a deployed RADAR scenario end to end by producing, on a monitored endpoint, the artefacts that the scenario detects. The artefacts then travel the production pipeline: Wazuh agent, manager decoders and rules, manager-side enrichment, the OpenSearch anomaly detector and webhook where the scenario uses one, the risk engine (radar_ar.py) and the active responses.

The framework covers four phases. Only one of them is implemented inside RATF:

Phase Implemented by Location
Setup build-radar.sh or the GUI's Scenario Management, then endpoint onboarding with radar-agent/bootstrap-agent.sh Outside RATF (deployment control plane, SWD-042)
Ingest run-radar.sh <scenario> --ingest true or the GUI's Anomaly Detector tab, which seeds detector history and creates the detector and monitor Outside RATF (radar/scenarios/ingest_scripts/)
Simulate One standalone script per scenario, copied to and run on the endpoint; inject_ad_alert.py runs on the manager host and posts an anomaly to the webhook radar/radar-test-framework/simulate/scenarios/
Evaluate Not implemented (see planned extensions) —

Besides the simulation scripts, radar/radar-test-framework/checks/ holds live checks that run from the RADAR host against the indexer. They currently cover off-hours activity detection (suspicious_login).

The framework has no controller process and no remote dispatch: there is no SSH, inventory or orchestration layer between the RADAR host and the endpoints. Each script carries its parameters in a CONFIG block at its top. The operator verifies the outcome on the Wazuh dashboard, in the active-response log, in the alert email and, if DECIPHER is configured, in the FlowIntel case. See: radar/radar-test-framework/README.md and radar/radar-test-framework/simulate/README.md.

Planned extensions

Status: planned. Not implemented as of v2.2.0. The extensions below specify intended behaviour; no code implements them yet.

  • Evaluator: retrieve the detection results of a simulation run from the indexer, compare them with the injected ground truth and compute detection metrics, written to a result file (SWD-021).
  • Single controller: one entry point that sequences setup, ingest, simulation and evaluation for a scenario without manual steps.

2.4 RADAR deployment topology: local manager, remote agents HARC-007

RADAR supports one deployment topology. The Wazuh manager, indexer and dashboard containers, the RADAR webhook container and the RADAR control plane (radar/radar.sh, the entry-point scripts, radar/radar_deploy/, radar/wazuh_api/ and the GUI) all run on one Docker host, the RADAR host. Monitored endpoints are separate hosts that run a native Wazuh agent.

  • Manager side. build-radar.sh brings up docker-compose.core.yml (Wazuh 4.14.1 manager, indexer, dashboard), overlaid with the bind mounts of volumes.yml, unless a manager container is already running. A pre-existing Wazuh installation running in containers on the same host can be used instead; its components are registered in infra.yaml through the GUI's Infrastructure page, and several manager nodes of one cluster can be registered. Manager-side files are written on the host side of the bind mounts, and docker exec is used only for ownership, permissions and package installs, so the manager containers must run on the RADAR host. Everything else goes through the Wazuh REST API (port 55000) and the indexer API (port 9200).
  • Webhook. docker-compose.webhook.yml runs the ad-webhook container, which receives OpenSearch monitor notifications on port 8080 and is itself a Wazuh agent enrolled with the manager.
  • Endpoints. An endpoint is onboarded by copying the radar/radar-agent/ folder to it and running bootstrap-agent.sh with the manager address, a short-lived enrollment token and the target groups. The script installs a pinned Wazuh agent package, enrolls through port 1515 while the enrollment window is open, installs the active-response dispatchers and the scenario's metric collectors, and starts the agent. No container runtime is needed on the endpoint, and the RADAR host never connects to the endpoint.
  • Run time. Agents send events to the manager on port 1514. Scenario configuration reaches them through their Wazuh agent groups. Active responses decided by radar_ar.py on the manager run on the endpoint through the Wazuh active-response channel.

There is no remote-manager mode and no containerised-agent mode (see HARC-006 and HARC-008, both obsolete). See: docs/manual/radar_docs/radar-getting-started.md.

2.6 RADAR risk engine architecture HARC-012

The RADAR risk engine is part of the active response radar_ar.py (radar/scenarios/active_responses/radar_ar.py), which the Wazuh manager runs for every alert bound to a RADAR scenario. It combines anomaly detection outputs, signature-based detection data and a CTI score into one risk score, maps the score to a tier, and drives the tier's actions.

The risk engine has three inputs:

  • Anomaly intensity (A): $A = G \times C$, from the alert's data.anomaly_grade and data.anomaly_confidence. These come from an OpenSearch RCF detector through the monitor and webhook, or are fixed values for the off-hours rule mode of suspicious_login. Only alerts whose rule is listed under the scenario's ad.rule_ids carry A, and only if they come from the webhook agent's log.
  • Signature risk (S): $S = L \times I$, where the likelihood $L$ is looked up in the scenario's signature_likelihood table (by rule ID or rule group) and the impact $I$ is the scenario's signature_impact. An anomaly-only alert has $S = 0$.
  • CTI score (T): the severity returned by DECIPHER's analyze endpoint for the scenario (SWD-038), clamped to [0, 1]. It is 0 when DECIPHER is not configured or unreachable, or when no analyze endpoint exists for the scenario.

For a scenario with a fusion block, the term an alert cannot carry itself is filled with the strongest alert of the other kind for the same entity within the fusion window, discounted linearly by the time gap; fusion can only raise A or S.

The weighted combination $R = w_{ad} A + w_{sig} S + w_{cti} T$, clamped to [0, 1], drives tier-based response actions. Weights are set per scenario in ar.yaml. Four tiers are delimited by the three configurable boundaries tier1_min, tier1_max and tier2_max; the normative tier semantics are specified in SRS-061.

  • Tier 0 (R < tier1_min, default boundary 0.0): the decision is logged; no notification, case or mitigation
  • Tier 1 (tier1_min ≤ R < tier1_max, default boundary 0.33): email notification and, when DECIPHER is reachable, Flowintel case creation
  • Tier 2 (tier1_max ≤ R < tier2_max, default boundary 0.66): tier 1 actions plus the scenario's mitigations_tier2, subject to allow_mitigation
  • Tier 3 (R ≥ tier2_max): tier 1 actions plus the scenario's mitigations_tier3, subject to allow_mitigation; in the shipped ar.yaml this list repeats the tier 2 mitigations and adds the stronger containment actions

Every decision, including withheld mitigations and the reason they were withheld, is written to the manager's active-responses.log.

2.7 RADAR deployment automation architecture HARC-013

RADAR's deployment automation (the deployment control plane) is made of shell entry points, a manager-side shell backbone and a Python Wazuh API layer, driven either from the command line or from the RADAR GUI. It replaced the Ansible-based automation, which was removed in v2.0.0. SWD-042 specifies its design.

Key architectural decisions:

  • One privileged host, no remote execution. The control plane runs on the Docker host that runs the Wazuh manager containers. Nothing is pushed to endpoints over SSH, and there is no inventory or vault. sudo is needed only to bring up the containers, to write under the bind-mounted manager directories and to manage the iptables rule guarding the enrollment port.
  • API first, files second. Whatever the Wazuh REST API can do (agent groups and their agent.conf, decoders, rules, CDB lists, ossec.conf blocks, agent assignment and deregistration, health) goes through radar/wazuh_api/. Files the API cannot place (radar_ar.py, ar.yaml, the manager's copy of .env, enrichment integrations, GeoLite2 databases, Filebeat pipeline patches) are written by radar/radar_deploy/ on the host side of the bind mounts listed in radar/volumes.yml.
  • Marker-delimited, idempotent changes. ossec.conf is changed only inside <!-- RADAR: <name> BEGIN/END --> blocks. Re-applying a scenario converges to the same state, and undoing a scenario keeps everything another deployed scenario still needs.
  • Self-onboarding endpoints. An endpoint runs radar/radar-agent/bootstrap-agent.sh with a short-lived enrollment token. Enrollment is hardened (use_password=yes, purge=no, port 1515 closed outside a timed window).
  • Runtime address resolution. radar/infra.yaml registers the manager node(s), indexer, dashboard and webhook. wazuh_api/infra.py tries a component's declared host first and falls back to its container name, so the same scripts serve a stack RADAR deployed itself and a pre-existing containerised Wazuh installation.

2.8 RADAR manager-side enrichment architecture HARC-014

The diagram below depicts the high-level architecture of RADAR's log enrichment, which runs on the Wazuh manager as two integratord integrations. It replaced the earlier RADAR helper, a per-endpoint enrichment daemon with its own virtual environment, service and GeoIP databases, which was removed in v2.0.0 (CHANGELOG, "Manager Enrichment & Architecture").

Enrichment adds geographic and behavioural context to authentication and web-access events so that the suspicious_login and geoip_detection rules can match on it (impossible travel, country change, country whitelist). Because the manager receives the events of every endpoint, it keeps one history per user, so geo-velocity and ASN novelty are computed across all endpoints a user reaches (SRS-068). Endpoints run only the Wazuh agent and forward their raw logs.

Key architectural components (radar/manager-enrichment/):

  • custom-radar-enrich: integration entry point for authentication events. Wazuh calls it for alerts in the authentication_success and authentication_failed groups. It parses the user, source IP, outcome and timestamp from the original log line, enriches them and appends the line with a RADAR … tail to /var/ossec/logs/radar/enriched_auth.log.
  • custom-radar-web-enrich: integration entry point for web-access events (accesslog group), writing /var/ossec/logs/radar/enriched_web_access.log.
  • enrichment.py: authentication log parsing, RadarEnricher (geo-velocity, country change, ASN novelty) and the tail format.
  • web_enrichment.py: source-IP extraction from access-log lines, private-address filtering and the web tail format.
  • geoip.py: stateless lookup of country, region, city, coordinates and ASN in the MaxMind GeoLite2 City and ASN databases.
  • state_store.py: UserState and UserStateStore, the per-user history (last time, position and country, 90-day ASN history) in one SQLite database on the manager.

The manager reads both enriched files through <localfile> entries, so each enriched line is decoded a second time by the scenario's -with-radar decoders, and the scenario rules evaluate the radar_* fields. Failures are written to /var/ossec/logs/radar/enrichment_errors.log and never suppress the original alert. The design is specified in LARC-025 and SWD-030.

2.9 RADAR adversarial ML defense architecture HARC-015

Status: planned. Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

The diagram below depicts the intended defense-in-depth architecture for protecting RADAR's anomaly detection against adversarial machine learning attacks (data poisoning, evasion, backdoors, model stealing).

The architecture is to provide five defensive layers:

Layer 1: Baseline Protection

  • Clean data initialization from verified periods
  • Gold-standard training dataset management
  • Digital clean room exercises for pristine baselines

Layer 2: Concept Drift Detection

  • Baseline shift velocity monitoring
  • Automated alerts on sudden baseline changes
  • Manual approval gates for model updates

Layer 3: Multi-Layer Validation

  • Signature-based detection (Wazuh, Suricata)
  • Multivariate AD (SONAR MVAD, ADBox MTAD-GAT)
  • Streaming AD (OpenSearch RRCF)
  • Cross-layer anomaly correlation

Layer 4: Human-in-the-Loop (HITL)

  • Transparent model reasoning exposure
  • Analyst review workflows
  • Feedback loops for model improvement
  • Alert fusion and enrichment

Layer 5: System Hardening

  • Cryptographic log integrity (SHA-256 hashing)
  • Model file access controls and versioning
  • Training pipeline authentication
  • Audit logging of all model operations

Relation to the current implementation

None of the five layers exists as specified: RADAR has no gold-standard baseline management, drift monitor, approval gate, analyst feedback loop, log hashing or model access control. Some existing mechanisms reduce the same risks and would be building blocks for it:

  • Hybrid scoring: a scenario can weight signature, anomaly and CTI evidence together, and suspicious_login fuses a signature alert with an anomaly alert for the same user (HARC-012, radar/scenarios/active_responses/radar_ar.py).
  • Alert origin checks: anomaly alerts are accepted only from the webhook container's agent and log file, and the webhook requires a shared secret (radar/webhook/ad_alerts_webhook.py).
  • Bounded mitigation: mitigation is opt-in per scenario and its targets are validated against allowlists on manager and endpoint.

Practitioner guidance on these attacks is in docs/manual/radar_docs/adversarial-ml-guidance.md.
