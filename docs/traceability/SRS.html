1.0 SONAR System Requirements

System-level requirements for SONAR (SIEM-Oriented Neural Anomaly Recognition) anomaly detection subsystem.

1.1 SONAR training adequacy SRS-072

SONAR SHALL NOT persist an anomaly detection model unless the training run performs at least one optimiser update and has validation data to select the model with. Before fitting, SONAR SHALL determine from the number of time buckets and the training parameters whether these conditions hold. If they do not, SONAR SHALL refuse to train, persist nothing, exit with a non-zero status, and state the number of time buckets the configured parameters require.

SONAR SHALL record in every persisted model the effective training parameters and the number of optimiser updates performed, and SHALL warn when that number is below a configurable minimum.

Rationale

The MVAD library builds training windows with a stride, drops incomplete batches and selects its checkpoint on a validation split. Below a data size that depends on these parameters it completes training without a single update and returns a randomly initialised network. Such a model produces anomaly scores that carry no information, and nothing in its output reveals this. Several shipped scenarios and a demonstration model were affected before this requirement.

Acceptance criteria

  1. Training with fewer time buckets than the configured parameters require fails before fitting, persists no model, exits non-zero and reports the required bucket count.
  2. The number of optimiser updates SONAR predicts equals the number the library performs.
  3. Every persisted model records its effective training parameters and number of updates.
  4. Training parameters the library would ignore are rejected.

1.2 SONAR regular time axis and volume features SRS-073

SONAR SHALL represent alert activity as a time series with one row for every time bucket of the analysed period, including buckets without any alert. Every feature that counts alerts (the total alert count, derived indicators, category values) SHALL be the number of matching alerts in the bucket, so that a change in alert volume changes the feature values. A numeric field SHALL be aggregated only over the alerts that carry it.

Rationale

Anomalies in alert streams are often changes in volume: a burst of failed logins, or alerts that stop arriving. Averaging per-alert indicators makes one failed login and two hundred indistinguishable, and dropping empty buckets makes silence invisible and the time axis irregular. Treating a missing field as zero dilutes metric averages with unrelated alerts.

Acceptance criteria

  1. Buckets without alerts inside the analysed period appear as rows with zero counts.
  2. One and two hundred matching alerts in a bucket yield different feature values.
  3. The mean of a numeric field in a bucket is computed over the alerts that carry the field only.

1.3 SONAR feature contract between training and detection SRS-074

SONAR SHALL record in every persisted model the feature configuration, the categorical vocabulary (the category values that have their own feature) and the feature layout version it was trained with. Detection SHALL build its features from the model's recorded configuration and vocabulary, SHALL count category values unseen in training in a dedicated "other" feature, and SHALL refuse to predict on features that differ from the training features or to load a model with a different feature layout version.

Rationale

Recomputing the category vocabulary from each detection window, and silently zero-filling or dropping columns that differ, discarded exactly the new categories that indicate an attack and applied models to data they were not trained on without any warning.

Acceptance criteria

  1. A category value unseen in training is counted in the "other" feature at detection, and the detection features equal the training features.
  2. When the scenario's feature settings differ from the model's, detection warns and uses the model's settings.
  3. Predicting on features that differ from the training features fails with an error naming the differing features.
  4. Loading a model with a different or unknown feature layout version fails with a request to retrain.

1.4 SONAR detection window and anomaly reporting SRS-075

A SONAR detection run SHALL give a verdict for every complete time bucket of the requested detection period and for no other bucket. The bucket still filling at detection time SHALL NOT be scored. SONAR SHALL obtain on its own the earlier data its model needs before the first bucket of the period. A bucket SHALL be reported as an anomaly when the model flags it, its severity (between 0 and 1) reaches the configured minimum if one is configured, and it belongs to a run of at least the configured number of consecutive such buckets. A one-shot detection run SHALL end with a status that distinguishes a scored period, a period that could not be scored for lack of data, and an error.

Rationale

The model needs a fixed amount of history before each bucket it scores. Requiring users to size the detection period for that history left most of the period without a verdict: in the resource-monitoring test data, injected attacks were never evaluated. Comparing the minimum with an unbounded raw score suppressed anomalies confined to a few features. A partially filled bucket looks like a drop in activity. Reporting an unscored period as success hid missing detection.

Acceptance criteria

  1. Every complete bucket of the requested period receives a verdict, and no bucket outside it is reported.
  2. The bucket containing the time of the run is not scored.
  3. The minimum is applied to the severity, a value between 0 and 1; a configured value outside that range is rejected.
  4. A one-shot run returns distinct statuses for scored, not scored for lack of data, and error.

1.5 SONAR does not write security alerts SRS-076

SONAR SHALL NOT write documents to the Wazuh alert indices it analyses. Training and detection SHALL use only alerts produced by the monitored environment.

Rationale

SONAR used to pad sparse history by generating synthetic alerts and indexing them into the live alert indices, then trained on them. That polluted the security record that analysts and other components rely on, and made the model learn fabricated behaviour.

Acceptance criteria

  1. No SONAR command or configuration option writes to the Wazuh alert indices.
  2. Configuration keys of the former synthetic-alert generation are ignored with a warning.

1.6 SONAR delivers each anomalous bucket at most once per scenario SRS-077

SONAR SHALL deliver each anomalous time bucket at most once per scenario to each of its destinations, however many detection runs score that bucket, including across process restarts. Anomalies that a destination did not accept SHALL be offered to it again by a later run, without being sent again to the destinations that accepted them. In realtime mode, a failed detection poll SHALL be retried, and SONAR SHALL stop with an error only after a configurable number of consecutive failed polls.

Rationale

Consecutive detection runs score overlapping windows, so the same anomalous bucket is found many times: a 24-hour window polled every 5 minutes reports each anomaly about 288 times. Duplicates inflate anomaly counts and, once anomalies reach the Wazuh manager, raise the same alert and trigger the same automated response repeatedly. A transient indexer error must not end continuous monitoring, and must not lose anomalies either.

Acceptance criteria

  1. Two detection runs over the same data deliver each anomalous bucket once; restarting SONAR does not deliver it again.
  2. When a run of anomalous buckets extends across two detection runs, the second delivers only the buckets the first did not.
  3. Every anomaly carries an identifier derived from its scenario and bucket, and an index that already holds that identifier is treated as having received it.
  4. When delivery fails, the anomalies are delivered by the next successful run; when one destination fails and another succeeds, the successful one does not receive them again.
  5. In realtime mode, a failed poll followed by a successful one keeps detection running; the configured number of consecutive failures stops it with a non-zero exit code; too little data to score is not a failure.
  6. A bucket is scored only once a configurable delay has passed since it ended, so that alerts indexed late are counted.

1.7 SONAR reports anomalies to the Wazuh manager SRS-078

SONAR SHALL report each anomaly to the Wazuh manager as an event that SONAR's Wazuh rules turn into a Wazuh alert, whether SONAR runs on the manager host or on a dedicated host, without a Wazuh agent on the SONAR host. The event SHALL carry the anomaly's severity and confidence in the fields RADAR reads for anomaly-detection scenarios. SONAR SHALL NOT use its own alerts as training or detection input.

Rationale

Anomaly documents written straight into the indexer bypass the manager: no Wazuh rule, active response or integration fires on them, and RADAR cannot act on them. SONAR may not run on monitored endpoints, which can be resource-constrained, so it reaches the manager either through a file the manager reads (same host) or through the Wazuh server API (another host). SONAR alerts are stored in the alert indices SONAR reads; learning from them would feed SONAR's output back into its input.

Acceptance criteria

  1. On the manager host, an anomaly appended to the file read by the manager's <localfile> (JSON) raises a Wazuh alert from a SONAR rule.
  2. From a host without a Wazuh agent, an anomaly sent to the server API raises the same alert, using an API user that is only allowed to ingest events.
  3. The alert carries data.anomaly_grade, data.anomaly_confidence and the scenario name; its rule reflects the severity band (low, medium, high), whose boundaries are configurable.
  4. SONAR's rules use IDs in 100500–100519 only, and none collides with another rule of the project.
  5. A RADAR scenario that maps a SONAR rule triggers the active response without changes to RADAR's code.
  6. Alert searches exclude SONAR's own alerts unless explicitly configured otherwise.
  7. Delivery to the manager keeps the guarantees of SRS-077.

1.8 SONAR runs as a standalone package with safe, interchangeable models SRS-079

SONAR SHALL find its configuration, models, state and data independently of the directory it is started from. Loading a SONAR model SHALL NOT execute code contained in the model file. The anomaly detector SHALL be selectable per scenario, with the same feature extraction, post-processing and delivery for every detector. SONAR installed as a package SHALL run its example scenarios in debug mode without the source repository.

Rationale

SONAR used to resolve models and debug data against the working directory, so it worked only when started from the repository root, and separate training and detection runs could look for different files. Its model files were Python pickles, which execute code when loaded: anyone able to write a model file could run code as SONAR. Being tied to one detector library, with no baseline to compare it with, makes it impossible to tell whether that library is worth its cost, or to replace it.

Acceptance criteria

  1. A relative path in a configuration or scenario file is relative to that file; unset paths default to a SONAR home directory; the same configuration gives the same locations from any working directory.
  2. Training and detection runs of a scenario use the same model without extra configuration.
  3. Model files contain no pickled objects, and a model in the former pickle format is refused without being opened as a pickle.
  4. A baseline detector without deep learning can be selected instead of MVAD; the MVAD detector gives the same verdicts as before the detector interface was introduced.
  5. From outside the repository, the installed package trains and detects on a packaged example scenario in debug mode and writes anomalies to a local file.

1.9 SONAR detection quality is measured against labelled data SRS-080

SONAR SHALL measure a scenario's detection quality against labelled data, as event-level precision, recall and F1, mean detection delay and false alarms per day, for any of its detectors and for the results of an external detector exported in a supported format. SONAR SHALL calibrate a scenario's severity threshold and minimum run length on a validation split within a false-alarm budget, and report the precision those values give on a separate test split as the scenario's anomaly confidence.

Rationale

Tests that mock the detector cannot show whether SONAR detects anything. Whether MVAD is worth its cost, and whether SONAR adds value over the anomaly detection already bundled with the Wazuh indexer, can only be decided by measuring both on the same labelled data. The confidence SONAR attaches to its alerts, which RADAR uses in its risk score, has to be a measured value rather than a constant.

Acceptance criteria

  1. Given alert files for training, validation and testing and label files listing each event's type and interval, SONAR reports for the test split: precision and recall over alarms and events, F1, mean detection delay and false alarms per day, plus each event's outcome.
  2. Counting can be restricted to the event types a scenario targets; alarms on other labelled events count neither as true nor as false alarms.
  3. Results of the OpenSearch anomaly detection plugin, and generic interval records with a severity, are scored the same way.
  4. Calibration chooses the threshold and minimum run length on the validation split only, and the reported anomaly confidence is the test-split precision with those values.
  5. The data generators produce reproducible labelled splits for the bundled scenarios.
  6. Tests with the real MVAD library detect an injected metric spike, a volume burst, a silence and a never-seen category clearly above the rate at which they flag normal data, and realtime polling over overlapping windows delivers each anomaly once.

1.10 SONAR scores RADAR's resource-utilization data for comparison SRS-081

SONAR SHALL provide a scenario that reads the events and features of RADAR's Linux resource-utilization scenario from a live Wazuh deployment. SONAR SHALL train and run one model per agent on request. SONAR SHALL export a time window of those events, labelled anomaly intervals and the results of RADAR's detector, so that SONAR and RADAR are scored by the same evaluation.

Rationale

RADAR already detects resource-utilization anomalies with the random cut forest of the OpenSearch anomaly detection plugin. Whether SONAR adds value over it can only be decided by running both on the same events and features and scoring both against the same labelled anomalies. RADAR models each host separately, so a fair comparison also needs SONAR models per host.

Acceptance criteria

  1. A packaged scenario reads the events of RADAR's resource-utilization collector from the archives index. It uses RADAR's event filter (without the history RADAR seeds synthetically), RADAR's interval and handling of empty intervals, and the mean and maximum of CPU and memory use per interval.
  2. Given an agent name, training, detection, evaluation and export use only that agent's events, and that agent's model, scenario identifier and event filter are separate from those of other agents and of the fleet-wide model.
  3. Export writes, for a time window: the scenario's events from the context its detector needs before the window to the end of the window; a label file whose span is the window and whose events are the given intervals; and RADAR's detector results for the window and agent. The evaluation reads all three files.
  4. The scenario's decision rule and anomaly confidence are calibrated on labelled data.

See: docs/manual/sonar_docs/radar-comparison-guide.md

1.11 SONAR reads every matching alert through one indexer client SRS-086

As a security analyst, I want SONAR to train and detect on every alert of the requested period, read from the Wazuh indexer with the same connection settings it uses to write, so that a model never learns from an arbitrary subset of the history and a TLS setting that works for one indexer operation works for all of them.

Scope

Alert reads from the Wazuh indexer (OpenSearch REST API) by sonar train, sonar detect, sonar scenario and sonar export, and every other connection SONAR opens to the indexer: the export of RADAR's detector results, the index sink and the datastream sink with its template installation. Implemented in sonar/wazuh_client.py (WazuhIndexerClient) and sonar/indexer.py (build_opensearch_client, tls_options, json_safe); the fields the features read are declared in sonar/features.py (WazuhFeatureBuilder.required_source_fields, DERIVED_FEATURE_FIELDS).

Out of scope: debug mode (--debug), which reads local files through sonar/local_data_provider.py (SWD-025), and the Wazuh server API used by the wazuh sink, which is a different service with its own client (sonar/sinks/wazuh.py).

The indexer user needs read access to the alert indices and permission to create and delete a point-in-time. See: docs/manual/sonar_docs/setup-guide.md#alert-ingestion

Requirements

  1. Complete read. An alert search SHALL return every alert of wazuh.alerts_index_pattern whose timestamp lies in [start, end) and that matches the scenario's alert_filter, each exactly once, in ascending timestamp order. SONAR SHALL page through a point-in-time with search_after, sorted on timestamp and then on the alert's id, and SHALL close the point-in-time after the search, also when a page fails.
  2. Bounded result, newest kept. One search SHALL return at most wazuh.max_alerts alerts (default 2,000,000). When more alerts match, SONAR SHALL keep the most recent ones and log a warning with the number of matches.
  3. Declared fields only. Training and detection SHALL request only the alert fields the feature configuration reads: timestamp, the numeric, maximum and categorical fields, and the fields each enabled derived feature declares. Every derived feature SHALL declare every field its condition reads.
  4. Own alerts excluded. Alerts in any rule group listed in wazuh.exclude_rule_groups (default ["sonar"]) SHALL NOT be returned, so SONAR does not read the alerts raised from its own anomalies (SRS-078, criterion 6). An empty list SHALL disable the exclusion.
  5. One client configuration. Every SONAR connection to the indexer SHALL be built from the wazuh: settings by one factory: base URL, basic authentication, request timeout (wazuh.timeout_seconds, default 30 s) and TLS. wazuh.verify_ssl SHALL accept false (no certificate check), true (system trust store) or the path of a CA bundle, with the same effect on reading alerts and on writing anomalies.
  6. JSON-safe writes. Documents written to the indexer SHALL be serialised so that timestamps and numeric types are valid JSON and NaN or infinite values become null.
  7. Failures are reported. A failed indexer request SHALL end the read with an error rather than return a partial result as complete.

Rationale

A single unsorted search page returns an arbitrary subset of at most 10,000 alerts, so long training lookbacks were silently truncated and models learnt from whichever alerts the indexer happened to return. Sorting newest first makes a capped result lose the oldest history rather than the detection window. Fetching whole alerts wastes memory and bandwidth on fields no feature reads; a derived feature whose fields are not declared would see them as missing against a live indexer while passing in debug mode, where local data is never filtered. Before the shared factory, a CA bundle in verify_ssl worked for alert search but not for shipping, which then fell back to the plain anomalies index against any indexer with a self-signed certificate.

Acceptance criteria

  1. A search over more alerts than one page, with several alerts per timestamp, returns every alert once, oldest first, in pages of at most 10,000, and closes the point-in-time; the point-in-time is also closed when a page fails, and the error is raised.
  2. The query has a timestamp range with gte start and lt end, the alert_filter as must (none without a filter), the sort on timestamp and id, and counts the matches on the first page only.
  3. With max_alerts below the number of matches, the result holds max_alerts alerts including the newest one, and a warning names the number of matches and max_alerts.
  4. Training and detection request exactly the fields the feature configuration declares; each derived feature gives the same result on an alert reduced to its declared fields as on the full alert.
  5. By default the query excludes the sonar rule group, which is the group of SONAR's Wazuh rules; with exclude_rule_groups: [] nothing is excluded.
  6. The alert search client and the data stream shipper are built with the same URL, credentials, timeout and TLS arguments, including a CA bundle path.
  7. Documents written to the indexer have NaN and infinite values replaced by null, and timestamps and numpy values converted to JSON values.

Verified by TST-087.

1.12 SONAR container image contains only SONAR SRS-087

As an operator, I want to run SONAR as a standalone container that holds SONAR and its runtime dependencies only, so that deploying it never ships credentials or other subsystems and its models and outputs stay on the host.

Scope

The SONAR image built from sonar/Dockerfile.sonar with the repository root as build context (docker build -f sonar/Dockerfile.sonar -t sonar:v0.8 ., also run by build.sh sonar), its build-context rules in sonar/Dockerfile.sonar.dockerignore, and the two ways the repository runs it: sonar/sonar.sh and the compose overlay sonar/wazuh/docker-compose.sonar.yml. The dependency groups are declared in pyproject.toml.

The per-Dockerfile ignore file is read by BuildKit, the default builder since Docker 23. The legacy builder reads the root .dockerignore, which the ADBox images share. See: docs/manual/sonar_docs/setup-guide.md#docker-deployment

Requirements

  1. Content. The image SHALL contain, under /home/alab/soar, only pyproject.toml, poetry.lock, README.md, the sonar/ package (code, default configuration, example scenarios, debug datasets and the Wazuh rule and integration files) and ADBox's package file adbox/__init__.py, which the project's package declaration requires to exist (it is not importable without the rest of ADBox; SONAR never imports it). It SHALL contain no other ADBox file and no RADAR file. The Dockerfile SHALL copy these paths explicitly and never the whole build context.
  2. No secrets or local state. Built with BuildKit, the build context SHALL be an allowlist of the paths above, and SHALL exclude, also inside sonar/: every .env file, every pickled file (*.pkl), the payload directory sonar/payloads, the delivery watermarks sonar/models/state, and Python caches. adbox/assets/secrets SHALL NOT be in the image with any builder.
  3. Dependencies. The image SHALL install only the main and sonar Poetry dependency groups, which together declare everything SONAR imports, and none of the adbox, radar, test, docs or plot groups. It SHALL be based on Python 3.10.12.
  4. Process. SONAR SHALL run as the unprivileged user alab, in /home/alab/soar, with the sonar console script as entry point and --help as default command, so that arguments given to the container are SONAR's command line.
  5. State on the host. sonar/sonar.sh SHALL mount the host's sonar/models, sonar/test_data, sonar/scenarios and sonar/default_config.yaml over their places in the image, and the directory $SONAR_ANOMALIES_DIR (default /srv/sonar/anomalies) at /var/log/sonar, where the wazuh sink's file transport writes for the Wazuh manager to read. The compose overlay SHALL mount the same model, scenario, configuration and anomaly directories.

Model directories present in sonar/models/ of the build context are copied into the image (only pickles and state/ are excluded); the mount of sonar/sonar.sh hides them at run time.

Rationale

The ADBox images need adbox/assets/secrets, which the shared root .dockerignore therefore lets through. A SONAR image built with COPY . would bake those secrets and any .env file into an image meant for distribution. ADBox's dependencies, including a git-hosted package, would enlarge the image and require git at build time for code SONAR never imports. A delivery watermark baked into the image would make a fresh container believe anomalies had already been delivered and suppress them. Keeping models, scenarios, configuration and anomaly files on the host lets a container be replaced without retraining or losing state, as a standalone process would (MRS-041).

Acceptance criteria

2.2 RADAR: Tiered active response logic SRS-061

As a security engineer, I want RADAR to apply a consistent, risk-scored tiered response framework across all detection scenarios, with integrated DECIPHER case creation, so that the SOC receives proportionate, auditable, and actionable responses for every alert.

Scope

Risk score input: The tier classification is driven by the unified risk score $R \in [0, 1]$ computed by the RADAR risk engine per the formula $R = w_{ad} \times A + w_{sig} \times S + w_{cti} \times T$. The risk engine and its fusion step are specified in SWD-026 and implemented in radar/scenarios/active_responses/radar_ar.py; the per-scenario values are set in radar/scenarios/active_responses/ar.yaml. See: docs/manual/radar_docs/radar-tuning.md

Tier boundaries: Boundaries are set per scenario in ar.yaml. A scenario that leaves them unset uses the built-in defaults 0.0 / 0.33 / 0.66; values are not inherited from the default scenario.

DECIPHER integration: Case creation is performed via the DECIPHER subsystem of SATRAP-DL, which creates and manages cases in FlowIntel. Availability of DECIPHER is checked at runtime; its unavailability does not interrupt risk calculation or other response actions.

Requirements

  1. RADAR shall classify every active response execution into exactly one response tier based on the computed risk score R:

  • (i) Tier 0 - Logging only (risk score below the configured Tier 1 minimum, where applicable): RADAR logs the event and risk computation to the audit log. No email notification is performed. Tier 0 is implemented as a minimum value of Tier 1. To explicitly enable Tier 0 suppression of Tier 1 actions, the tier1_min parameter must be set to a value greater than 0 in ar.yaml.

  • (ii) Tier 1 - Low risk (tier1_min ≤ R < tier1_max, default 0.0–0.33): RADAR sends an email notification to the configured SOC recipient, creates a Flowintel case (requirement 5) and records the decision in the audit log.

  • (iii) Tier 2 - Medium risk (tier1_max ≤ R < tier2_max, default range 0.33–0.66): RADAR executes all Tier 1 actions, and the scenario's mitigations_tier2 if allow_mitigation is true in ar.yaml.

  • (iv) Tier 3 - High risk (R ≥ tier2_max, default tier2_max = 0.66): RADAR executes all Tier 1 actions, and the scenario's mitigations_tier3 if allow_mitigation is true, subject to the mitigation safety gates of SWD-027 (target taken from the triggering alert only, never_block addresses, protected users, service allowlists, scenario allowlist).

  • (v) Mitigation identifiers: the only mitigations are firewall-drop, lock_user_linux.sh and terminate_service.sh. Any other identifier configured for a scenario shall be refused and logged (unsupported_mitigation). When allow_mitigation is false, or the tier has no mitigations, the planned actions shall be logged with a withheld_reason instead.

  1. Tier boundaries shall be configurable in ar.yaml without code changes:
  • (i) Each scenario defines its boundaries under its own tiers: key:
tiers:
    tier1_min: 0.0    # Lower bound for Tier 1; set > 0 to enable Tier 0 suppression
    tier1_max: 0.33   # Upper bound of Tier 1 (low risk)
    tier2_max: 0.66   # Upper bound of Tier 2 (medium risk)
  • (ii) Tier boundaries are expected to satisfy 0.0 ≤ tier1_min ≤ tier1_max ≤ tier2_max ≤ 1.0. Out-of-order or out-of-range values shall be normalised rather than rejected: a negative tier1_min becomes 0, a boundary below the previous one is raised to it, and a boundary above 1 becomes 1. Equal boundaries leave the tier between them empty.
  1. RADAR shall match incoming Wazuh alerts to active response scenarios using the rule mapping declared in radar/scenarios/active_responses/ar.yaml:
  • (i) Each scenario may define rule_ids for exact alert.rule.id matching and rule_groups for membership overlap against alert.rule.groups.
  • (ii) Exact rule_ids shall take precedence over rule_groups when an alert matches both.
  • (iii) If an alert matches multiple scenarios by rule_groups only, the first matching scenario listed in ar.yaml shall be selected and the ambiguity shall be logged for audit.
  • (iv) If no scenario matches by rule_ids or rule_groups, the active response execution shall log a warning and exit without taking further action.
  • (v) An alert matched as an anomaly alert (ad.rule_ids) shall be acted on only if it was read by the webhook agent from the anomaly alert log; any other such alert shall be logged and dropped without scoring or action.
  1. RADAR shall integrate with the DECIPHER subsystem of SATRAP-DL:

  • (i): Before making use of DECIPHER endpoints (e.g. to obtain a CTI score or create an incident case), RADAR shall first query the DECIPHER health endpoint. If DECIPHER is unavailable (connection refused, timeout, or non-2xx response), RADAR shall log a WARNING and proceed with all other risk-aware tiered response actions (email, mitigations, audit logging) without interruption. DECIPHER API invocation shall not be retried within the same active response execution.

  • (ii): When DECIPHER is available, RADAR shall submit a CTI analysis request to DECIPHER.

  • (iii): A successful DECIPHER response will return a CTI score $T$.

  • (iv): The call to the analysis endpoint of the DECIPHER API shall provide a dictionary of specific fields, specified per scenario.

  • (v): If DECIPHER returns an error response (4xx or 5xx), RADAR shall log the error with full response detail and continue with the remaining response actions. The execution result record shall reflect the DECIPHER execution status.

  1. For Tier 1 and above, RADAR shall send an email notification to the configured SOC recipient and create a Flowintel case via the incident endpoint of the DECIPHER API:

  • (i) RADAR invokes the incident endpoint of the DECIPHER API to create a case. The case is populated by DECIPHER with CTI analysis results and assigned a priority tag. The priority tag reflects the tier determined by RADAR (based on its computed risk score) and it is intended for use by security analysts for triage within the FlowIntel interface.

  • (ii) The case submitted to DECIPHER shall include at minimum: RADAR scenario name, triggering agent name and ID, alert timestamp, risk score, tier classification, decision ID, title of case origin and the list of extracted IOCs.

  • (iii) The email body content shall include: scenario name and detection type, the triggering rule and agent, risk score and tier classification, risk component breakdown (anomaly, signature, CTI components), the CTI labels, the context window and extracted IOCs (including user names), scenario-specific details, and the decision ID. Moreover, the email body shall include the FlowIntel case ID and URL link returned by DECIPHER in response to the incident API call, enabling the analyst to navigate directly to the case. Both the case ID and the link shall be: - Included in the email body sent to the SOC - Recorded in the active response log for the execution

  • (iv) If DECIPHER returns an error response (4xx or 5xx), RADAR shall log the error with full response detail and continue with the remaining response actions. The execution result record shall reflect the DECIPHER execution status.

  • (v) If the SMTP configuration is incomplete or the email send fails, the failure shall be logged as ERROR and the remaining response actions shall continue unaffected.

  1. RADAR shall generate a unique decision ID for every active response execution and maintain a complete audit record:

  • (i) The decision ID is computed as SHA256(JSON.dumps({alert_id, timestamp, rule_id, agent_id, scenario, detection, window, effective_agent}, sort_keys=True)), ensuring idempotency and deduplication.

  • (ii) The audit record shall capture: decision ID, tier classification, risk score and all components, planned and executed actions, DECIPHER case ID and link (if created), mitigation outcomes, and any errors encountered.

  • (iii) Audit records shall be written to /var/ossec/logs/active-responses.log. For a scenario that sets allowlist_file in ar.yaml, each action outcome (executed, declined with its reason, or nothing planned) shall additionally be written as one JSON entry in the format of native Wazuh active responses, so that Wazuh decodes it with its shipped rule 650.

  1. RADAR shall be able to combine, per scenario, the signature-based and the anomaly-based evidence about the same entity over time:

  • (i) Combination is enabled per scenario in ar.yaml. It applies only to a scenario that has both anomaly and signature rules and non-zero w_ad and w_sig.

  • (ii) For each alert, RADAR shall look back, within a configured time window, for alerts of the other detection type on the same entity (a configured field on each side), and use the strongest one, discounted by the time between the two, for the risk component the alert does not carry itself.

  • (iii) RADAR shall not delay a decision to wait for a counterpart alert. The absence of a counterpart, or a failure to look one up, shall leave the risk score equal to the score of the alert on its own.

  • (iv) Only anomaly alerts written by the anomaly-detection webhook shall count as anomaly evidence.

  • (v) A counterpart alert shall contribute to the risk score only. Mitigation targets shall come from the alert being decided, as without combination.

  • (vi) The audit record, the email and the case shall identify the counterpart alert used.

Rationale

Automated response to security events must be proportionate to the assessed risk: acting aggressively on low-confidence signals wastes analyst time, disrupts legitimate users, and erodes trust in the system; acting conservatively on high-confidence signals leaves threats uncontained.

A tiered framework directly addresses this by mapping the continuous risk score R onto a discrete set of escalating response actions, each calibrated to the level of certainty and urgency warranted. Tier 0 preserves observability for events that are detected but do not yet meet the confidence threshold for operational action. Tier 1 ensures that no qualifying event goes unnoticed by the SOC. Tier 2 allows medium containment actions. Tier 3 authorizes automated containment actions (account lock, firewall block, service termination) only when the risk score provides sufficient confidence to justify the operational impact of those actions.

The use of a configurable risk score threshold, adjustable tier boundaries, and a per-scenario allow_mitigation flag means the framework can be tuned conservatively during initial deployment and progressively hardened as operational baselines and false-positive rates are understood. This avoids the binary choice between fully manual and fully automated response, instead providing a graduated path toward automation that the SOC can control and audit at each step.

Each alert carries only one kind of detection evidence, so without combination the anomaly and signature weights can never both contribute, and the highest tiers of a hybrid scenario are out of reach. The two kinds of alert do not arrive together: anomaly alerts lag the data they describe by the detector and monitor intervals, and either may never come. Combination therefore looks back instead of waiting, treats a missing counterpart as no evidence rather than evidence against (an attacker who keeps the detector quiet must not also lower the signature-driven score), and never lets the counterpart choose what to block or lock.

Acceptance criteria

Successful validation according to test case specification, which shall verify:

  1. Tier classification correctness: For each tier boundary, inject a synthetic alert with a risk score at and around the boundary value and verify that the correct tier is assigned and the correct actions are executed.

  2. Tier 0 / Tier 1 minimum behavior: With default configuration (tier1_min = 0), verify that no event is suppressed to Tier 0 - all events receive at minimum Tier 1 (email) treatment. With tier1_min > 0, verify that events below the minimum receive logging-only treatment.

  3. DECIPHER health check - available: With DECIPHER running, trigger a Tier 2 alert and verify: health check passes, case is created, a FlowIntel case ID and link are returned, the link appears in the email body, and both are recorded in the audit log.

  4. DECIPHER health check - unavailable: With DECIPHER unreachable, continue with risk calculation: health check fails with WARNING log, email notification is still sent, mitigations (if configured) are still executed, and the active response exits with success code.

  5. Audit log completeness: For every tier test, verify that the audit log entry contains the decision ID, tier, risk score and all components, action outcomes, DECIPHER case ID/link (where applicable), and any errors.

  6. Combination in both orders: with combination enabled, an anomaly alert for user U followed within the window by a signature alert for U gives the signature alert a higher risk score than it has alone, and its decision names the anomaly alert; the same holds with the signature alert first.

  7. No counterpart: an alert with no counterpart in the window, or only a counterpart for another entity, gets exactly its single-alert risk score.

  8. Targets: a combined decision on an anomaly alert dispatches no firewall-drop and no lock_user_linux.sh; a combined decision on a signature alert targets only that alert's source IP and user.

  • Abnormality criteria: repeated connections to the same external destination at near-regular intervals, where interval regularity and frequency exceed the host’s learned baseline and the anomaly score is above a configured threshold.
  • Per-host model: each endpoint shall have an independent behavioral baseline to distinguish beaconing from legitimate scheduled outbound activity (e.g., NTP, telemetry agents).

  1. Alert content: The alert shall include sufficient context for triage and response:
  • Host identity (agent.name) and user context where available
  • Detector name/ID, anomaly score, and confidence value
  • Timestamp and analysis window covering the beaconing activity
  • Destination IP/domain, observed interval regularity, and connection count
  1. Risk-threshold evaluation: The anomaly monitor shall notify the RADAR webhook when the anomaly grade and confidence exceed the scenario's thresholds, and the resulting Wazuh alert shall be scored by the RADAR active response (SRS-061):
  • Risk scoring shall use the RADAR risk score $R = w_{ad} \cdot A + w_{sig} \cdot S + w_{cti} \cdot T$ (SRS-061), with $A$ the anomaly grade times confidence and the weights set in the scenario's ar.yaml block.
  • Detector thresholds (config.yaml) and tier boundaries (ar.yaml) shall be adjustable without code changes.
  1. Automated response: When the risk threshold is passed, RADAR shall execute the configured containment active responses:
  • Firewall block: outbound connections to the identified destination IP/range shall be blocked via Wazuh active response.
  • Service termination: the process responsible for the beaconing connection shall be terminated on the affected host where process attribution is available.
  • Host quarantine: the affected host shall be network-isolated to prevent further C2 communication and lateral movement.
  • Below-threshold handling: if the computed risk score is below the threshold, the alert shall be logged to the index without triggering containment actions.
  1. Audit trail: All detection events, alerts, active responses, and their outcomes shall be logged to the Wazuh indexer with complete audit trails for compliance and forensic analysis.

2.12 RADAR scenario simulation framework SRS-059

As a security engineer, I want scenario simulations that produce realistic attack artefacts on a monitored endpoint, so that RADAR detection scenarios can be exercised end to end and reproducibly through the real pipeline, without injecting synthetic alerts or documents.

Scope

Framework coverage: This requirement applies to the simulation phase of the RADAR test workflow (SRS-054) for the RADAR detection scenarios: suspicious_login (signature side, and anomaly side for fusion tests), geoip_detection, log_volume, scanning_detection and linux_resource_utilization.

Execution environment: Simulations run on a Linux endpoint that is enrolled with a running RADAR deployment and assigned to the scenario's agent groups. Artefacts are written on the endpoint and reach the manager through the Wazuh agent, so decoders, rules, manager-side enrichment, the anomaly detector where the scenario has one, the risk engine and the active responses are all exercised. The one exception is the anomaly-side injection for suspicious_login, which runs on the RADAR host and posts an alert to the webhook as the detector's monitor would, because the real detector needs days of baseline before it fires.

Distribution model: Each simulation is a standalone script copied to the endpoint and run there. There is no central dispatcher, remote execution or inventory.

Requirements

  1. One script per scenario: Each scenario shall have its own simulation script under radar/radar-test-framework/simulate/scenarios/ that runs on the endpoint with no companion files. The Python scripts shall use only the Python 3 standard library. The linux_resource_utilization script is a Bash script that needs stress-ng for its load modes.

  2. Agent-realistic artefacts: Each script shall produce the artefact its scenario actually detects: - suspicious_login: SSH authentication lines appended to the configured authentication log. - geoip_detection: SSH authentication lines and web access-log lines from whitelisted, non-whitelisted and private source addresses. - scanning_detection: Suricata eve.json HTTP and alert records. - log_volume: real filesystem growth in a monitored directory. - linux_resource_utilization: real CPU and/or memory load held for a configured duration, or, in an inject mode, metric lines in the collector's log format.

  3. Named cases with expected outcomes: The suspicious_login, geoip_detection and scanning_detection scripts shall be organised as named cases that cover both alerting and non-alerting behaviour. Each case shall print the rule IDs expected to be present and absent. Running a script without arguments shall run every case. Running it with case names shall run only those cases, and an unknown case name shall be rejected before anything is written.

  4. Operator verification: The case-based scripts shall by default pause after each case until the operator confirms having checked the dashboard, and shall print a per-case summary at the end. A batch flag (-b) shall run all requested cases unattended.

  5. Configurable behaviour: Each script's tunable parameters (target host name, log paths, source addresses, users, thresholds, timing, sizes, duration) shall be grouped at the top of the script, so the script can be adapted to an environment without changing its logic.

  6. Bounded side effects: - log_volume shall cap per-step and total growth (max_step_bytes, max_total_bytes) and shall remove its spike file after cleanup_minutes through a detached background process; cleanup_minutes: 0 disables the removal. - linux_resource_utilization shall release the load when it exits, including on interruption, and shall keep a configurable amount of memory available. - Log lines appended by the other scripts are not removed; they stay in the target logs.

  7. Failure reporting: Each endpoint script shall exit with a non-zero status and a one-line ERROR: message on failure, and shall offer RATF_DEBUG=1 to show the full traceback (or, for the Bash script, a command trace).

  8. Anomaly-side injection for fusion tests: A script run on the RADAR host shall post one off-hours anomaly for a chosen user to the webhook, authenticated with the webhook's shared secret, in the same body format the monitor sends, so that signature and anomaly fusion (SRS-061) can be tested without a trained baseline.

Rationale

Direct log injection and synthetic OpenSearch documents bypass decoders, rules, enrichment, the webhook bridge and the active-response chain, so they cannot validate the detection stack. Producing the real artefact on the endpoint exercises every component that is exercised in production. Standalone scripts need nothing on the endpoint beyond an interpreter, which matches how endpoints are onboarded (SRS-067). Named cases with printed expectations make a run checkable against the dashboard without separate documentation.

Acceptance criteria

Successful validation according to the corresponding test case specifications. For each scenario, running its script on an enrolled endpoint with a default configuration must produce the expected alerts and no others:

  • suspicious_login: burst raises 210013, failed_travel 210020, travel 210021, composite 210022, and benign raises none of them.
  • geoip_detection: ssh_non_whitelisted raises 100900, the non-whitelisted web cases raise 100902, and the whitelisted and private-address cases raise neither.
  • scanning_detection: each case raises exactly the rules it prints as expected (100810, 100815, 100820/100821, 100825, 100830), and the legit, excluded-method, WebDAV and split-source cases do not raise 100830.
  • log_volume: the monitored directory grows enough for the anomaly detector to report an anomaly and rule 100309 to fire, and the spike file is removed after cleanup_minutes.
  • linux_resource_utilization: CPU load mode leads the detector to report an anomaly and rule 100321 to fire, and the load stops when the script ends.
  • Anomaly injection: the webhook accepts the alert and rule 210040 fires for the injected user.

2.13 RADAR deployment health check SRS-060

As a security engineer or operator, I want a single-command tool that verifies the completeness and operational readiness of a RADAR deployment, so that misconfiguration, missing artifacts, or broken connectivity can be identified quickly after deployment or after infrastructure changes, without manually inspecting each component.

Scope

Tool coverage: This requirement applies to RADAR deployments whose Wazuh manager node(s) run as Docker containers on the RADAR host and are registered in radar/infra.yaml, across all scenarios listed in radar/config.yaml. It covers every registered manager node, the indexer and webhook as seen from the manager side, and, when named agents are supplied, those agents' status as reported by the Wazuh management API.

Invocation: The health check shall be executable through a single entry-point script (health-radar.sh, also radar.sh health and the GUI's Status tab) that runs a manager-side check (container and file presence, reachability from inside the containers), a manager-side API check (Wazuh management API, OpenSearch, and the alert webhook, all over HTTP), and, only if named agents are supplied, an agent check via the Wazuh management API.

Output: Check results shall be printed as each section completes: manager checks, then manager API checks, then (if requested) named-agent checks. Each check line is marked OK, WARN, FAIL or, for a reachability check whose source container is not running, SKIP.

Scope exclusions: The health check is a validation tool. It shall not change the deployment's configuration, restart services, or remediate detected issues, with the single exception stated in requirement 4.

Requirements

  1. Single entry point: A single script shall be the sole invocation interface:

    • Accept a --scenario <name|all> argument and an optional --agent-name <name1,name2,...> argument. Manager nodes are always addressed through their containers and the Wazuh management API, never over SSH.
    • Run the manager checks, then the manager API checks, and, only if agent names are supplied, the named-agent checks.
    • Return a non-zero exit code if any underlying check fails to run.

  2. Manager checks: Executed against each registered manager node's container, these shall verify:

    • Container health: the manager container and the alert-webhook container are running.
    • Key file presence and ownership: the active-response script, its configuration, and its environment file are present with the correct group ownership, along with the manager's core configuration files (a missing configuration file of the baseline agent group is reported as a warning, not a failure). Scenario-specific checks shall be verified as well:
      • For suspicious_login or geoip_detection: the manager's Python runtime and GeoIP library are available.
      • For suspicious_login: the manager-side enrichment files and GeoIP reference databases are present, the per-user enrichment state store exists and is writable (a store not yet created is a warning), and the enrichment error log is empty or absent.
      • For log_volume: the log-ingestion pipeline has the routing update it needs for log-volume metrics.
    • Reachability: OpenSearch, and DECIPHER when it is configured, are reachable from inside the manager container; for log_volume and linux_resource_utilization, the configured webhook endpoint is reachable from inside the indexer container.

    Separately, a check against the Wazuh management API shall verify: - Core daemon status: the manager's core processes are reported running, per cluster node when the manager runs as a cluster. - Active-response wiring and scenario group configuration: for each target scenario, the corresponding ossec.conf active-response block and agent-group configuration are present. - Ruleset files: the decoder and rule files each target scenario depends on are present; for geoip_detection, the country whitelist is additionally checked. - Scenario agent state: the agents assigned to all of each target scenario's group(s) and their connection status are reported; no such agent is a failure. - Connectivity: OpenSearch is reachable and its cluster health status is reported; for log_volume, the OpenSearch index template is additionally checked; the configured webhook endpoint responds (an unreachable webhook is a warning).

  3. Agent checks: When agent names are supplied, a check against the Wazuh management API shall verify, with no direct connection made to the agent endpoint itself:

    • The named agent is registered and its connection status is active (a status of "never connected" is reported as a failure).
    • The agent's group membership includes the baseline group and, unless all scenarios were requested, the named scenario's group.

  4. Non-destructive execution: No check defined by this requirement shall write to or modify any configuration file, ruleset, group or agent on the manager or on any agent. The single exception: before checking, the tool revokes an enrollment token whose expiry has passed but which is still active (which restarts the manager), so that an expired token never stays usable.

  5. Ordered output: The tool shall print the manager section, then the manager API section, then (if requested) the agent section, each clearly labelled, so the full result is visible as a single, ordered output.

  6. Scenario filtering: When a specific scenario is named, scenario-specific checks (ruleset file presence, log_volume pipeline/index-template checks, geoip_detection whitelist check, enrichment checks, expected agent group membership) shall be scoped to that scenario only. When all scenarios are requested, checks shall cover every scenario listed in radar/config.yaml.

Rationale

Manual post-deployment verification of a RADAR stack requires inspecting container state, file presence and permissions, Python environments, and scenario-specific artifacts across multiple nodes. Without automation this is error-prone and time-consuming, and failures are typically discovered only when an alert fails to trigger rather than at deployment time. A single-command health check that surfaces all misconfiguration after deployment reduces mean time to operational readiness and provides a repeatable baseline for regression testing after infrastructure changes.

Acceptance criteria

A complete health check run against a correctly deployed RADAR stack with at least one agent in the scenario's groups must complete without any FAIL, covering manager checks, manager API/OpenSearch/webhook checks, and (when requested) agent checks, using only the health check tool's --scenario and --agent-name options.

  • The manager section, the manager API section, and (if requested) the agent section shall each print in full and in order; no section shall be silently skipped or interleaved with another.
  • Against a deployment where a scenario's ruleset files, group configuration or active-response block are missing, the corresponding checks shall report FAIL.

2.14 RADAR scenario: off-hours activity detection SRS-062

As a security engineer, I want RADAR to report user activity outside each user's declared working hours, judged strictly for staff with fixed hours and against a learned baseline for administrators who sometimes work late, and to score it with the existing risk policy together with the user's signature alerts.

Scope

  • Events: every archived Wazuh event that names a user, from agents (through Filebeat) and from RADAR's own writers (synthetic history). Real events name the user in data.srcuser or data.dstuser; the fields are configurable.
  • Users: only users assigned to a schedule group, unless a default group is configured. Listed exceptions (service accounts, root) are never evaluated.
  • Working hours: declared per schedule group as a time zone, the weekdays on which a shift starts, and a start and end time. A shift may cross midnight.
  • Out of scope: holidays, leave and approved overtime; user names containing @; events indexed later than the configured delay.

Requirements

  1. Declared schedules. RADAR shall read schedule groups, user assignments and settings from one block of the RADAR configuration (scenarios.suspicious_login.off_hours). Each group shall choose one of two modes, rule or model. Validation shall reject the whole block, listing every problem, when it contains: - an unknown time zone; - an unquoted or impossible time; - equal start and end; - a weekday outside 1–7; - an unknown mode or group; - a user assigned twice or also excepted; - an unknown key.
  2. Marking. Every archived event of an evaluated user shall carry the normalised user name, the user's schedule group and an off-hours flag (1 outside the group's working hours in its time zone, otherwise 0). The part of a shift after midnight shall belong to the day the shift started. Summer time shall follow the time zone. An event whose time cannot be read shall be indexed with an error marker, not dropped, and no event shall be lost because the marking is unavailable.
  3. Marking history. Deployment shall mark the archived events of a configurable number of past days (default 45) that carry no flag yet.
  4. Rule mode. For users in rule-mode groups, RADAR shall alert at the start of each off-hours burst: when a user has at least a configured number of off-hours events in the current interval and none in a configured quiet period before it. One burst shall give one alert, and activity after the quiet period shall give a new one. The alert shall name the user, the schedule group, the number of events, and the first and last event time. It shall need no training.
  5. Model mode. For users in model-mode groups, RADAR shall learn each user's usual number of off-hours events per interval, and alert when a count is anomalous for that user and at least a configured minimum. Intervals without events shall not count as zero. Users in rule-mode groups shall not enter the model.
  6. Response. Both alerts shall reach Wazuh through the RADAR anomaly path (webhook, opensearch_ad decoder) as distinct rules, and radar_ar.py shall score them as the scenario's anomaly side and combine them with the same user's signature alerts by fusion. Rule-mode alerts shall carry a configured fixed grade and confidence.
  7. Replacing the previous detectors. Redeploying the scenario shall stop the previous time-of-day detectors and disable their monitors, without deleting them. Changing the configuration and redeploying shall update the marking, the monitors and the detector in place, leaving one of each.
  8. Other scenarios unaffected. Shared parts (the archives pipeline, the webhook, the opensearch_ad decoder) shall change only by addition, so that lines and events of other scenarios are processed as before.

See: docs/manual/radar_docs/radar-scenarios/off-hours-activity.md

Rationale

Stolen credentials are often used outside the victim's working hours. The previous detector learned each user's average login time, which one night-time login among a day of normal work barely moves, and it missed the reference event (bob, 2026-09-18 02:05 UTC). Staff with fixed hours normally have no off-hours activity at all: a declared schedule states this exactly and alerts from the first event. Administrators and on-call staff do work late, so for them only an unusual amount of off-hours activity is suspicious, which a per-user model of the count captures. Counting rather than averaging keeps on-shift events from diluting off-hours ones. Decision record: DEC-2026-11-21-radar-off-hours-declared-schedules.

Dependencies

  • OpenSearch with the Anomaly Detection and Alerting plugins (verified on 2.19.3, Wazuh 4.14.1).
  • The RADAR webhook and the opensearch_ad decoder.
  • radar_ar.py and its fusion of signature and anomaly alerts.

Related requirements

  • SRS-051: Suspicious login detection (the signature side combined with these alerts).
  • SRS-061: Fusion of signature and anomaly alerts.

Acceptance criteria

  1. The shared case table (the 18 cases of the specification plus the cases found on live data) gives the expected flag, group and user in the Python implementation and through the deployed pipeline (_simulate).
  2. Validation rejects each invalid input of requirement 1 with a message naming it.
  3. Events from Filebeat and events written directly are both marked; the number of indexed events is the same with and without marking.
  4. Rule mode on a live cluster: - a user always off hours is reported once with count 1; - a user always on hours is not reported; - three more events in the next interval give no second report; - an event after the quiet period is reported again; - the reference event for bob is reported with count 1.
  5. Model mode on the synthetic history: the 30-event burst of the administrator trent gets an anomaly grade above 0. The number of anomalies on his ordinary evenings is reported (target 0). Rule-mode users have no results.
  6. Deploying twice leaves one pipeline, one template, one monitor per mode and one detector, and the previous detectors stopped with their monitors disabled.
  7. No file on an endpoint and no agent configuration is changed.

2.15 RADAR SOAR web interface: REST API SRS-063

Scope

API coverage: This requirement defines the REST API that backs the RADAR web interface (radar/gui/app.py). It covers six groups of endpoints under /api/: scenario configuration (list, detail, active-response settings, bind/unbind, deployment status), connector configuration (external service settings, secret reveal and connection tests), infrastructure registration (dashboard, manager and indexer nodes, reachability tests), the sudo credential session, logout, and deployment actions (scenario deploy/undeploy, anomaly detector, agent onboarding and lifecycle, enrollment window, health checks, teardown, preview).

Requirements

Access control

  1. Every request shall be refused unless its Host header names an allowed host (the loopback names on the GUI port, the configured bind address, and any host listed in RADAR_GUI_ALLOWED_HOSTS).
  2. Unless authentication is explicitly disabled (RADAR_GUI_AUTH=off), every request shall be refused unless it carries the login token generated at server start (or set in RADAR_GUI_TOKEN). Opening the login URL with the token sets an HttpOnly, SameSite=Strict cookie that authenticates later requests.
  3. State-changing requests (POST, PUT, PATCH, DELETE) shall be refused unless they are sent as JSON and are not cross-site or cross-origin.
  4. A logout endpoint shall stop the GUI's running jobs, clear every stored sudo credential, clear the cookies, and shut the server down.

Scenario endpoints

  1. A scenario list endpoint shall return every scenario the interface is allowed to show (gui_visible in radar/config.yaml), each with an identifier, display name, description, status, detection type (signature, anomaly, hybrid, derived from the scenario's risk weights), and its rule IDs, plus whether it is currently bound and whether it is a shared scenario. For each bound scenario, its active-response configuration shall be included inline.

  2. A scenario detail endpoint shall return the same record for a single named scenario, or a not-found error if the scenario does not exist. The baseline default scenario shall be returned as always bound.

  3. An active-response configuration endpoint shall support reading a scenario's active-response configuration on its own, and separately updating it. An update shall accept a partial set of fields and merge them into the existing configuration; it shall not require the caller to resend the full configuration. Mitigation names not listed in the active-response catalog (radar/radar-agent/ar-scripts.yaml, plus the built-in firewall-drop) shall be rejected.

  4. Bind and unbind endpoints shall add a scenario's active-response block to, or remove it from, ar.yaml. The default scenario and scenarios with status demo cannot be bound or unbound.

  5. A deployment-status endpoint shall report, for each scenario, whether it is recorded as deployed.

Connector endpoints

  1. A connector list endpoint shall return the current value of every connector field except secret-bearing fields, plus, for each secret-bearing field, whether a value is currently set.

  2. A per-connector save endpoint shall accept and persist a connector's fields. Changing an endpoint address that receives a stored secret (for example the OpenSearch or Wazuh API URL) without supplying a new secret in the same request shall require an unlocked sudo credential.

  3. A reveal endpoint shall return the current value of a single secret-bearing field, restricted to a fixed set of fields, and only while the caller's sudo credential is unlocked.

  4. A per-connector test endpoint shall attempt a live connection check for the named connector using its currently saved fields, and report whether it succeeded.

Infrastructure endpoints

  1. Endpoints shall read, create, update and delete the dashboard registration and the manager and indexer node registrations (container name, host, port, scheme), set the primary node of a role, detect the GUI host's own address, and test reachability between two registered components.

  1. Status, unlock and lock endpoints shall manage the host sudo password for the caller's session. Unlock shall verify the password with sudo before storing it. The password shall be associated with the session through a single session cookie, held in the server's memory, dropped after an idle period (RADAR_SUDO_IDLE_MINUTES, default 15 minutes), and never persisted; a privileged action receives it through an owner-only temporary file deleted when the action ends.

  1. Each deployment action (build, undo scenario, run anomaly detector, health check, mint token, assign and unassign agent group, deregister agent, enrollment window, teardown) shall have its own endpoint taking a JSON specification, and shall stream the action's output as plain text while it runs rather than only on completion. An action that needs host privileges and has no unlocked sudo credential shall be refused with a response that tells the frontend to prompt for it.

  2. A preview endpoint shall return the commands a deployment action would run without executing them.

Error handling

  1. Every JSON endpoint's error responses shall indicate failure and include a human-readable message, and shall use standard HTTP status codes to distinguish a refused request, a missing resource, an invalid request and a server-side failure. Streaming endpoints report errors in the stream as lines starting with [ERROR].

Rationale

RADAR's configuration and operational actions are otherwise only reachable by editing files or running scripts directly on the RADAR host. A REST API layer gives the web interface a stable way to read and change that configuration and to trigger deployment actions, without requiring direct host access or knowledge of the underlying file formats and scripts. Because these actions include privileged ones on the host, the API is reachable on the loopback interface by default and is protected by a login token, a host allowlist and cross-site request checks.

  • SRS-069, SRS-067, SRS-060: the scenario deployment, agent onboarding, and health-check mechanisms invoked by the deployment action endpoints.

Related requirements

Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

  1. Access control: a request with a disallowed Host, without the login token, or a cross-site state-changing request is refused; a request with the token cookie succeeds.
  2. Scenario list and detail: the list endpoint returns every visible scenario with its identifier, name, description, status, detection type, rule IDs, bound state and shared state, bound scenarios include their active-response configuration, and the detail endpoint returns a not-found error for an unknown scenario.
  3. Active-response read and update: a partial update changes only the supplied fields, and an unknown mitigation name is rejected.
  4. Connector list, save and reveal: the list endpoint omits secret values while indicating which are set, a connector's fields can be saved, and a secret can be revealed only for an allowed field and only with an unlocked sudo credential.
  5. Connector test: the test endpoint reports success or failure for each connector type based on its currently saved fields.
  6. Credential sessions: a wrong sudo password is not stored; a stored one is dropped after the idle period and on logout.
  7. Deployment action streaming: a long-running deployment action streams its output progressively rather than only on completion.
  8. Preview: the preview endpoint returns the commands a deployment action would run without executing it.
  9. Error handling consistency: failure responses are distinguishable from success, carry a human-readable message, and use an HTTP status code appropriate to the failure type.

2.18 RADAR scenario: web scanning detection SRS-066

As a security engineer, I want RADAR to detect web-layer scanning by combining three indicators that are each individually evadable but not all at once — scanner tool signatures, failed-request rate, and HTTP method abuse — and to apply automated response only where two or more agree on the same source.

Scope

This requirement applies to detection of automated web-layer scanning against monitored HTTP servers, via three indicators: a known scanner signature in the User-Agent, an abnormal rate of failed requests, and use of HTTP methods a normal client would not send. Automated response is scoped to fire only when two or more indicators agree on the same source within a short window; a single-indicator match remains a detection-only alert and is out of scope for automated response.

Payload-level detection (SQLi, XSS, path traversal in request parameters) is out of scope for this scenario — that is a WAF function, handled separately.

Requirements

  1. RADAR shall evaluate the HTTP events of Suricata's eve.json on the monitored host (Wazuh group ids, Suricata http.* fields), read through the scanning_detection agent group. Every indicator rule attaches to the ids group and keys on the source IP field src_ip. Rules: radar/scenarios/rules/scanning_detection/a4-scanning-detection.xml.

  2. RADAR shall fire Indicator 1 — tool signature (100810, level 3) when a request's User-Agent matches a known scanning tool: sqlmap, nikto, nmap, masscan, nuclei, gobuster, dirb/dirbuster, ffuf, feroxbuster, wfuzz, wpscan, joomscan, openvas, nessus, acunetix, burp, w3af, whatweb, arachni, skipfish, zgrab.

  3. RADAR shall fire Indicator 2 — failed-request rate: rule 100815 (level 3, not bound to any response) records each 404/401/403 response; rule 100825 (level 10) fires when 100815 matches 20 times from the same source IP within 70 seconds. The threshold is to be calibrated per deployment.

  4. RADAR shall fire Indicator 3 — method abuse (level 6): rule 100820 on TRACE, TRACK and CONNECT, and rule 100821 on the WebDAV set (PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK, SEARCH) for any virtual host (http.hostname) not listed in the CDB list radar_webdav_apps. OPTIONS is excluded (CORS preflight is legitimate high-volume traffic); PUT, DELETE, and PATCH are excluded (normal REST semantics). Virtual hosts that serve WebDAV natively (SharePoint, Nextcloud, CalDAV, SVN-over-HTTP, macOS Finder mounts) must be listed in radar_webdav_apps.

  5. RADAR shall fire Scan confirmation (100830, level 12) when two or more of Indicators 1–3 match the same source IP within 300 seconds. Each ordered pair of indicators has its own low-level anchor rule (level 3, not bound to any response: 100826, 100827, 100828, 100829, 100831, 100832) that fires on an indicator when a different indicator matched the same source in the previous 300 seconds; 100830 is the child of all six. 100830 is the sole trigger for notification and active response.

  6. Repeated matches of a single indicator alone shall never satisfy the confirmation rule: every anchor rule requires a prior match of a different indicator group.

  7. RADAR shall enforce an allowlist only at the active-response handler, not in the detection rules, so an allowlisted source still raises alerts. A matching source's active response shall be declined and recorded in an audit entry (decision_id, rule_id, source_ip, action, tier, result, reason), with reason: allowlist.

  8. RADAR shall raise operational alert 100835 (level 12, no attacker source IP or ATT&CK technique) and decline the active response if the allowlist cannot be read, rather than fail open. A declined block is recoverable; an executed block against unverified infrastructure is not, within its timeout. 100835 is raised from the audit entry itself (rule 100840 under the stock active-response log rule 650).

  9. RADAR shall score 100830 as a signature alert (SRS-061; ar.yaml block scanning_detection: w_sig 0.7, w_cti 0.3, signature_impact 0.6, signature_likelihood 0.9), so a confirmation alone reaches Tier 2 and Tier 3 needs a high CTI score. The CTI score comes from the DECIPHER suspicious_nt_scanning analysis endpoint, sent the source IPs, URIs, methods, User-Agents, target host and the chain of rules that fired. Tier 2 and Tier 3 run firewall-drop against the source IP when allow_mitigation is true (false as shipped). X-Forwarded-For shall be used for the source IP only when the request came through an address listed in trusted_proxies.

See: docs/manual/radar_docs/radar-scenarios/scanning_detection_explained.md

2.19 Secure agent enrollment and automated onboarding SRS-067

As a security engineer, I want agent enrollment to require a credential, endpoint onboarding to be a single command, and a clean Linux endpoint to become a fully monitored one without manual configuration steps, so that no unauthenticated host can register as a RADAR-monitored endpoint and onboarding a legitimate endpoint requires no hand-editing of Wazuh configuration.

Scope

This requirement covers, for Linux endpoints:

  • The manager-side credential requirement for Wazuh agent enrollment, rejection of duplicate-name enrollment attempts, cluster-key handling, and the time-limited restriction of network access to the enrollment port (radar/radar_deploy/manager-harden-enrollment.sh, manager-mint-token.sh, manager-revoke-token.sh, manager-enrollment-window.sh).
  • The installer that takes a clean Linux endpoint to a fully monitored one, the short-lived token that authorizes it, and the corresponding removal script. Both scripts ship in the radar/radar-agent/ folder, which is copied whole to the endpoint and from which they are run (bootstrap-agent.sh, uninstall-agent.sh).

Windows endpoints and Docker-based agent deployment are out of scope for the installer and removal script; the manager-side enrollment controls (requirements 1-6) apply regardless of the endpoint's operating system.

Requirements

  1. The manager shall refuse an agent-auth enrollment attempt that does not present the current, valid enrollment credential. An unauthenticated enrollment attempt shall not receive an agent key.

  2. An enrollment attempt using the name of an agent already registered on the manager shall fail with an explicit error, rather than silently overwriting the existing agent's registration.

  3. The manager's cluster authentication key shall be generated randomly at first setup, or read from an environment variable (WAZUH_CLUSTER_KEY). A randomly generated key shall be persisted to the RADAR environment file so that it survives a restart.

  4. Network access to the manager's agent enrollment port (1515) shall be blocked by a host-level firewall rule by default. It shall be reachable only during an explicitly opened, time-limited window. Managing the rule requires root on the RADAR host.

  5. An engineer shall be able to open the enrollment window for a specified duration, close it before that duration elapses, and query its current state (open or closed), independently of minting a token. An opened window shall close automatically once its duration elapses, without requiring a manual close action.

  6. Minting an enrollment token shall open the enrollment window for the token's lifetime (1 to 1440 minutes). An enrollment token shall become invalid once its expiry elapses: it shall be replaced with an undisclosed value by a timer, and, if the timer did not run, by the next deployment or health check. Minting a new token shall immediately invalidate any previously minted token.

  7. A single script, run as root from the radar-agent folder, shall, given a manager address, a valid token, and one or more target groups:

    • Install a pinned version of the Wazuh agent package from the official repository with apt-get, yum or dnf, and hold it at that version so that routine system updates do not change it.
    • Write the manager address into the agent's configuration.
    • Enroll the agent using the supplied token, into the specified group(s).
    • Install every active-response script listed in the folder's catalog (ar-scripts.yaml), whatever the endpoint's groups, together with the catalog, with root ownership and permissions that prevent other users from modifying them. The catalog maps each active-response name to a versioned script, so the version used on an endpoint can be switched by editing the catalog alone.
    • Install and start the metric collector of each target group that has one (log_volume, linux_resource_utilization).
    • Enable and start the agent service.
    • Print a clear success or failure message, including a next step on failure.

The script shall check the folder's contents (catalog, scripts, collectors, helpers) before changing anything on the endpoint.

  1. Running the installer again on an endpoint that is already enrolled (a non-empty local agent key file exists, or the manager reports "Duplicate agent name" and a key is available locally) shall not create a duplicate registration or fail; it shall keep the existing enrollment and proceed to updating the installed scripts and verifying the service. After an uninstall without data purge, re-running the installer for the same agent name and manager shall reuse the kept agent key, so the agent keeps its ID and groups.

  2. The installer shall not require Docker or any container runtime on the target endpoint.

  3. A separate script, run on the endpoint from the same folder, shall remove the RADAR collectors and active-response scripts, stop the agent service and uninstall the agent package. Without options it shall keep a copy of the agent key for a later re-installation. An option (--purge-data) shall additionally and irreversibly remove all local agent state (logs, enrollment data, the kept key, installed active-response scripts, collected metrics).

Rationale

RADAR trains an anomaly detection model on incoming data; a host that can enroll without authentication can inject events that teach the model that attack behaviour is normal (training data poisoning), which is a materially worse consequence than the equivalent gap in a signature-only system. Closing this gap with a shared credential, immediately, was prioritized over a higher-assurance certificate-based scheme that would take materially longer to stand up correctly — the risk reduction from "no authentication" to "some authentication" is large and urgent, and is layered with additional mitigations (short-lived tokens rather than one long-lived secret, rejection of duplicate-name enrollment, and a normally-closed enrollment port) that narrow the residual exposure of a shared-credential scheme to a bounded, operator-controlled window.

Wazuh's authd reads its password file only at start, so activating and revoking a token each restart the manager and briefly disconnect connected agents. This is an accepted cost of short-lived tokens.

Many organizations already manage endpoints with configuration/fleet management tooling (Ansible, Puppet, Intune, SCCM). A single, parameterized installer that does nothing beyond onboarding means each of these can wrap the same artifact rather than RADAR maintaining a separate integration per tool.

  • SRS-069: Scenario-scoped agent group configuration delivery. The installer's group assignment step, and all configuration an onboarded agent receives afterward, are delivered through the mechanism this requirement defines.

Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

  1. An agent-auth attempt without a credential is refused by the manager.
  2. An agent-auth attempt with the correct, currently valid credential succeeds.
  3. A second enrollment attempt using an existing agent's name, from an endpoint without that agent's key, is rejected rather than silently replacing that agent's registration.
  4. The enrollment port is unreachable from a general network outside of an explicitly opened window, and an opened window closes on its own once its duration elapses.
  5. A freshly minted token authorizes onboarding, and an expired or superseded token is refused.
  6. A clean, supported Linux endpoint becomes a fully enrolled, correctly grouped, running monitored endpoint with every catalog active-response script installed, by running the installer once with a valid manager address, token, and group.
  7. Running the installer a second time on the same, already-enrolled endpoint completes without error and creates no duplicate agent.
  8. The installer fails clearly and promptly when the manager is unreachable, the supplied token is invalid, or the radar-agent folder is incomplete.
  9. Running the removal script on an onboarded endpoint stops and uninstalls the agent, and the --purge-data option additionally removes all local agent state.

2.21 Scenario-scoped agent group configuration delivery SRS-069

As a security engineer, I want each RADAR scenario's agent-side configuration delivered exclusively through its own Wazuh agent group, so that deploying, changing, or removing a scenario's configuration is a manager-side operation that never requires direct contact with any individual endpoint.

Scope

This requirement defines how RADAR's scenario-specific agent configuration (log collection paths and related agent-side settings) reaches an enrolled agent, and how it is withdrawn. It covers the group structure used, and the manager-side operations that apply a scenario's configuration.

The configurations and files that are dependent on more than one scenario (a shared agent group, or a decoder/rule file used by more than one scenario) should be handled safely, so that an operation scoped to one scenario cannot break another scenario currently relying on the same shared resource.

Requirements

  1. Each production scenario shall have its own dedicated Wazuh agent group, distinct from any other scenario's group and from the baseline group every agent belongs to regardless of scenario.

  2. Configuration needed by more than one scenario shall be delivered through a single shared group used by exactly those scenarios, rather than duplicated into each scenario's own group.

  3. Applying, updating, or removing a scenario's agent-side configuration shall be accomplished entirely by updating the relevant group's configuration through the Wazuh REST API. No script or operation defined by this requirement shall connect to, or require credentials for, an individual agent endpoint in order to change its configuration.

  4. Deploying a scenario shall ensure its own group exists and shall push that scenario's agent-config snippet to it; if the scenario depends on the shared group, deploying it shall also ensure the shared group exists and carries the shared snippet.

  5. Removing a scenario's deployment shall reset its own group's configuration to empty and shall remove any agent's membership in that group. It shall not modify the baseline group every agent belongs to.

  6. An operation that removes one scenario's configuration shall not modify or remove the shared group's configuration, or any file used by more than one scenario, while another scenario that depends on that shared group or file is still currently deployed. Such shared resources shall only be removed once no remaining deployed scenario depends on them.

  7. Deploying an already-deployed scenario, or removing an already-removed (or never-deployed) scenario's configuration, shall complete without error and without unintended side effects.

Rationale

Wazuh's own group mechanism already distributes configuration to every agent in a group without requiring the manager to individually contact each one; using it as the sole configuration-delivery path for RADAR scenarios means adding, changing, or removing a scenario never requires direct access to any endpoint, and an agent picks up a group's configuration through Wazuh's own existing synchronization rather than a RADAR-specific mechanism that would have to replicate it. Because some configuration is legitimately needed by more than one scenario, that sharing has to be handled explicitly and conservatively during removal.

Dependencies

  • SRS-067: Secure agent enrollment and automated onboarding. The group assignment step of the onboarding installer, and any later re-assignment of an already-enrolled agent, both use the mechanism this requirement defines.

Acceptance criteria

Successful validation according to the corresponding test case specification, which shall verify:

  1. Deploying a scenario updates only that scenario's own group, and the shared group if the scenario depends on it — no other scenario's group is modified.
  2. An agent assigned to a scenario's group receives that scenario's configuration without any direct connection having been made to the agent itself.
  3. Removing one scenario's configuration, while a different scenario that depends on the same shared group or file is still deployed, leaves that shared group and file unchanged and the other scenario's detection unaffected.
  4. Removing one scenario's configuration, once no other deployed scenario depends on the same shared group or file, removes that shared resource too.
  5. Removing a scenario's configuration resets its own group and clears agent membership in it, without altering the baseline group any agent retains regardless of scenario.
  6. Repeating a deploy or a remove operation for the same scenario a second time completes without error and produces no change beyond the first operation's effect.

2.23 RADAR scenario: Linux resource utilization detection SRS-071

As a security engineer, I want RADAR to detect anomalous CPU and memory utilization on Linux endpoints using a per-endpoint behavioral baseline, and apply the existing risk policy to respond to it.

Scope

Endpoints: Linux hosts running the Wazuh agent, enrolled in the linux_resource_utilization agent group. Metric source: A local collector on the endpoint. No external log source is involved. Required event fields:

- `data.cpu_usage_pct` (string-encoded percentage)
- `data.mem_usage_pct` (string-encoded percentage)
- `agent.name`
- `@timestamp`

Detection method: OpenSearch RCF Anomaly Detection, categorical field agent.name. Each endpoint is scored against its own history; there is no fleet-wide fixed threshold.

Pipeline reuse: Detection → webhook → Wazuh ingestion → active response reuses the opensearch_ad_alerts pipeline.

Requirements

  1. Local metric collection (bootstrap-agent.sh, run when an agent is enrolled in linux_resource_utilization):
  • Installs a systemd timer, radar-linux-resource-utilization.timer, running radar-linux-resource-utilization-metric.sh every 30 seconds.
  • CPU: cpu_pct = (1 − Δidle/Δtotal) × 100, from two /proc/stat reads 1 second apart.
  • Memory: mem_pct = (1 − MemAvailable/MemTotal) × 100, from /proc/meminfo.
  • Output line: <timestamp> <hostname> resource_usage_metric: cpu=<cpu_pct> mem=<mem_pct>, appended to /var/log/radar/resource_usage_metric.log.
  • Log rotation: daily, 7 files retained, compressed (/etc/logrotate.d/radar-linux-resource-utilization).
  1. Decoder (scenarios/decoders/linux_resource_utilization/0001-linux-resource-utilization.xml):
  • resource_usage_metric decoder matches on program_name = resource_usage_metric.
  • Child decoder resource_usage_metric_fields extracts cpu_usage_pct and mem_usage_pct with regex cpu=(\S+) mem=(\S+).
  1. OpenSearch detector (config.yaml, scenarios.linux_resource_utilization):
  • Detector LINUX_RESOURCE_UTILIZATION_DETECTOR on the index pattern wazuh-archives-*.
  • Result index: opensearch-ad-plugin-result-linux-resource-utilization.
  • Categorical field: agent.name.
  • Filter query: data.mem_usage_pct exists.
  • Features (Painless scripts that parse the string field as a number and return 0.0 if absent; imputation_option: { method: ZERO }):
    • cpu_usage_avg = avg(data.cpu_usage_pct)
    • cpu_usage_max = max(data.cpu_usage_pct)
    • memory_usage_avg = avg(data.mem_usage_pct)
    • memory_usage_max = max(data.mem_usage_pct)
  • Shingle size: 8. Detector interval: 1 minute. Window delay: 1 minute.
  • Alert threshold: anomaly_grade ≥ 0.01 and confidence ≥ 0.01 (anomaly_grade_threshold, confidence_threshold); up to monitor_max_entities (default 5) agents reported per monitor run.
  • Monitor name: LinuxResourceUtilization-Monitor. Trigger name: LinuxResourceUtilization-Anomaly-Detected.
  1. Wazuh rules (scenarios/rules/linux_resource_utilization/a5-linux-resource-utilization.xml, group opensearch_ad_alerts):
  • Rule 100320, level 5: any opensearch_ad-decoded alert read from /var/log/ad_alerts.log, tagged with the group radar_ad_received.
  • Rule 100321, level 12, if_group radar_ad_received: matches trigger name LinuxResourceUtilization-Anomaly-Detected. It attaches by group rather than to 100320, so it still fires when another AD scenario's catch-all (100300 or 210039) is the one Wazuh matched first.
  • Rule 100321 is the only rule in this scenario bound to active response.
  1. Active response context resolution (scenarios/active_responses/radar_ar.py):
  • Registry maps linux_resource_utilization to LinuxResourceUtilization, which inherits LogVolume unchanged.
  • It therefore takes its context window from alert.data.period_start/period_end (capped at delta_ad_minutes and at the alert time) and its effective agent from alert.data.entity_keyword.
  • Without this registration the scenario would fall back to BaseScenario, whose AD context is the delta_ad_minutes before the alert on all agents.
  1. Active response and risk scoring (scenarios/active_responses/ar.yaml, linux_resource_utilization):
  • ad.rule_ids: ["100321"]. signature.rule_ids: [].
  • w_ad: 0.9, w_sig: 0.0, w_cti: 0.1.
  • delta_ad_minutes: 10, delta_signature_minutes: 1.
  • signature_impact: 0.0, signature_likelihood: 0.0.
  • Tier boundaries: tier1_min: 0.0, tier1_max: 0.33, tier2_max: 0.66 (SRS-061 defaults, not overridden).
  • mitigations_tier3: [terminate_service.sh]. mitigations_tier2: []. allow_mitigation: true. terminate_service.sh stops only a service listed in the scenario's terminable_services and on the agent; an anomaly alert carries no source IP, so without such a service nothing is terminated.
  • Risk formula: $R = w_{ad} \times (\text{anomaly_grade} \times \text{confidence}) + w_{sig} \times 0 + w_{cti} \times T$. There is no DECIPHER analysis endpoint for this scenario, so $T = 0$ and $R \le 0.9$.
  • Example: anomaly_grade = 0.82, confidence = 0.75, $T$ = 0 → $R = 0.9 \times 0.615 = 0.5535$ → Tier 2.
  1. OSSEC wiring (scenarios/ossec/radar-linux-resource-utilization-ossec-snippet.xml):
  • Commands: radar_ar_linux_resource_utilization (executable radar_ar.py), terminate_service.sh.
  • Active response: bound to rules_id: 100321, location: server.
  • Rule ID 100321 must match across ar.yaml's ad.rule_ids, this file's <rules_id>, and the rule defined in a5-linux-resource-utilization.xml.
  1. Audit logging: each active response execution for this scenario records its decision_id, the scenario and detection type (ad), the resolved time window and effective agent, the risk breakdown ($A$, $S$, $T$, $R$, tier), and the planned, withheld and executed actions with their outcomes, per SRS-061.

Rationale

Sustained CPU/memory anomalies indicate cryptomining, resource-exhaustion attacks, or a compromised process, independent of which application or protocol is responsible. A per-endpoint RCF baseline adapts to each host's own load profile instead of a single fleet-wide threshold.

  6. For each active response execution in criteria 4-5, /var/ossec/logs/active-responses.log records the decision with its decision_id and the full risk breakdown.

2.25 RADAR anomaly alert relay contract SRS-089

As a security engineer, I want anomaly alerts from OpenSearch to reach the RADAR active response only through one authenticated, validated relay, with one Wazuh event per anomalous entity, so that a forged or malformed anomaly alert cannot trigger a response and every reported entity is scored on its own.

Scope

  • Producers: the OpenSearch Alerting monitors of the anomaly-based scenarios: log_volume and linux_resource_utilization (radar/anomaly_detector/monitor.py), and the off-hours rule-mode and model-mode monitors of suspicious_login (radar/anomaly_detector/off_hours.py). The notification channel they post to is created by radar/anomaly_detector/webhook.py.
  • Relay: the RADAR webhook service radar/webhook/ad_alerts_webhook.py, its container and Wazuh agent (radar/webhook/, radar/docker-compose.webhook.yml).
  • Consumer: the shared decoder 0001-ad-common.xml (shipped under radar/scenarios/decoders/log_volume/, linux_resource_utilization/ and suspicious_login/), the AD catch-all and trigger rules, and radar/scenarios/active_responses/radar_ar.py.
  • Out of scope: TLS on the webhook port (plain HTTP; a reverse proxy is needed for TLS) and rate limiting, neither of which is implemented.

Requirements

  1. Authentication. The webhook shall accept notifications only as POST /notify carrying the header X-RADAR-Webhook-Token equal to the shared secret WEBHOOK_SHARED_SECRET, compared in constant time. A missing or wrong token shall be refused (401). Without a configured secret every request shall be refused, and the webhook container shall not start without one. The notification channel shall send the header with the secret.

  2. Size and form. A body larger than 16 KiB shall be refused (413). A body that is not a JSON object shall be refused (400). The body {"ping": true} shall be answered as a connectivity check and write nothing.

  3. Validation. Every value written shall first be validated; an invalid required value rejects the entry: - trigger name and entity: 1 to 128 characters from [A-Za-z0-9._:-]; - monitor period start and end: ISO 8601 timestamps; - anomaly grade and confidence: numbers in [0, 1].

Optional values (the anomaly's data window; the off-hours event count and schedule group) shall be written only when usable: the data window only when both bounds are valid and ordered, rewritten in ISO 8601 UTC; the count and group only together. An unusable optional value shall be dropped without rejecting the entry. No other value from the body shall be written.

  1. Several entities per notification. A monitor run shall report up to monitor_max_entities entities (default 5, bounded to 1–50; model_mode.max_entities for the off-hours model mode) whose grade and confidence reach the configured thresholds, highest grade first, as an anomalies list. The webhook shall: - read at most 50 entries, each inheriting the trigger name and monitor period of the notification; - skip invalid entries, and refuse the notification (400) only when no entry is usable; - write one line per entity, keeping the highest-graded entry of an entity reported twice; - for a notification without an anomalies list, write the single line of its top-level values.

  2. Line format. Each line shall be appended, under a lock, to the anomaly alert log (AD_ALERTS_LOG, default /var/log/ad_alerts.log) in syslog form with the program name ad_alert, the marker OpenSearchAD, the trigger name, and the quoted fields entity, start, end, anomaly_grade, anomaly_confidence, then the optional data_start, data_end and off_hours_count, schedule_group. The response shall state the number of lines written.

  3. Decoder contract. The decoder opensearch_ad (program name ad_alert, prematch OpenSearchAD) and its children shall extract detector_name, entity_keyword, period_start, period_end, anomaly_grade, anomaly_confidence, and, when present, data_start, data_end, off_hours_count, schedule_group. A line without the optional fields shall still decode. All copies of 0001-ad-common.xml shall be identical, and the line format and decoder shall change together.

  4. Delivery and rules. The Wazuh agent in the webhook container, enrolled as WEBHOOK_AGENT_NAME (default ad-webhook), shall read the anomaly alert log as syslog (radar/webhook/ad-ossec.conf) and forward it to the manager. Each AD scenario shall ship a catch-all rule on the opensearch_ad decoder that sets the group radar_ad_received (100300, 210039, 100320), and trigger rules that match the trigger name under that group with if_group, never if_sid (100309, 210040, 210041, 100321), so that a trigger rule fires whichever catch-all matched first.

  5. Origin check in the active response. radar_ar.py shall act on an alert identified as an anomaly alert (rule ID in a scenario's ad.rule_ids) only when it comes from the webhook agent (agent.name equal to WEBHOOK_AGENT_NAME, default ad-webhook) and from the anomaly alert log (location equal to AD_ALERTS_LOCATION, default /var/log/ad_alerts.log, possibly prefixed by the agent's address). Any other such alert shall be logged as rejected and dropped without context collection, scoring, notification or mitigation (AdAlertOrigin in radar_ar.py). Fusion shall count only alerts that pass the same check as anomaly evidence (SRS-061 requirement 7).

See: docs/manual/radar_docs/radar-run-ad.md

Rationale

The webhook turns HTTP notifications into log lines that the active response trusts as detector output. Anyone who can write such a line could make RADAR notify, open cases or, with mitigation enabled, act. The shared secret protects the HTTP side; the origin check protects the Wazuh side, where a forged ad_alert line could otherwise arrive from any agent or file. Strict validation of each written value prevents log injection through entity or trigger names. A monitor run can find several anomalous entities at once; one line per entity lets each be decoded, scored and attributed separately instead of only the top hit.

  4. Every AD trigger rule attaches to every AD catch-all through if_group radar_ad_received.
  5. An anomaly alert from another agent or another file is rejected by radar_ar.py without scoring or action.

2.26 RADAR resilience to adversarial ML SRS-090

Status: planned. Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

As a security engineer, I want RADAR's anomaly detection to resist attempts to poison, evade or tamper with its models, and its automated response not to depend on a model an attacker could have shaped, so that an adversary who knows RADAR learns from the monitored data cannot teach it that an attack is normal or turn it against legitimate users.

Scope

The anomaly detectors RADAR deploys in OpenSearch (log_volume, linux_resource_utilization, and the off-hours model mode of suspicious_login), the data they learn from, and the decisions the active response takes on their alerts. The intended architecture is described in HARC-015, its implementation flow in LARC-031 and its design in SWD-036. The five layers below follow HARC-015.

Out of scope: the signature rules themselves, and SONAR and ADBox models (their own requirements apply).

Requirements

  1. Clean baselines. RADAR shall let an operator declare, per scenario, the period and the endpoints a detector's initial baseline is learned from, and exclude periods or hosts suspected of compromise. A detector shall not be started on history that contains an excluded period or host.

  2. Drift detection and gating. - RADAR shall track, per detector, the shift of its baseline (mean, spread, and correlated shifts across features) between consecutive evaluation periods. - A shift above a configured threshold shall raise an alert to the SOC and freeze further model updates for that detector until an analyst approves or rejects the change. - A rejected change shall restore the last approved baseline.

  3. Multi-layer validation. For a scenario configured to require it, an anomaly alert shall reach the mitigation tiers only when corroborated by evidence from another detection layer (signature, CTI, or another anomaly detector) on the same entity within a configured window. An uncorroborated anomaly alert shall still be scored, logged and notified.

  4. Human oversight. - Each anomaly decision shall expose the features and values that drove it to the analyst. - Analysts shall be able to label an alert as a true or false positive; the labels shall be stored and available to the model-update process. - Operations listed in configuration (for example a baseline reset or a detector reconfiguration) shall require explicit approval.

  5. System hardening. - The audit records of decisions and model operations shall be tamper-evident (for example by a hash chain). - Model and detector definitions shall be versioned with a checksum, and changing them shall require an authenticated, authorised role separate from the role that reads results. - Every model operation (create, start, stop, update, reset) shall be audited with its actor and time.

  6. Configuration. All the above shall be configured in one section of the RADAR configuration, disabled by default, so that existing deployments keep their current behaviour until an operator enables it.

Relation to the current implementation

None of the requirements above is implemented. Existing mechanisms that address part of the same risks, and that the planned layers would build on:

  • Anomaly alerts are relayed only through an authenticated webhook and accepted by the active response only from the webhook agent's log (SRS-089).
  • A scenario can weight signature, anomaly and CTI evidence together, and suspicious_login fuses a signature alert with an anomaly alert for the same user (SRS-061 requirement 7). Corroboration raises the score but is not required before mitigation.
  • Mitigation is opt-in per scenario, and its targets come only from the triggering alert and are checked against allowlists (SRS-061).

See: docs/manual/radar_docs/adversarial-ml-guidance.md

Rationale

RADAR's detectors learn continuously from the data they monitor. An attacker with a foothold can shift a baseline slowly until attack behaviour scores as normal (poisoning), shape activity to stay just below thresholds (evasion), or alter detector definitions (tampering). A detection that is itself manipulable should neither suppress alerts silently nor, on its own, drive the most intrusive responses. Defence in depth, human approval of model changes, and tamper-evident records bound the damage each of these attacks can do.

Acceptance criteria

To be verified by a test case specification once implemented:

  1. A detector configured with an excluded period does not learn from events in that period.
  2. A synthetic gradual shift of a monitored metric above the drift threshold raises a drift alert and freezes the detector's model updates until approval; rejecting the change restores the previous baseline.
  3. With corroboration required, an anomaly alert alone never triggers a mitigation, and the same alert with a signature alert for the same entity in the window does.
  4. Modifying an audit record or a detector definition outside the approved path is detected.
  5. With the configuration section absent, RADAR behaves exactly as before.

4.32 Authenticated and encrypted component channels SRS-083

As a security engineer, I want every channel between IDPS-ESCAPE components that cross a host or trust boundary to authenticate its peer and encrypt its traffic, so that an attacker on the network can neither read nor forge alerts, credentials or configuration in transit.

Scope

This requirement covers the channels of a RADAR-deployed C&C stack (radar/build-radar.sh, radar/docker-compose.core.yml, radar/docker-compose.webhook.yml) and of the clients that RADAR and SONAR run against it. The components and ports are described in LARC-034. Channels to external services (SMTP relay, DECIPHER) are covered as far as RADAR's client settings go. The remote traffic-mirroring setup of docs/manual/custom_deployments/remote_monitoring/ is covered under planned extensions.

Requirements

  1. Agent enrollment. Enrollment on port 1515 SHALL run over TLS (Wazuh agent-auth/authd) and SHALL require the current enrollment credential. radar/radar_deploy/manager-harden-enrollment.sh sets <use_password>yes</use_password> and <purge>no</purge> in the manager's ossec.conf on every build. Credentials are short-lived tokens (manager-mint-token.sh, manager-revoke-token.sh), and port 1515 is blocked in the DOCKER-USER chain outside an enrollment window (manager-enrollment-window.sh). The detailed enrollment behaviour is specified in SRS-067.
  2. Agent events. Endpoint agents and the webhook agent SHALL send events to the manager on port 1514 over the Wazuh agent protocol, encrypted with the per-agent key issued at enrollment. RADAR does not change the manager's agent-protocol encryption settings.
  3. Certificates. On the first build, radar/radar_deploy/manager-ensure-certs.sh SHALL generate a root CA and node certificates for the indexer, manager (Filebeat), dashboard and indexer admin with wazuh/wazuh-certs-generator from radar/config/certs.yml, into radar/config/wazuh_indexer_ssl_certs/. It SHALL keep existing certificates.
  4. Manager to indexer. Filebeat in the manager SHALL ship alerts and archives to the indexer over HTTPS with full certificate verification against the generated root CA (FILEBEAT_SSL_VERIFICATION_MODE=full in radar/docker-compose.core.yml), authenticated with the indexer admin credential.
  5. Indexer. The indexer SHALL serve its REST interface (port 9200) and its node transport over TLS with the generated certificates (radar/config/wazuh_indexer/wazuh.indexer.yml, TLS 1.2 with ECDHE-AES-GCM ciphers on HTTP), and SHALL require a user name and password on every request.
  6. Dashboard. The dashboard SHALL serve HTTPS on port 443 with its generated certificate, and SHALL connect to the indexer over HTTPS, verifying the indexer certificate against the root CA (radar/config/wazuh_dashboard/opensearch_dashboards.yml). It SHALL reach the Wazuh API over HTTPS with the credentials written to radar/.radar-generated/wazuh.yml.
  7. Wazuh API. The Wazuh API (port 55000) SHALL be served over HTTPS and SHALL require authentication.
  8. Per-deployment credentials. The indexer, dashboard and Wazuh API passwords SHALL be generated per deployment, not taken from the stock Wazuh defaults (radar/wazuh_api/credentials.py, SRS-016), and SHALL be rotatable with radar/radar.sh rotate-credentials.
  9. Indexer to webhook. Every request to the AD alert webhook (POST /notify) SHALL carry the shared secret in the X-RADAR-Webhook-Token header. The webhook (radar/webhook/ad_alerts_webhook.py) SHALL compare it in constant time and refuse a missing or wrong secret, or any request when no secret is configured, with HTTP 401. build-radar.sh generates the secret into radar/.env (WEBHOOK_SHARED_SECRET), and radar/anomaly_detector/webhook.py adds it to the indexer's notification channel.
  10. Client TLS settings. RADAR and SONAR clients SHALL reach the indexer, Wazuh API and DECIPHER over HTTPS, and SHALL make certificate verification configurable: OS_VERIFY_SSL, DASHBOARD_VERIFY_SSL, WAZUH_VERIFY_SSL and DECIPHER_VERIFY_SSL in radar/.env (documented in radar/env.example), and wazuh.verify_ssl in SONAR's configuration (sonar/default_config.yaml, which also accepts a CA bundle path).
  11. Email. The active response SHALL use STARTTLS when sending email unless SMTP_STARTTLS is set to no.

Rationale

MRS-027 requires authenticated and encrypted channels between components outside a common trust boundary. In a RADAR deployment the endpoints are outside the C&C trust boundary and may be hostile (see radar/README.md, "Security assumptions and recommendations"); the agent channels therefore carry both authentication and encryption. The webhook carries anomaly alerts that RADAR trusts to drive automated responses, so it must at least authenticate its caller.

Acceptance criteria

Successful validation according to:

  • TST-082, which verifies the agent enrollment hardening (credential required, short-lived tokens, closed enrollment port);
  • TST-041, which verifies that a fresh build generates the certificates and per-deployment credentials, hardens enrollment, and that the indexer answers over HTTPS with the generated credentials.

The webhook secret check (requirement 9) is also covered by radar/tests/py/test_ad_alerts_webhook.py.

Planned extensions

Status: planned. Not implemented as of v2.2.0. The extensions below specify intended behaviour; no code implements them yet.

These gaps are listed as open items in radar/README.md ("Known limitations"):

  • Certificate verification on by default. radar/env.example sets OS_VERIFY_SSL, DASHBOARD_VERIFY_SSL and DECIPHER_VERIFY_SSL to false, the active response and radar/wazuh_api/ default to no verification when the setting is absent, and SONAR's default verify_ssl is false. Verification against the generated root CA shall be the default. Most RADAR clients read these settings as booleans only; only the GUI connector checks (radar/gui/orchestrator/connectors.py) accept a CA file path, so all clients shall accept one.
  • Hostname verification. The indexer does not enforce hostname verification on its transport layer, and the dashboard verifies the indexer certificate but not its host name (verificationMode: certificate). Both shall verify host names.
  • Manager authentication at enrollment. radar/radar-agent/bootstrap-agent.sh and the webhook container (radar/webhook/entrypoint.sh) call agent-auth without the manager's CA, so the agent does not verify the manager's certificate. Agents shall verify it.
  • Encrypted webhook. The webhook is served over plain HTTP (WEBHOOK_URL=http://…:8080/notify), so the shared secret and the alert payload cross the network in clear text when the indexer and the webhook are on different hosts. It shall be served over HTTPS.
  • Encrypted traffic mirroring. The remote-monitoring setup (docs/manual/custom_deployments/remote_monitoring/idps-escape-port-mirroring.sh) mirrors endpoint traffic to the C&C server's Suricata through a GRE (gretap) tunnel, which is neither authenticated nor encrypted. The mirror tunnel shall run inside an authenticated, encrypted tunnel.

4.33 Alert and anomaly storage on the C&C host SRS-084

As a security engineer, I want the alerts, archived events and anomalies that IDPS-ESCAPE produces to be stored on the C&C host, so that detection data stays within the C&C trust boundary and is not held on the monitored endpoints.

Scope

This requirement covers a C&C stack deployed by RADAR (radar/build-radar.sh), with the optional SONAR container next to it (sonar/wazuh/docker-compose.sonar.yml). When RADAR is attached to an existing Wazuh installation, radar/volumes.yml describes where that installation keeps its data; keeping that storage within the C&C trust boundary is the operator's responsibility. Encryption at rest is not provided by RADAR and is out of scope.

Requirements

  1. The Wazuh manager's state SHALL be stored in host directories of the C&C host, bind-mounted into the manager container as declared in radar/volumes.yml (by default under /srv/wazuh/manager/): configuration (/var/ossec/etc, including the agent keys), logs (/var/ossec/logs, including the alert and archive logs, active-responses.log and the RADAR enrichment logs), queues, integrations, active-response scripts, and the Filebeat configuration, registry and archives ingest pipeline.
  2. Before it creates the core stack for the first time, build-radar.sh SHALL create every missing host directory declared for the manager in radar/volumes.yml, with mode 0750, and SHALL abort if the archives ingest pipeline has no bind mount.
  3. The indexer's data (/var/lib/wazuh-indexer) SHALL be stored in the Docker volume wazuh-indexer-data on the C&C host (radar/docker-compose.core.yml). It holds the wazuh-alerts-* and wazuh-archives-* indices, the indices that RADAR scenarios write (for example wazuh-ad-log-volume-*), the results of the OpenSearch anomaly detectors, and what SONAR's indexer sinks write.
  4. Deploying a RADAR scenario SHALL enable archiving of all events on the manager (logall and logall_json in ossec.conf, set by radar/wazuh_api/scenario_ops.py) and the Filebeat archives input (radar/radar_deploy/manager-apply-scenario.sh), so that archived events are kept on the C&C host and indexed there.
  5. Anomaly alerts from RADAR's detectors SHALL be persisted on the C&C host: the webhook writes them to /var/log/ad_alerts.log in the Docker volume wazuh-webhook-logs (radar/docker-compose.webhook.yml), and the manager stores and indexes them as alerts.
  6. When SONAR runs next to the manager with the file transport of its Wazuh sink, it SHALL write anomaly events to a host directory of the C&C host (/srv/sonar/anomalies by default, set by SONAR_ANOMALIES_DIR in sonar/sonar.sh), which the manager mounts read-only and reads as a log file (sonar/wazuh/ossec-localfile.xml).
  7. The stored data SHALL be readable through the indexer only with the per-deployment credentials (SRS-016, SRS-083). RADAR SHALL write its own secrets on the C&C host with owner-only permissions: radar/.env with mode 0600, and radar/.radar-generated/ with mode 0700 (radar/wazuh_api/envfile.py, radar/wazuh_api/credentials.py).

Rationale

MRS-035 requires that anomaly events and the detection and observation data collected from endpoints be stored within the C&C trust boundary. Endpoints are assumed to be potentially hostile (radar/README.md, "Security assumptions and recommendations"), so detection data must not be kept where a compromised endpoint could alter it. Host directories and named volumes on the C&C host also survive the re-creation of containers during upgrades and credential rotation.

Acceptance criteria

Successful validation according to TST-041, which brings up the core stack on a host with storage under /srv/wazuh/, reads the manager's ossec.conf from its host path /srv/wazuh/manager/etc/, and queries the indexer with the generated credentials.

4.34 Monitoring a fleet of endpoints SRS-085

As a security engineer, I want one C&C deployment to monitor at least five endpoints at the same time, with each endpoint onboarded, configured and tracked without per-endpoint changes on the manager, so that IDPS-ESCAPE can be used on a realistic network rather than a single test host.

Scope

This requirement covers Linux endpoints running the Wazuh agent and connected to a RADAR-managed Wazuh manager, either the single-node stack that RADAR deploys (radar/docker-compose.core.yml) or an existing multi-node Wazuh installation registered in radar/infra.yaml. Network-only monitoring through traffic mirroring is out of scope.

Requirements

  1. A C&C deployment SHALL monitor at least five enrolled endpoints at the same time, each with its own agent identity and key.
  2. Each endpoint SHALL be onboarded independently with the same installer and a short-lived token (radar/radar-agent/bootstrap-agent.sh, SRS-067), without changes to the manager's configuration for that endpoint.
  3. Scenario configuration SHALL reach endpoints through Wazuh agent groups (SRS-069), so that adding an endpoint to a scenario only requires assigning it to the scenario's group.
  4. RADAR SHALL assign a list of endpoints, given by name and optionally by IP address, to a scenario's group in one operation (python3 -m wazuh_api.cli assign-hosts-to-groups; one endpoint at a time with radar/radar_deploy/manager-assign-agent-group.sh). An endpoint that cannot be resolved SHALL not prevent the others from being assigned; the operation SHALL then report a warning for it and exit non-zero.
  5. RADAR SHALL record, for every endpoint it has assigned, the agent ID, groups, last scenario, last action and any warning in radar/fleet.yaml (radar/wazuh_api/fleet.py).
  6. RADAR SHALL support more than one manager node: the manager and indexer nodes are registered in radar/infra.yaml (radar/wazuh_api/infra.py), the first or marked node being the primary, and deploying a scenario SHALL apply it to every registered manager node (radar/radar_deploy/manager-apply-scenario-all.sh). A failure on a non-primary node SHALL be reported and SHALL not stop the deployment on the other nodes.
  7. The log_volume and linux_resource_utilization anomaly detectors SHALL model each endpoint separately (categorical_field: agent.name in radar/config.yaml), so that one endpoint's behaviour is not masked by the rest of the fleet.

Rationale

MRS-029 sets a minimum of five monitored endpoints. Per-endpoint work on the manager does not scale and is error-prone; group-based configuration, a single installer and list-based group assignment keep the effort per added endpoint constant. Larger installations spread agents over several manager nodes, so RADAR has to configure all of them.

Acceptance criteria

Successful validation according to TST-049, executed with at least five enrolled endpoints, which shall show that:

  1. every enrolled endpoint is listed as active by the Wazuh API before and after a RADAR deployment;
  2. a scenario is applied to every registered manager node of a multi-node installation.

Requirement 4 is also covered by the group-assignment tests in radar/tests/py/test_scenario_ops.py.
