1.0 SONAR Low-Level Architecture

Low-level architecture requirements for SONAR (SIEM-Oriented Neural Anomaly Recognition) subsystem.

1.1 SONAR training pipeline sequence LARC-019

Training workflow sequence diagram

The training pipeline retrieves historical alerts, builds the feature matrix and its categorical vocabulary, trains the scenario's detector backend (mvad by default, or pca, ewma) and saves the model directory. Every training command (sonar train with or without a scenario, and the training phase of sonar scenario) runs this one sequence (_execute_training_phase in sonar/cli.py).

With the datastream sink or shipping enabled (and not in debug mode), training then installs the data stream's index templates and ISM policy for the scenario (SWD-024).

Key operations

Component Operation Input Output
Scenario Loader Parse and validate YAML Scenario file path UseCase
Data Provider Fetch alerts Time range, alert_filter Raw alerts (JSON); only the fields the features read, SONAR's own alerts excluded
Feature Builder Build features Raw alerts Time-series matrix, categorical vocabulary
ModelEngine Train Feature matrix, vocabulary Trained backend, metadata (feature contract, training record)
Detector backend Fit Feature matrix Backend state (mvad: training pre-flight with sonar/training_plan.py)
File System Persist model Metadata and backend state Model directory (no pickle)

Error handling

  • Insufficient data: no alerts with a valid timestamp, or fewer buckets than the backend needs (for mvad: one optimiser update and a validation window under the configured parameters; for pca and ewma: a fixed minimum): training fails, saves nothing and exits with status 1, stating the required bucket count. For mvad, fewer updates than min_gradient_steps only warns.
  • Invalid parameters: an unknown key in extra_params is an error; unknown keys elsewhere in configuration and scenario files are ignored with a warning.
  • Indexer failures: every indexer request has a timeout (wazuh.timeout_seconds); a failed connection check or search ends training with status 1. Training does not retry.
  • Model persistence: the model is written to a staging directory and swapped in only when complete, so a failed save leaves the previous model in place.

1.2 SONAR detection pipeline sequence LARC-020

Detection workflow sequence diagram

The detection pipeline loads a trained model, scores the complete buckets of the detection window, and delivers the new anomalies to the configured sinks. Every detection command (sonar detect with or without a scenario, and the detection phase of sonar scenario) runs this one sequence (_run_single_detection in sonar/cli.py); realtime mode repeats it once per bucket.

Detection modes

detection.mode is read only by sonar scenario; sonar detect always runs once.

Mode Behavior
historical, batch One detection run over the window, then exit
realtime Repeat the run once per bucket, after the bucket has ended plus ingest_delay_seconds (or every polling_interval_seconds if set), until stopped

In realtime mode a failed run is retried after 10 s, doubling per consecutive failure and capped at one bucket; after max_consecutive_failures consecutive failures SONAR exits with status 1. A run with too little data is not a failure. SONAR itself does not schedule periodic one-shot runs; a scheduler (cron, a container restart policy) may.

Scored window

Detection scores the complete time buckets of the last lookback_minutes; the current bucket, still filling, is never scored, nor is one that ended less than ingest_delay_seconds ago. The model needs a fixed number of earlier buckets as context before the first bucket it can score (derived from its backend's window), so the pipeline fetches them as well and reports only buckets inside the scored window. In debug mode the local file is scored as a whole, without a time range.

Post-processing steps

  1. Thresholding: Keep buckets that the backend flags and whose severity (0–1) reaches the configured minimum (threshold), if one is set
  2. Consecutive filtering: Keep only runs of at least min_consecutive such buckets, evaluated over the whole scored window before the watermarks are applied
  3. Enrichment: Add anomaly_id (from the scenario ID and bucket start), scenario and model names, severity, raw score, top contributors with their values, and anomaly_confidence
  4. Delivery: Each sink receives the documents after its own watermark; the wazuh, jsonl and stdout sinks send the SONAR event derived from the document, the indexer sinks store the document (SWD-024). Debug runs (output.debug_sinks) and dry runs (a JSON-lines file) use no watermark

Exit status

A one-shot run exits with 0 when the window was scored and its new anomalies delivered, 2 when there was too little data to score it (no alerts, or fewer buckets than the model needs), and 1 on an error, including a delivery in which every sink with anomalies to deliver failed and no fallback took them all. When some sinks fail and others succeed, the run logs a warning and exits with 0; the failed sinks catch up on a later run.

1.3 SONAR evaluation and calibration workflow LARC-032

sonar evaluate measures a scenario's detection quality against labelled data and calibrates its decision rule (SRS-080). It works offline, on alert files, and scores SONAR's own backends and the exported results of another detector with one implementation, so that the comparison is fair. This item describes the components and the order in which they run; the metric definitions and file formats are in SWD-045.

Workflow

Components

Component Implementation Role
Data generators sonar/test_data/generate_resource_data.py, sonar/test_data/generate_attack_data.py, sonar/test_data/labelled_splits.py With --evaluation, write a training file of normal data and a validation and a test split, each normal context followed by events injected at random, non-overlapping times, plus a label file per split; the seed (--seed, default 42) makes them reproducible
Format converter sonar/test_data/radar_format.py Rewrites the resource splits as RADAR collector events, keeping timestamps and hosts so the label files stay valid
Command sonar/cli.py (cmd_evaluate, _sonar_detections) Validates the inputs, runs SONAR's backend or loads external results, calibrates, scores and writes the report
Scenario configuration sonar/cli.py (load_scenario_for_phase, apply_agent) The same configuration path as sonar train and sonar detect: features, backend, window, threshold, min_consecutive
Model engine sonar/engine.py, sonar/backends/ Trains the scenario's backend in memory, with the same pre-flight check as sonar train, and predicts each split
Evaluation sonar/evaluation.py Labels, detections, alarm grouping, metrics, calibration and the Markdown summary
Decision rule sonar/pipeline.py (select_anomalies) The rule detection applies; evaluation reuses it so an evaluated setting behaves the same in production

Behaviour

  1. Inputs. Exactly one of --scenario (with --train-file and --test-file) and --detections is given; --test-labels is always required. Calibration needs both validation data (--validation-file or --validation-detections) and --validation-labels. Any other combination fails before work starts.
  2. SONAR's detections. The backend (the scenario's, or --backend) is trained on the last training.lookback_hours of the training file; the model is not saved. Each split is scored as a whole, as in debug mode, so its first context_buckets buckets serve as context only; a split shorter than the backend's minimum is an error. Like debug mode, the files are not filtered by alert_filter; with --agent, only that agent's alerts are kept, and the model and report are named after it.
  3. External detections. Results of the OpenSearch anomaly detection plugin (an anomaly when anomaly_grade is above 0, the grade as severity) or generic interval records are loaded; their own configured decision rule is not known, so the configured run uses no threshold and runs of one.
  4. Calibration searches a fixed grid of thresholds and run lengths on the validation split only, choosing the best F1 within the false-alarm budget (--max-false-alarms-per-day, default 5). The test split is then scored with the configured and with the calibrated values; the test precision of the calibrated values is the scenario's anomaly_confidence.
  5. Output. <name>.json (the full record) and <name>.md (a summary, also printed) are written to --output-dir; <name> defaults to <scenario_id>-<backend>. Exit status 0 on success, 1 on any error, including too little training data.

Recorded reports of the shipped scenarios are kept as test evidence in docs/specs/trp/assets/sonar-evaluation/.

Design constraints

  • One scoring path. SONAR's verdicts and external results become the same interval type and go through the same scoring function; there is no SONAR-only path.
  • No calibration on the test split. Values are chosen on the validation split and reported on the test split, so the reported precision is not fitted to the data it is measured on.
  • No network. Evaluation reads local files only; live data reaches it through sonar export (LARC-033).

See: docs/manual/sonar_docs/evaluation-guide.md

1.4 SONAR export and RADAR comparison workflow LARC-033

SONAR and RADAR's linux_resource_utilization detector are compared on the same events, features and labelled anomalies (SRS-081). The packaged scenario sonar/scenarios/radar_linux_resource_utilization.yaml reads RADAR's collector events; --agent gives one model per host, as RADAR's detector has; sonar export takes a labelled window and RADAR's results out of a live indexer; sonar evaluate (LARC-032) scores both detectors.

Workflow

Components

Component Implementation Role
Comparison scenario sonar/scenarios/radar_linux_resource_utilization.yaml RADAR's index (wazuh-archives-*), filter (events with data.mem_usage_pct, without radar_seed: true documents), one-minute interval, zero fill and the mean and maximum of data.cpu_usage_pct and data.mem_usage_pct, as in radar/config.yaml
String metrics sonar/features.py RADAR's decoder stores the metrics as strings; the feature builder parses them as numbers
Per-host restriction sonar/cli.py (apply_agent) Adds an agent.name term to alert_filter and suffixes the model name and an explicit scenario ID with the agent; applied the same way by train, detect, scenario, evaluate and export, after the scenario and any --model-name
Export sonar/cli.py (cmd_export, _export_labels) Writes the window's events with their context, the label file and RADAR's results
Indexer reads sonar/wazuh_client.py (search_alerts, search_detector_results) Events through a point-in-time (SRS-086); RADAR's results through a scroll
Evaluation sonar/evaluation.py (load_external_detections, score) Reads RADAR's results as detections and scores both detectors with the same function
Debug data sonar/test_data/radar_format.py, sonar/test_data/radar_resource_utilization/ The synthetic resource data rewritten as RADAR events, for debug runs and calibration

Behaviour

  1. Window. --start and --end (ISO 8601, UTC without an offset) are rounded down to a bucket; the window must span at least one bucket. Each --event TYPE,START,END must overlap the window; a malformed or outside event fails before the indexer is contacted.
  2. Context. Events are exported from the context before --start, so that SONAR gives a verdict for every bucket of the window. The context is the number of buckets the scenario's backend needs before its first verdict, taken from an untrained engine with the scenario's settings (119 one-minute buckets for MVAD with sliding_window: 120), or --context-minutes.
  3. Events. Whole documents are exported, not only the fields the features read, through the scenario's index, alert_filter and agent term.
  4. RADAR's results. With --radar-results <index pattern>, the plugin's results whose interval starts in the window are read through a scroll: results of several hosts share a start time and the result index has no keyword tiebreaker for point-in-time paging. With --agent, a nested query on the plugin's entity list (name agent.name, value the agent) keeps that host's results. At most wazuh.max_alerts results are kept.
  5. Files. events.json (a JSON array), labels.json (sonar-labels/1, span = the window) and, with --radar-results, radar_results.json. Exit status 0 on success, 2 when the window holds no events (wrong index, filter or agent), 1 on error.
  6. Scoring. sonar evaluate --scenario radar_linux_resource_utilization --agent <host> trains on an exported training window and scores the test window; sonar evaluate --detections radar_results.json scores RADAR's results on the same labels. RADAR's result counts as an anomaly when its anomaly_grade is above 0.

Design constraints

  • Same inputs, different detectors. The scenario's features, interval and empty-bucket handling copy RADAR's; changing one side without the other makes the comparison measure the inputs rather than the detectors.
  • No seeded history. RADAR seeds a flat synthetic history into wazuh-archives-radar-seed, which matches the scenario's index pattern; SONAR excludes it so it never learns a host that did not exist.
  • One model per host. A host's model stores its agent filter, so detection with that model reads only that host; each host has its own scenario ID, and therefore its own watermarks, data stream and anomaly identifiers.

2.1 RADAR scenario setup flow LARC-015

Setting up a RADAR scenario takes the following steps, in this order. Each one can be run from the command line or from the GUI's Deployment page.

  1. Deploy the scenario on the manager (build-radar.sh <scenario>, GUI Scenario Management). Bring up the core stack if no manager is running, build and enroll the webhook, harden enrollment, then place the manager-side files (risk engine radar_ar.py, ar.yaml, enrichment integrations, Filebeat pipeline changes) and deploy, through the Wazuh API, the scenario's agent-group configuration, decoders, rules, CDB lists and ossec.conf blocks, including the active-response commands.
  2. Onboard endpoints (radar.sh mint-token or GUI Agent Management, then radar-agent/bootstrap-agent.sh on the endpoint). Install and enroll the Wazuh agent into default, the scenario's group and, for shared scenarios, radar_shared. Install the active-response scripts listed in radar-agent/ar-scripts.yaml and the scenario's metric collector, if it has one. Already-enrolled agents are assigned to the scenario's groups from the manager instead (GUI Group Management).
  3. Create the anomaly detection pipeline, only for scenarios that use the OpenSearch AD plugin (run-radar.sh <scenario> [--ingest true], GUI Anomaly Detector). Optionally seed the indices with synthetic history, then create and start the detector and create the monitor that posts to the webhook. For suspicious_login, off_hours.py deploys the off-hours pipeline, backfills it and creates the rule-mode monitor or the model-mode detector and monitor instead.

The thresholds that trigger the monitors come from radar/config.yaml, and the risk tiers and mitigations that decide the response come from radar/scenarios/active_responses/ar.yaml.

2.2 RADAR active response flow LARC-016

Every RADAR scenario ends in the same active response, radar_ar.py (radar/scenarios/active_responses/radar_ar.py), which the Wazuh manager runs on the manager itself (<location>server</location>) for each alert whose rule is bound to it in the scenario's ossec.conf snippet (radar/scenarios/ossec/).

  1. Alert. A signature rule fires on a decoded event, or an anomaly trigger rule fires on the log line the webhook wrote for an OpenSearch monitor notification (/var/log/ad_alerts.log in the webhook container, forwarded by that container's Wazuh agent).
  2. Scenario and trust. radar_ar.py maps the alert to a scenario in ar.yaml by rule ID, then by rule group. An anomaly alert that does not come from the webhook agent's log is dropped without scoring.
  3. Context and CTI. It collects the scenario's context events from the indexer for a window that ends at the alert's timestamp (delta_signature_minutes or delta_ad_minutes), extracts IOCs, and, when DECIPHER is reachable, asks DECIPHER's analyze endpoint for a CTI score (SWD-038).
  4. Risk and tier. It computes the risk score from the anomaly, signature and CTI terms, fused with a counterpart alert where the scenario enables fusion, and maps it to tier 0 to 3 (HARC-012, SRS-061).
  5. Actions. From tier 1: a Flowintel case through DECIPHER's incident endpoint (when reachable) and an email notification. At tiers 2 and 3, and only when the scenario's allow_mitigation is true: the tier's mitigations (firewall-drop, lock_user_linux.sh, terminate_service.sh), sent through the Wazuh API to the affected endpoint's agent (for a per-agent anomaly, the agent the anomaly names), after allowlist and target checks.
  6. Record. Every step and decision, including withheld mitigations, is written to /var/ossec/logs/active-responses.log.

The detailed decision pipeline is specified in LARC-026 and SWD-027.

2.3 RADAR integration with OpenSearch modules LARC-017

RADAR uses two OpenSearch plugins shipped with the Wazuh indexer: Anomaly Detection, which runs a random cut forest (RCF) detector per scenario, and Alerting, which runs the monitor that reports anomalies to RADAR.

  • Configuration. run-radar.sh runs detector.py and monitor.py (or, for suspicious_login, off_hours.py) in the throwaway radar-cli container. They create the detector from the scenario's features, categorical_field, shingle_size, detector_interval and delay_minutes in radar/config.yaml, and a monitor with the scenario's anomaly_grade_threshold and confidence_threshold.
  • Input indices. log_volume reads wazuh-ad-log-volume-*, filled through the patched Filebeat archives pipeline. linux_resource_utilization reads wazuh-archives-*. The off-hours model mode of suspicious_login reads wazuh-archives-* events flagged by the radar-off-hours ingest pipeline.
  • Output path. When the monitor's trigger condition holds, it POSTs to the ad-webhook container at /notify on port 8080. The webhook writes one ad_alert line per anomalous entity to a log file read by its own Wazuh agent. The manager decodes the line with the opensearch_ad decoder, matches the scenario's AD rules, and runs radar_ar.py.

2.4 RADAR logical flow LARC-018

RADAR has two detection paths, which converge on the same active-response pipeline (LARC-026).

Overall pipeline

Wazuh agent (raw logs, RADAR metrics) -> Wazuh manager (decode -> rules)
    |
    [Enrichment, suspicious_login and geoip_detection only]
                        stock rule alert -> enrichment integration -> enriched log line -> Wazuh manager (decode again -> RADAR rules)
    |
    [Signature path]    Wazuh manager (RADAR rules) -> Active response
    |
    [Anomaly path]      Wazuh indexer (archives) -> Detector or query monitor -> Monitor -> Webhook -> Webhook container's agent -> Wazuh manager (rules) -> Active response

Both paths terminate in the same place: a Wazuh rule firing an active-response command bound to radar_ar.py (SWD-027). The anomaly path exists to get an anomaly result into that same rule-firing mechanism; it does not bypass it.

Signature-based detection flow

  1. Collection: the Wazuh agent forwards a raw log line to the manager, unmodified.
  2. Decoding and first rule match: decoders parse the line into structured fields and rules evaluate them.
  3. Enrichment (only suspicious_login and geoip_detection): an alert in an authentication or web-access group triggers a manager-side integration, which writes the original line plus a RADAR tail (GeoIP, ASN, velocity) to a file the manager monitors. The manager decodes that enriched line a second time, and the scenario's rules match on the radar_* fields (SWD-030).
  4. Rule matching: a RADAR rule matches and generates an alert at its configured level.
  5. Active response: the alert's active-response binding invokes radar_ar.py, which scores the alert and dispatches the tier-appropriate response (SWD-027, SRS-061). The outcome is written to /var/ossec/logs/active-responses.log.

Anomaly-based detection flow

  1. Collection: the agent forwards raw logs and, for log_volume and linux_resource_utilization, the metric lines written by RADAR's collectors on the endpoint.
  2. Indexing: the manager archives every event, and the Filebeat archives pipeline indexes it into wazuh-archives-*, except log_volume metrics, which it routes to wazuh-ad-log-volume-*. For suspicious_login, the pipeline also calls the radar-off-hours ingest pipeline, which flags events of listed users that fall outside their declared working hours.
  3. Detection: on its configured interval, an RCF anomaly detector queries the index, extracts feature values per entity (agent, or user for the off-hours model mode), and stores an anomaly grade and confidence per entity and interval. The off-hours rule mode of suspicious_login uses no detector: a query monitor counts flagged events directly.
  4. Monitoring: on its own interval, a monitor selects results above the scenario's anomaly_grade_threshold and confidence_threshold (up to monitor_max_entities) and sends an HTTP POST, authenticated with a shared secret, to the webhook.
  5. Webhook: the webhook service validates the notification and writes one log line per anomalous entity to /var/log/ad_alerts.log in its container; the Wazuh agent installed in that container forwards the lines to the manager.
  6. Re-entry into the rule engine: the manager decodes and evaluates the line like any other event. A scenario's trigger rule matches, and radar_ar.py scores and responds, accepting the anomaly alert only because it comes from the webhook agent's log.

2.5 RADAR risk engine calculation flow LARC-021

This item describes the risk calculation flow of the RADAR active response (radar/scenarios/active_responses/radar_ar.py, class RiskEngine, with FusionCorrelator). The flow combines anomaly, signature and threat-intelligence evidence into one normalised risk score that selects the response tier.

Mathematical foundation

The risk calculation follows the formula, clamped to [0, 1]:

$$R = w_A \cdot A + w_S \cdot S + w_T \cdot T$$

Where:

  • A (anomaly intensity) = $G \cdot C$, the anomaly grade and confidence carried by the alert (data.anomaly_grade, data.anomaly_confidence). Only alerts matched by a scenario's ad.rule_ids carry them: today the OpenSearch AD alerts relayed by the RADAR webhook.
  • S (signature risk) = $L \cdot I$, with $I$ the scenario's signature_impact and $L$ the signature_likelihood of the alert's rule (a per-rule or per-group list, or one scalar). An alert matched only as an anomaly alert has $S = 0$.
  • T (CTI score) = cti_score_T, the normalised score returned by the DECIPHER analyze endpoint (SWD-038), clamped to [0, 1]. Scenarios without a DECIPHER analyze endpoint always have $T = 0$. RADAR does not aggregate CTI indicators locally.
  • Fusion (opt-in per scenario, SRS-061 requirement 7): the term an alert cannot carry itself is raised to the strongest time-discounted score of an alert of the other kind for the same entity. It never lowers a term.

The weights are set per scenario in ar.yaml; a weight left unset is 0. Shipped values:

Scenario $w_A$ $w_S$ $w_T$
default, scanning_detection 0.0 0.7 0.3
geoip_detection 0.0 1.0 0.0
suspicious_login 0.3 0.4 0.3
log_volume, linux_resource_utilization 0.9 0.0 0.1

Tier determination

Risk scores map to four response tiers via the scenario's tier1_min/tier1_max/tier2_max boundaries in ar.yaml (built-in defaults 0.0/0.33/0.66); see SRS-061 for the normative response semantics of each tier:

  • Tier 0 (R < tier1_min): logged only, no notification
  • Tier 1 (tier1_min ≤ R < tier1_max): email notification + Flowintel case creation
  • Tier 2 (tier1_max ≤ R < tier2_max): Tier 1 actions + mitigations_tier2 (if allow_mitigation)
  • Tier 3 (R ≥ tier2_max): Tier 1 actions + mitigations_tier3 (if allow_mitigation)

Flow sequence

  1. Input collection: the alert's AD grade and confidence (anomaly alerts), the rule's likelihood and the scenario's impact (signature alerts), and the CTI score returned by DECIPHER.
  2. Component calculation: compute A, S, T.
  3. Fusion: if the scenario enables it, raise A or S with the strongest discounted counterpart alert.
  4. Weighted combination: apply the scenario's weights and clamp R to [0, 1].
  5. Tier assignment: map R to Tier 0–3 with the scenario's boundaries.
  6. Action selection: plan the tier's actions, gated by allow_mitigation (LARC-026).

See also: radar/scenarios/active_responses/ar.yaml for the per-scenario values, SWD-026 for the normative design and algorithm, and docs/manual/radar_docs/radar-tuning.md for reachable tiers per scenario.

2.6 RADAR detector creation workflow LARC-022

2.7 RADAR monitor and webhook workflow LARC-023

The diagram below depicts how radar/anomaly_detector/monitor.py and radar/anomaly_detector/webhook.py create the OpenSearch notification channel and alerting monitor for an anomaly detector, and how the monitor's notifications then reach Wazuh through the RADAR webhook service (radar/webhook/ad_alerts_webhook.py). run-radar.sh runs monitor.py after detector.py (LARC-022) for log_volume and linux_resource_utilization; the suspicious_login off-hours monitors are created by off_hours.py through the same channel and webhook.

Workflow stages

1. Notification channel (idempotent)

ensure_webhook() in webhook.py:

  • GET /_plugins/_notifications/configs and look for a webhook channel with the configured name (webhook.name in config.yaml, else WEBHOOK_NAME, default "RADAR Webhook") and URL (webhook.url, else WEBHOOK_URL).
  • If found, update it when its shared-secret header differs; otherwise POST /_plugins/_notifications/configs to create it.
  • The channel sends the header X-RADAR-Webhook-Token with WEBHOOK_SHARED_SECRET.

2. Monitor specification

monitor_payload() builds a query-level monitor named monitor_name:

  • Schedule: every monitor_interval, else detector_interval, minutes.
  • Input: search of the detector's result_index for results of this detector in the last interval with anomaly grade and confidence at or above anomaly_grade_threshold and confidence_threshold, highest grade first, at most monitor_max_entities (default 5) hits.
  • Trigger trigger_name: a Painless condition on the maximum grade and the top hit's confidence.
  • Action: POST to the channel with the message template of SWD-029: the top hit's keys plus an anomalies list with one entry per hit, each with entity, grade, confidence and the anomaly's own data window.
  • A SHA-256 fingerprint of the payload is stored in the monitor's ui_metadata.

3. Monitor creation or update

  • POST /_plugins/_alerting/monitors/_search by monitor name.
  • If it exists and its detector ID or payload fingerprint differs, PUT the new payload; if it matches, leave it. Otherwise POST /_plugins/_alerting/monitors.
  • Print the monitor ID.

4. Runtime delivery

  • Each run with a hit posts to the webhook (POST /notify, port WEBHOOK_INTERNAL_PORT, default 8080).
  • The webhook checks the token, validates each entry, and writes one line per entity to /var/log/ad_alerts.log (format in SWD-035).
  • The Wazuh agent in the webhook container ships the file to the manager, where the opensearch_ad decoder, an AD catch-all rule (radar_ad_received group) and the scenario's trigger rule invoke radar_ar.py.

2.8 RADAR deployment pipeline flow LARC-024

This item describes the flow radar/build-radar.sh runs to deploy a scenario, or with --core-only to bring up a plain Wazuh stack. The GUI's Deploy action (radar/gui/orchestrator/deploy.py, stream_build) runs the same stages with the same scripts and wazuh_api calls, streaming their output to the browser. Two differences: it does not revoke an expired enrollment token when the manager is already running, and on success it records the scenario as deployed (active: true) in ar.yaml, which the GUI uses to show deployment status. It replaced the Ansible deployment pipeline, which was removed in v2.0.0. The component design is in SWD-042.

Pipeline stages

  1. Validation. The scenario must be listed in radar/config.yaml, and radar/.env must exist. WAZUH_API_URL, WAZUH_AUTH_USER and WAZUH_AUTH_PASS must be set before any API stage runs.
  2. Core stack. Skipped when the registered manager container is already running; an expired enrollment token is then revoked. Otherwise certificates and per-deployment credentials are created if missing, every host-side path of the volumes.yml overlay is created, the Filebeat archives pipeline.json is seeded (the build aborts if volumes.yml does not map it), and the core compose project is started.
  3. Component registration. The running components are recorded in radar/infra.yaml, which later stages use to resolve addresses.
  4. Webhook (scenario builds only). A shared secret is ensured. If the webhook has no agent key yet, a 60-minute token for group default is minted so the container can enroll on first start.
  5. Enrollment hardening. After the Wazuh API is reachable, authd requires a password, auto-purge is disabled, the cluster key is set, and port 1515 is closed (the firewall step needs root).
  6. Manager-side files. Applied to the primary manager node first, then to each additional registered node. A failure on an additional node is reported as a warning and does not stop the build.
  7. API-side configuration. The scenario's agent-group configuration, then its ruleset (always together with the default ruleset) and its marker-delimited ossec.conf blocks. The manager is restarted at most once, and only if something changed.

The anomaly detector and monitor are created afterwards, separately, by run-radar.sh (LARC-015, LARC-017).

Idempotency

  • Files and ossec.conf blocks are compared with what is deployed and written only when they differ. ossec.conf changes stay inside <!-- RADAR: <name> BEGIN/END --> markers.
  • Certificates, credentials, the webhook enrollment and the GeoLite2 databases are created only when absent.
  • Re-running the pipeline for a deployed scenario converges to the same state.

2.9 RADAR manager-side enrichment pipeline LARC-025

This item describes the log enrichment pipeline that runs on the Wazuh manager for the suspicious_login and geoip_detection scenarios (HARC-014). It replaced the per-endpoint RADAR helper daemon, removed in v2.0.0.

Pipeline overview

Endpoints forward their raw authentication and web-access logs. The manager classifies each line with Wazuh's stock decoders and rules; an alert in a relevant group triggers an enrichment integration, which appends geographic and behavioural context to the original line and writes it to a file the manager monitors. The enriched line is decoded a second time, and the scenario rules match on the added radar_* fields.

Path Trigger (rule groups) Integration Output file
Authentication authentication_success, authentication_failed custom-radar-enrich /var/ossec/logs/radar/enriched_auth.log
Web access (geoip_detection only) accesslog custom-radar-web-enrich /var/ossec/logs/radar/enriched_web_access.log

Both integrations and their <localfile> entries are declared in the manager snippets radar/scenarios/ossec/radar-shared-auth-log-ossec-snippet.xml and radar/scenarios/ossec/radar-geoip-detection-ossec-snippet.xml, and installed by radar/radar_deploy/manager-apply-scenario.sh.

Pipeline stages (authentication path)

1. Trigger and loop guard

integratord passes the alert to custom-radar-enrich. If the alert's full_log already carries a RADAR tail, the line is an enriched line on its second pass, and the integration exits without output.

2. Parsing

The integration parses the event timestamp, user, source IP and outcome (success or failure) from the original sshd log line itself, not from Wazuh's decoded fields, which the scenario decoders fill only once a tail exists. Accepted and failed logins, including invalid users, are recognised; any other line produces no output. The timestamp is the log line's own (syslog or ISO 8601), so velocity is computed on event time, not processing time.

3. Geographic lookup

geoip.py looks up the source address in the MaxMind GeoLite2 City and ASN databases (/var/ossec/etc/radar/): ISO country code, first subdivision, city, latitude, longitude and ASN. A missing ASN sets asn_placeholder_flag to true.

4. User state

state_store.py loads the user's state from the SQLite database /var/ossec/etc/radar/user_state.sqlite3, keyed by user name and shared by all endpoints: last event time, last position, last country, and the ASN history of the last 90 days.

5. Behavioural indicators

  • Geo-velocity: great-circle (haversine) distance between the previous and current positions divided by the time between the two events: $v = d_{km} / \max(|\Delta t_h|, 10^{-9})$. It is 0 for the user's first located event. Velocity is not capped.
  • Country change: 1 when the user's previous known country differs from the current one, else 0.
  • ASN novelty: 1 when the ASN is not in the user's ASN history, else 0. History entries older than 90 days (relative to the event time) are dropped before the check.

The updated state is written back before the tail is emitted.

6. Enriched line

The original line is appended with a tail and written to enriched_auth.log, for example:

Nov 23 10:15:02 web01 sshd[4242]: Accepted password for alice from 203.0.113.42 port 52111 ssh2 RADAR outcome='success' asn='64500' asn_placeholder_flag='false' country='US' region='California' city='San Francisco' geo_velocity_kmh='450.230' country_change_i='1' asn_novelty_i='0'

7. Second pass

The manager reads the file as syslog. The -with-radar decoders in radar/scenarios/decoders/suspicious_login/0310-ssh.xml (shipped identically for geoip_detection) extract the radar_* fields, and the rules evaluate them: for example impossible travel (velocity of at least 900 km/h with a country change) in suspicious_login, and a country outside the whitelist_countries CDB list in geoip_detection.

Web-access path

custom-radar-web-enrich handles access-log lines (Apache or Nginx, plain or relayed through rsyslog). It extracts the client address, skips loopback and RFC 1918 addresses, and appends RADAR country="…" region="…" city="…" lat="…" lon="…". It keeps no state and computes no velocity or novelty. The geoip_detection web decoders in 0375-web-accesslog.xml read the tail.

Failure handling

Any failure to read the alert, open a GeoIP database, update the state or write the output is appended to /var/ossec/logs/radar/enrichment_errors.log; the integration then exits without output. The first-pass alert is unaffected, so a broken enrichment never hides the original event. radar/radar_deploy/manager-health.sh reports missing integration files, databases, an unwritable state database and recent error-log entries (SRS-068).

2.10 RADAR active response decision pipeline LARC-026

The diagram below depicts the decision pipeline implemented in radar/scenarios/active_responses/radar_ar.py, the Wazuh active response that every RADAR scenario invokes on the manager. It expands on LARC-016 (RADAR active response flow); SWD-027 is the normative design.

Pipeline stages

1. Alert intake

  • Wazuh runs the script once per matching alert (<active-response> with location server) and writes {"parameters": {"alert": {...}}} on stdin.
  • Settings come from active_responses.env next to the script; the scenario configuration from ar.yaml (AR_RISK_CONFIG).
  • An empty or unparseable input ends the run (exit 1).

2. Scenario identification

ScenarioIdentifier (SRS-061 requirement 3):

  • An exact rule.id match in a scenario's ad.rule_ids or signature.rule_ids wins; otherwise rule.groups are matched against the scenario's rule_groups. In both cases the first scenario listed in ar.yaml wins.
  • Detection type: ad, signature, or hybrid (rule ID in both lists).
  • No match: logged, exit 0.

3. Anomaly alert origin

An ad or hybrid alert is processed only if the webhook agent (WEBHOOK_AGENT_NAME, default ad-webhook) read it from /var/log/ad_alerts.log; any other is logged and dropped (exit 0).

4. Context collection

The scenario's strategy class (Registry: BaseScenario, GeoipDetection, SuspiciousLogin, LogVolume, LinuxResourceUtilization, ScanningDetection):

  • Time window: delta_signature_minutes (default 1) before the alert for signature alerts, delta_ad_minutes (default 10) for anomaly alerts; LogVolume and LinuxResourceUtilization use the alert's monitor period, capped at delta_ad_minutes.
  • Effective agent: the alert's agent for signature alerts; the anomalous agent (entity_keyword) for LogVolume/LinuxResourceUtilization; for suspicious_login anomaly alerts, the named user's events on any agent, and the agent that appears most in them.
  • Query: the indices in OS_INDEXES (default wazuh-alerts-*,wazuh-archives-*), up to 1000 events, retried while empty (AR_CONTEXT_QUERY_ATTEMPTS).
  • IOCs from the alert and the context: IPs, users, services, domains, hashes, radar_country, radar_asn, agent.

The context feeds the email, DECIPHER and the case, never the risk score.

5. CTI enrichment (DECIPHER)

  • Health check once per run; a failure is a WARNING and DECIPHER is skipped.
  • If healthy and the scenario has an analyze endpoint (suspicious_login, scanning_detection), post the scenario's payload; the returned severity is $T$. Otherwise $T = 0$.

6. Scoring

  • Anomaly grade and confidence from the alert (ad, hybrid).
  • Fusion lookup (FusionCorrelator) for scenarios that enable it; a failure is logged and the alert is scored alone.
  • Risk score and tier (LARC-021, SWD-026).

7. Decision

  • Decision ID: SHA-256 of the alert ID, timestamp, rule, agent, scenario, detection, window and effective agent (SRS-061 requirement 6). It correlates log lines and the case; there is no deduplication cache.
  • Target IP: the alert's own source IP (ScanningDetection: src_ip, or the X-Forwarded-For client when the peer is a trusted proxy).
  • Tier ≥ 1 and DECIPHER healthy: create the Flowintel case through the DECIPHER incident endpoint (priority by tier).

8. Action planning

ActionPlanner: email from Tier 1; mitigations_tier2 at Tier 2 and mitigations_tier3 at Tier 3 only if allow_mitigation is true. Otherwise the would-be mitigations are logged with a withheld_reason (mitigation_disabled, tier_out_of_mitigation_range).

9. Action execution

ActionExecutor, for each planned mitigation:

  • Gates: scenario allowlist (allowlist_file, checked once per decision, fail-closed when unreadable); global.never_block plus loopback, link-local and the manager's own addresses; supported identifiers only.
  • Agent: Wazuh agent ID of the effective agent (GET /agents?search=), else the alert's own agent ID.
  • Arguments: firewall-drop the target IP; lock_user_linux.sh the Linux users named in the alert, never root or protected_users; terminate_service.sh a context service listed in terminable_services, else the alert's remote IPv4.
  • Dispatch: PUT /active-response?agents_list=<id> with command !<name>; the agent-side script runs on the endpoint.

Then the email is sent (if SMTP is configured).

10. Logging

Every stage writes a line <time> [LEVEL] <message> {json} to /var/ossec/logs/active-responses.log (AR_LOG_FILE): scenario, context, CTI, risk components, planned and withheld actions, case, dispatch results. Scenarios with an allowlist_file also get one JSON audit entry per action outcome, in the native active-response format that Wazuh decodes with rule 650.

11. Exit

  • 0: processed, including no scenario match and an untrusted anomaly alert
  • 1: no alert could be read
  • 2: unhandled exception (logged as CRITICAL with traceback)

Error handling

  • OpenSearch, DECIPHER, fusion, Wazuh API and SMTP failures are logged and the remaining stages continue.
  • An empty context query is retried a fixed number of times with a fixed delay; there is no other retry.
  • An anomaly alert without a numeric grade and confidence raises an error (exit 2).

Configuration schema (ar.yaml)

Abbreviated from radar/scenarios/active_responses/ar.yaml:

scenarios:
  geoip_detection:
    signature:

    w_ad: 0.0

      - rule_id: [100900, 100901, 100903]

2.11 RADAR data ingestion pipeline LARC-027

This item describes how run-radar.sh seeds the indexer with history for the anomaly-based scenarios, through the scenario-specific wazuh_ingest.py scripts (SWD-033).

Pipeline purpose

An OpenSearch RCF detector needs enough past intervals per entity before it reports anomalies, and the suspicious_login off-hours model mode needs weeks of per-user activity. Ingestion writes that history so a scenario can be demonstrated and tested right after deployment, without waiting for real data to accumulate. It is optional (run-radar.sh <scenario> --ingest true) and exists for three scenarios:

Scenario Target index What is written Shaped from
log_volume wazuh-ad-log-volume-<date> (today) Synthetic log_volume_metric samples (data.log_bytes) for one agent, growing linearly up to the latest real value The agent's two most recent real samples
linux_resource_utilization wazuh-archives-radar-seed Synthetic resource_usage_metric samples (data.cpu_usage_pct, data.mem_usage_pct) per agent, marked radar_seed: true, ending where the agent's real samples begin Agents with real samples in the configured recent window
suspicious_login wazuh-archives-4.x-<date> (one index per day) Synthetic archived activity events (data.user, data.action) per configured user, inside each user's shift, with optional evening work and one burst The ingest.users list in config.yaml

All parameters come from scenarios.<scenario>.ingest in radar/config.yaml; the indexer connection from OS_URL, OS_USER, OS_PASS and OS_VERIFY_SSL.

Workflow stages

1. Invocation

run-radar.sh builds the radar-cli image, which contains the three ingest scripts, and runs python <scenario>/wazuh_ingest.py in it, passing the indexer settings as environment variables and mounting the indexer CA certificate. Ingestion runs before the detector is created; detector.py additionally waits briefly (about ten seconds at most) for the index pattern to have documents, because the AD plugin cannot start a detector on an empty index.

For suspicious_login, off_hours.py deploy first creates the radar-off-hours ingest pipeline, the synthetic events are indexed through it so they carry the off-hours flags, and off_hours.py backfill then flags real archived events indexed earlier.

2. Baseline

  • log_volume: the two most recent data.log_bytes values of the configured agent give the latest value and the growth per step. With no real sample the script waits 60 seconds and asks again, then falls back to baseline_bytes and fallback_delta and warns that the scenario is probably not wired up. With one sample, it uses fallback_delta; a non-positive delta is replaced by fallback_delta.
  • linux_resource_utilization: targets are the configured agent_names, or every agent with real (non-seed) samples in baseline_window. Each target's earliest real sample marks where the seed must end; an agent that already has history_minutes of history is skipped. With no target at all, the script exits with an error.
  • suspicious_login: no query; the history comes entirely from configuration.

3. Generation

  • log_volume: history_minutes × 60 / step_seconds points, one every step_seconds, rising linearly by the delta per step and ending at the latest real value, plus one point one step after now.
  • linux_resource_utilization: one point every step_seconds from now − history_minutes to the agent's first real sample, CPU and memory drawn around baseline_cpu_pct and baseline_mem_pct with the configured jitter (reproducible per agent).
  • suspicious_login: for each workday from history_days back to future_days ahead, between events_per_login_min and events_per_login_max events at random times within the user's shift (± drift_minutes), in the user's time zone; optionally evening events and a burst days_ago days back.

4. Bulk indexing

Documents are sent to the OpenSearch Bulk API (POST /_bulk, NDJSON): in one request for log_volume, in chunks for the other two (suspicious_login names the radar-off-hours pipeline when off-hours detection is enabled). linux_resource_utilization first creates its seed index with an explicit mapping if it does not exist.

5. Result

An HTTP error or a failed bulk item makes log_volume and linux_resource_utilization exit with an error; suspicious_login raises on HTTP errors and prints failed items. Each script prints what it indexed. linux_resource_utilization then stops its detector, if one exists, so that the detector re-initialises on the seeded history at its next start. There is no separate verification query and no retry.

2.12 RADAR GeoIP detection scenario flow LARC-028

This item describes the end-to-end flow of the geoip_detection scenario, which uses signature rules to detect and block access from non-whitelisted countries (SRS-055).

Scenario overview

GeoIP detection is a signature-based scenario with no anomaly detector. It relies on:

  • manager-side GeoIP enrichment by Wazuh integrations (SRS-068; replaces the former endpoint-side RADAR helper),
  • RADAR-aware decoders that read the enrichment,
  • rules that look the country up in a CDB whitelist,
  • the RADAR active response for notification and blocking.

Flow stages

1. Source events on the endpoint

  • SSH authentication lines in /var/log/auth.log, collected through the radar_shared agent group.
  • Apache access logs (/var/log/apache2/access.log, other_vhosts_access.log), collected through the geoip_detection agent group.

2. First pass on the manager

  • The stock decoders and rules classify the events (authentication_success / authentication_failed, accesslog). Only an event that produces an alert reaches the integrations; a plain 2xx/3xx web request stays at level 0.

3. Enrichment (SRS-068)

  • custom-radar-enrich (groups authentication_success, authentication_failed) looks the source IP up in GeoLite2 City and ASN, updates the user's travel state, and appends a RADAR ... tail (country, region, city, ASN, geo-velocity, country change, ASN novelty) to the original line in /var/ossec/logs/radar/enriched_auth.log.
  • custom-radar-web-enrich (group accesslog) skips private addresses and appends RADAR country="…" region="…" city="…" lat="…" lon="…" to /var/ossec/logs/radar/enriched_web_access.log.
  • The manager reads both files back as localfile inputs.

4. Decoding of the enriched lines

  • 0310-ssh.xml (sshd-success-with-radar, ssh-failed-with-radar, ssh-invfailed-with-radar) and 0375-web-accesslog.xml (web-accesslog-*-radar) extract radar_country and the other radar_* fields. They replace the stock 0310-ssh_decoders.xml and 0375-web-accesslog_decoders.xml, which are excluded in ossec.conf.

5. Rule evaluation

  • 100900: authentication_success and radar_country not in etc/lists/whitelist_countries.
  • 100901: authentication_success and srcgeoip not Luxembourg, France, Germany or Belgium (fallback; needs Wazuh's legacy GeoIP support).
  • 100902: accesslog and radar_country not in the whitelist.
  • 100903 (level 12): 300 matches of 100902 within 300 seconds.

6. Active response trigger

  • Rules 100900, 100901 and 100903 invoke the radar_ar_geoip command (radar_ar.py) on the manager.

7. Active response processing (LARC-026)

  • Scenario geoip_detection, detection signature; context: the alert agent's events in the last delta_signature_minutes.
  • No DECIPHER analysis endpoint: $T = 0$.
  • Risk: $R = 1.0 \cdot (0.9 \times 0.6) = 0.54$ for the bound rules, Tier 2 with the default boundaries.
  • Tier 1 and above: email and, if DECIPHER is reachable, a Flowintel case. Tier 2 and 3: firewall-drop of the alert's source IP when allow_mitigation is true (shipped value), unless the IP is protected by global.never_block.

8. Logging

2.13 RADAR log volume detection scenario flow LARC-029

This item describes the end-to-end flow of the log_volume scenario (SRS-056), which uses behaviour-based anomaly detection (OpenSearch RCF) to identify abnormal growth of the logs on an endpoint, a possible sign of log flooding, malware error loops or other abnormal activity.

Scenario overview

  • Measures the size of /var/log on each endpoint.
  • Per-endpoint baselines through a detector with a categorical field (agent.name).
  • Anomalies reach Wazuh through the OpenSearch monitor and the RADAR webhook.
  • The RADAR active response scores the anomaly and applies the tier's actions.

Flow stages

1. Collection on the endpoint

  • bootstrap-agent.sh installs the log_volume collector (radar/radar-agent/collectors/log_volume/) as a systemd timer that runs every 30 seconds.
  • Each run appends <timestamp> <hostname> log_volume_metric: /var/log <bytes> (from du -sb /var/log) to /var/log/radar/log_volume_metric.log.
  • The log_volume agent group reads this file (log_format syslog).

2. Decoding and indexing on the manager

  • Decoders log_volume_metric / log_volume_metric_fields (radar/scenarios/decoders/log_volume/0001-log-volume.xml) extract data.log_path and data.log_bytes.
  • A date_index_name step added to the Filebeat archives pipeline (radar/scenarios/pipelines/log_volume/radar-pipeline.txt) routes these events to wazuh-ad-log-volume-YYYY.MM.DD; the radar-log-volume index template (radar/scenarios/templates/log_volume/radar-template.json) maps data.log_bytes as long and agent.name as keyword.

3. Optional history seeding (LARC-027)

  • run-radar.sh log_volume --ingest true runs radar/scenarios/ingest_scripts/log_volume/wazuh_ingest.py, which writes a synthetic history (by default 240 minutes at 20-second steps, settings under scenarios.log_volume.ingest in config.yaml) for the configured agent (ingest.agent_name), continuing the growth of its latest indexed values, or from the configured seed when there are none.

4. Detector creation (LARC-022)

  • run-radar.sh log_volume creates and starts LOG_VOLUME_DETECTOR: feature log_volume_max = max of data.log_bytes, category field agent.name, shingle size 8, interval 1 minute, window delay 1 minute, rules that ignore deviations too small to matter.

5. Anomaly detection

  • Every interval the detector scores each agent's value against that agent's model and writes the anomaly grade and confidence to opensearch-ad-plugin-result-log-volume.

6. Monitor and webhook (LARC-023)

  • LogVolume-Monitor runs every interval and, when grade and confidence reach the thresholds (shipped 0.01 / 0.01), posts up to 5 anomalous agents to the webhook with trigger LogVolume-Growth-Detected.
  • The webhook writes one line per agent to /var/log/ad_alerts.log, for example: Feb 16 10:30:15 <host> ad_alert: OpenSearchAD LogVolume-Growth-Detected: entity="edge.vm", start="…", end="…", anomaly_grade="0.85", anomaly_confidence="0.92" data_start="…", data_end="…"

7. Wazuh rule matching

  • The webhook container's agent ships the line; the opensearch_ad decoder extracts the entity, period, grade, confidence and data window.
  • 100300 (level 5): AD catch-all for lines from /var/log/ad_alerts.log, group radar_ad_received.
  • 100309 (level 12): if_group radar_ad_received and the trigger name.

8. Active response (LARC-026)

  • 100309 invokes radar_ar_log_volume (radar_ar.py) on the manager; scenario log_volume, detection ad.
  • Context: the anomalous agent's (entity_keyword) events in the monitor period, capped at delta_ad_minutes (10).
  • Risk: $A$ = grade × confidence, $R = 0.9 \cdot A + 0.1 \cdot T$, with $T = 0$ (no DECIPHER analysis endpoint). Example: grade 0.85, confidence 0.92 gives $A = 0.782$ and $R = 0.704$, Tier 3.
  • Tier 1 and above: email and, if DECIPHER is reachable, a Flowintel case. Tier 3: terminate_service.sh when allow_mitigation is true, only for a context service listed in terminable_services and on the agent.

9. Logging

  • The decision is recorded in /var/ossec/logs/active-responses.log (SRS-061).

Configuration

  • config.yaml, scenarios.log_volume: index pattern, result index, feature, category field, interval, delay, shingle size, thresholds, monitor and trigger names, ingest settings.
  • ar.yaml, log_volume: ad.rule_ids: ["100309"], w_ad 0.9, w_cti 0.1, tiers 0.0 / 0.33 / 0.66, mitigations_tier3: [terminate_service.sh], terminable_services: [], allow_mitigation: true.

Key characteristics

  • Adaptive: learns normal growth per endpoint.
  • Per entity: separate baselines per agent avoid one busy host masking another.
  • Streaming: detection runs continuously, without batch retraining.
  • Decoupled: detection runs in OpenSearch, response in Wazuh and radar_ar.py.

2.15 RADAR adversarial defense implementation flow LARC-031

Status: planned. Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

The diagram below depicts the intended implementation flow for adversarial ML defense mechanisms in RADAR (HARC-015), protecting anomaly detection against data poisoning, evasion attacks and model tampering. The configuration keys shown in this item are proposed; none of them exists in radar/config.yaml or ar.yaml.

Defense layers

Layer 1: Baseline initialization with clean data

Intended behaviour:

  • Clean period identification: Analyze historical data for known-clean periods (pre-incident, honeypot-free)
  • Gold-standard datasets: Use verified attack-free data for initial training
  • Digital clean room: Temporary system lockdown to capture pristine baselines
  • Exclusion filtering: Remove time segments with suspected attacker presence

Configuration:

baseline_init:
  use_gold_standard: true
  clean_period_start: "2026-01-01T00:00:00Z"
  clean_period_end: "2026-01-15T00:00:00Z"
  excluded_hosts: ["suspected-compromised-01"]

Layer 2: Concept drift detection

Intended behaviour:

  • Baseline shift monitoring: Track mean, variance, and distribution shape changes
  • Velocity thresholds: Alert when baseline shift rate exceeds historical norms
  • Correlation analysis: Flag simultaneous shifts across multiple features
  • Automated gating: Freeze model updates when anomalous drift detected

Algorithm:

Algorithm: Detect abnormal baseline shifts
  Input: current_stats, historical_stats, threshold (default: 0.2)

  // Calculate relative changes
  mean_shift ← |current_stats.mean - historical_stats.mean| / historical_stats.mean
  std_shift ← |current_stats.std - historical_stats.std| / historical_stats.std

  // Check correlation across features
  correlated_shifts ← count_features_with_simultaneous_shifts(current_stats, historical_stats)

  // Determine if drift is anomalous
  drift_detected ← (mean_shift > threshold) OR
                     (std_shift > threshold) OR
                     (correlated_shifts ≥ 3)

  drift_metrics ← {
    mean_shift: mean_shift,
    std_shift: std_shift,
    correlated_features: correlated_shifts
  }

  Output: drift_detected (boolean), drift_metrics (dictionary)

Configuration:

drift_detection:
  enabled: true
  check_interval_hours: 24
  threshold_percent: 20
  correlation_threshold: 3
  freeze_on_drift: true
  require_analyst_approval: true

Layer 3: Multi-layer validation (defense in depth)

Intended behaviour: alerts from independent detection layers are cross-checked, and agreement raises confidence:

  • Signature-based (Wazuh, Suricata): Fast, deterministic, resistant to ML poisoning
  • Multivariate AD (SONAR MVAD): Complex patterns, correlation-aware
  • Streaming AD (OpenSearch RRCF): Real-time, distinct algorithm
  • Cross-layer correlation: Flag events detected by multiple layers as high confidence

What exists today is narrower: a RADAR scenario can weight signature, anomaly and CTI evidence in one risk score, and suspicious_login fuses a signature alert with an off-hours anomaly alert for the same user (HARC-012). RADAR does not consume SONAR or Suricata alerts in any shipped scenario, and there is no confidence boost per agreeing layer.

Validation algorithm:

Algorithm: Validate alert across detection layers
  Input: alert

  layers_triggered ← empty_list

  if signature_detection_fired(alert):
    append 'signature' to layers_triggered

  if mvad_detection_fired(alert):
    append 'mvad' to layers_triggered

  if rrcf_detection_fired(alert):
    append 'rrcf' to layers_triggered

  // Multi-layer agreement increases confidence
  confidence_boost ← count(layers_triggered) × 0.15
  high_confidence ← count(layers_triggered) ≥ 2

  Output: {
    layers: layers_triggered,
    confidence_boost: confidence_boost,
    high_confidence: high_confidence
  }

Layer 4: Human-in-the-loop (HITL) oversight

Intended behaviour:

  • Transparent reasoning: Expose model decisions (which points anomalous, why)
  • Analyst review workflows: Dashboard for reviewing flagged baseline changes
  • Feedback loops: Analysts flag incorrect classifications
  • Approval gates: Model updates require manual approval when drift detected

Workflow:

  1. System detects concept drift or baseline shift
  2. Generate alert to SOC dashboard
  3. Analyst reviews: - Shift magnitude and velocity - Affecting features and entities - Timeline correlation with known events
  4. Analyst decision: - Approve: Legitimate change (new application, infrastructure update) - Reject: Suspected poisoning, freeze baseline - Investigate: Escalate to incident response

Layer 5: System hardening

Intended behaviour:

Log integrity:

Process: Cryptographic hashing of log files
  1. Generate SHA-256 hash of log file
     Command: sha256sum /var/log/wazuh/alerts.json > /var/log/wazuh/alerts.json.sha256

  2. Enable append-only logging (immutable storage)
     Command: chattr +a /var/log/wazuh/alerts.json

  3. Forward-secure audit logs
     Mechanism: Time-stamped cryptographic signatures preventing retroactive tampering

Model security:

Process: Secure model file storage and versioning
  1. Set restrictive permissions
     Permissions: read-only for radar-ml group (mode 440)
     Owner: root:radar-ml

  2. Model versioning and integrity
     Version control: Git repository for model files
     Integrity: SHA-256 checksums for all model files

  3. Audit logging
     Log all model updates with: timestamp, user, model version

Access control: role-based access (viewer, operator, administrator), with model training, baseline reset and model deployment reserved to administrators and subject to approval. See the configuration section below.

Integration with RADAR workflows

Detector creation (LARC-022)

  • Before training: Validate data cleanliness
  • Contamination parameter: Configure RCF contamination tolerance
  • Baseline documentation: Record training period and data sources

Monitor evaluation (LARC-023)

  • Drift detection: Monitor checks for baseline shift before evaluating anomalies
  • Multi-layer correlation: Cross-reference with signature-based rules
  • Confidence adjustment: Boost detection confidence when multiple layers agree

Active response (LARC-026)

  • Risk calculation: Include drift detection status in context
  • Action planning: Require higher confidence when drift suspected
  • Audit logging: Record all defense layer activations

Configuration

The layers above are to be configured in one proposed adversarial_defense section with a block per layer: baseline_initialization (gold-standard dataset, clean period), drift_detection (interval, mean and standard-deviation thresholds, correlation threshold, freeze on drift), multi_layer_validation (required layers, confidence boost per layer), hitl_oversight (operations that need approval) and system_hardening (log hashing, model checksums and versioning, role-based access with radar_viewer, radar_operator and radar_admin roles).

Monitoring and alerting

Drift detection alerts:

  • Email to SOC when drift exceeds threshold
  • Dashboard visualization of baseline trends
  • Automated freeze of model updates

Access control alerts:

  • Failed authentication attempts to model files
  • Unauthorized model update attempts
  • Suspicious baseline reset requests

2.16 RADAR suspicious login flow: signature, off-hours and fusion LARC-035

This item describes how the suspicious_login scenario turns authentication events into RADAR decisions along two independent paths, signature rules on enriched authentication lines (SRS-051) and off-hours activity against declared working hours (SRS-062), and how the active response fuses the two for the same user (SRS-061 requirement 7).

Flow diagram

Signature path

  1. Collection. The radar_shared agent group, assigned with suspicious_login (and geoip_detection), reads /var/log/auth.log as syslog (radar/scenarios/agent_configs/_shared/radar-shared-auth-log-agent-snippet.xml). The suspicious_login group itself adds nothing.
  2. First pass. The stock rules 5715 (success) and 5760 (failure) classify the line into authentication_success / authentication_failed. These groups trigger the custom-radar-enrich integration, and the manager reads its output file back as a localfile (radar/scenarios/ossec/radar-shared-auth-log-ossec-snippet.xml).
  3. Enrichment (LARC-025, SRS-068). The integration appends GeoIP, ASN, geo-velocity, country-change and ASN-novelty fields, computed against the user's history kept on the manager, and writes the line to /var/ossec/logs/radar/enriched_auth.log.
  4. Second pass. The -with-radar decoders of radar/scenarios/decoders/suspicious_login/0310-ssh.xml, which replace the stock 0310-ssh_decoders.xml (decoder_exclude), extract the radar_* fields.
  5. Rules (radar/scenarios/rules/suspicious_login/a3-suspicious-login.xml): failed-login burst 210013 (repeated 5760, same user), impossible travel 210020 / 210021 (radar_geo_velocity_kmh above 900), credential compromise 210022 (210021 after repeated failures of the same user). Off-hours path

All of it is managed by radar/anomaly_detector/off_hours.py from the block scenarios.suspicious_login.off_hours of radar/config.yaml; radar/run-radar.sh suspicious_login runs its deploy, backfill and monitors commands.

  1. Marking. off_hours.py deploy creates the ingest pipeline radar-off-hours (a Painless script rendered from the declared schedule groups) and the legacy index template radar-off-hours (mappings only). At scenario deployment radar/radar_deploy/manager-apply-scenario.sh adds a step that calls the pipeline to the Filebeat archives pipeline (radar/scenarios/pipelines/suspicious_login/radar-off-hours-step.json, with ignore_failure), so that no archived event is lost if the pipeline is missing. Each archived event of an evaluated user gets radar.user, radar.schedule_group and radar.off_hours (0 or 1), or radar.off_hours_error when its time cannot be read.
  2. History. off_hours.py backfill marks archived events of the last backfill_days (45) that carry no flag yet. The optional synthetic history (run-radar.sh suspicious_login --ingest true, LARC-027) is indexed through the same pipeline.
  3. Rule mode (groups with mode: rule). The query monitor SuspiciousLogin-OffHours-RuleMode-Monitor runs every rule_mode.interval_minutes. Its query keeps the users with at least min_events off-hours events in the interval and none in the preceding quiet period, so a burst is reported once. The trigger SuspiciousLogin-OffHours-Rule-Detected posts one entry per user with the configured fixed grade and confidence, the event count and the schedule group.
  4. Model mode (groups with mode: model). The detector SUSPICIOUS_LOGIN_OFF_HOURS_DETECTOR learns, per radar.user, the sum of radar.off_hours per interval, without imputation of empty intervals. Its monitor SuspiciousLogin-OffHours-ModelMode-Monitor reports up to max_entities users whose grade and confidence reach the thresholds and whose interval count is at least min_events, with trigger SuspiciousLogin-OffHour-Detected.
  5. Replacement of the previous design. off_hours.py monitors stops the former time-of-day detectors and disables their monitors without deleting them, and updates or removes the off-hours monitors and detector in place when the configuration changes.
  6. Relay. Both monitors post to the RADAR webhook (SRS-089). The catch-all 210039 (or another AD scenario's catch-all) tags the line radar_ad_received, and the trigger names select 210041 (rule mode) or 210040 (model mode), with the user as entity_keyword.

Active response and fusion

The manager runs radar_ar.py for rules 210013, 210020, 210021, 210022, 210030, 210031, 210040 and 210041 (radar/scenarios/ossec/radar-suspicious-login-ossec-snippet.xml). ar.yaml maps the signature rules to signature.rule_ids and 210040 / 210041 to ad.rule_ids.

  • Origin check: an anomaly alert not read by the webhook agent from its own log is dropped (SRS-089).
  • Context: a signature alert's context is the alert agent's events in the last delta_signature_minutes; an anomaly alert's context is the named user's events on any agent in the last delta_ad_minutes (SuspiciousLogin in radar/scenarios/active_responses/radar_ar.py).
  • CTI: the DECIPHER suspicious_login analysis endpoint receives the alert's user (else the anomalous user, else the first user in the context), host and source IPs.
  • Fusion (FusionCorrelator): on every alert, one backward search of wazuh-alerts-* for alerts of the other detection type on the same user (data.entity_keyword on the anomaly side; data.dstuser, data.srcuser, data.user, data.username on the signature side) within window_minutes (30), widened by ad_lead_minutes (10) before the anomaly's data window. The strongest counterpart, discounted linearly by its time gap, supplies the missing $A$ or $S$ term; only trusted anomaly alerts count. Nothing waits for a counterpart, and without one the score is that of the alert alone.
  • Risk and tiers: $R = 0.3 A + 0.4 S + 0.3 T$, tiers 0.15 / 0.33 / 0.55. A signature alert alone stays below Tier 3.
  • Mitigation (with allow_mitigation): Tier 2 firewall-drop of the triggering alert's source IP; Tier 3 adds lock_user_linux.sh for the triggering alert's own users, never root or a protected user. Fused counterparts never supply targets, so an anomaly alert blocks or locks nothing.

This item describes the end-to-end flow of the scanning_detection scenario (SRS-066): Suricata HTTP events from a monitored web server are evaluated by three independent indicator rules, two agreeing indicators on the same source confirm a scan, and only the confirmation reaches the RADAR active response, which applies its allowlist before any mitigation.   • Context: the alert agent's events in the last delta_signature_minutes (5).
  • Source address (ScanningDetection): src_ip; the X-Forwarded-For value is used instead only when src_ip is a configured trusted_proxies address, taking the last hop that is not itself a trusted proxy.
  • CTI: the DECIPHER suspicious_nt_scanning analysis endpoint receives the source IPs, URIs, methods, User-Agents, target host and the chain of rules that fired in the context.

  • Before dispatching, AllowlistGuard reads etc/lists/radar_scanning_allowlist (allowlist_file). A listed source is declined (reason: allowlist); an unreadable list declines too (reason: allowlist_unreadable), failing closed. Detection rules do not consult the allowlist, so an allowlisted source still alerts.
  • Because the scenario sets allowlist_file, AuditLog writes one JSON entry per action outcome (executed, declined with reason, or nothing planned) to /var/ossec/logs/active-responses.log, in the format of native active responses. The stock rule 650 decodes it, 100840 selects RADAR entries, and 100835 (level 12) raises an operational alert for allowlist_unreadable.

2.18 RADAR Linux resource utilization flow LARC-037

This item describes the end-to-end flow of the linux_resource_utilization scenario (SRS-071): CPU and memory utilization measured on each Linux endpoint, scored by an OpenSearch RCF detector against that endpoint's own history, relayed as an anomaly alert to Wazuh, and decided by the RADAR active response. It shares the anomaly path (LARC-022, LARC-023) and the context handling of log_volume (LARC-029).

Flow diagram

Flow stages

1. Collection on the endpoint

Nov 23 10:15:02 web01 resource_usage_metric: cpu=12.40 mem=71.85

The agent group's configuration reads /var/log/radar/resource_usage_metric.log as syslog (radar/scenarios/agent_configs/linux_resource_utilization/).

No rule fires on these events: they reach the indexer as archived events (logall_json, enabled by every scenario deployment) through the stock Filebeat archives pipeline, in the daily wazuh-archives-4.x-* indices. The scenario has no ingest pipeline or index template of its own.

3. Optional history seeding (LARC-027)

run-radar.sh linux_resource_utilization --ingest true runs radar/scenarios/ingest_scripts/linux_resource_utilization/wazuh_ingest.py. 2.19 RADAR ruleset-as-code pipeline LARC-038

Status: planned. Not implemented as of v2.2.0. This item specifies intended behaviour; no code implements it yet.

This item describes the intended pipeline of SRS-065: changes to RADAR's Wazuh rule and decoder files are proposed by pull request, checked automatically for rule ID conflicts, and, once merged, applied to the Wazuh manager by a CI job without an interactive session on the RADAR host. None of the workflows, scripts or secrets named below exists in the repository: there is no ci/ directory, and the only GitHub Actions workflow (.github/workflows/tests.yml) runs the repository-level test suite.

Intended pipeline

Stages

  1. Scope. The pipeline covers the XML rule files under radar/scenarios/rules/<scenario>/ and the XML decoder files under radar/scenarios/decoders/<scenario>/. It is a second path for day-to-day rule and decoder changes; full scenario rollouts, CDB lists, ossec.conf blocks, agent groups and the rest of a deployment stay with the existing scenario deployment.
  2. Validation on pull request. A workflow triggered by pull requests to main runs ci/check_rule_ids.py as its only validation step. It fails when a changed file defines the same rule ID twice, when a new file reuses a rule ID that exists anywhere on main, or when a modified file introduces a rule ID that exists in another file on main. It passes when no rule file changed.
  3. Merge gate. Branch protection on main forbids direct pushes and requires the check_rule_ids status.
  4. Deployment on merge. A workflow (integrate_rulesets) runs only when a merge changes a rule or decoder XML. It copies the changed files to the manager host over SSH, using the repository secrets RAC_SSH_HOST, RAC_SSH_USER, RAC_SSH_PORT, RAC_SSH_KEY, RAC_MGR_CONTAINER, RAC_HOST_RULES_DIR and RAC_HOST_DECODERS_DIR.
  5. Apply on the host. ci/deploy_rulesets.sh aborts if the manager container is not running; otherwise it copies rules and decoders to the host directories bind-mounted at /var/ossec/etc/rules and /var/ossec/etc/decoders, sets root:wazuh and 0640 inside the container, restarts the manager with wazuh-control restart through docker exec, and reports success or fails the job with a non-zero exit.

Relation to the current implementation

The existing scenario deployment, which the pipeline is to complement, already provides the building blocks for applying rule files to a running manager, through the Wazuh server API rather than through the host's Docker daemon:

  • radar/wazuh_api/ruleset.py uploads a rule, decoder or CDB list file (PUT /rules/files/{name}, /decoders/files/{name}, /lists/files/{name} with overwrite=true) only when its content differs from the manager's copy, and deletes such files.
  • deploy_ruleset_files in radar/wazuh_api/scenario_ops.py uploads a scenario's decoders, rules and lists, together with the default rules, after refusing a scenario whose rules reference a CDB list that has no source file.
  • restart_manager_or_cluster in radar/wazuh_api/manager_config.py restarts the manager, or every cluster node, through the API. The same module can query the manager's configuration validation endpoint, which the deployment does not call today.
  • The rule ID ranges each scenario uses are documented in SWD-034; no tool checks them for conflicts.

2.20 RADAR endpoint onboarding and agent lifecycle flow LARC-039

This item describes how a Linux endpoint joins a RADAR deployment, changes scenario groups, and leaves it again. Manager-side steps run on the RADAR host, from the command line (radar/radar.sh, radar/radar_deploy/) or from the GUI's Deployment page, which runs the same scripts (LARC-040). Endpoint-side steps run on the endpoint itself, from a copy of the radar/radar-agent/ folder. The RADAR host never connects to an endpoint: enrollment is initiated by the endpoint, and every later configuration change reaches it through its Wazuh agent groups (SRS-069).

The enrollment controls and the token lifecycle are designed in SWD-049, the endpoint package in SWD-048, and the API calls for groups and agents in SWD-047.

Lifecycle stages

Stage Runs on Command line GUI (Deployment page) Effect
Harden enrollment RADAR host radar_deploy/manager-harden-enrollment.sh, run by every build-radar.sh every Build Manager requires an enrollment password (use_password=yes), refuses duplicate names (purge=no), cluster key set, port 1515 closed
Mint token RADAR host sudo ./radar.sh mint-token <group>[,<group>...] [minutes] Agent Management, Onboard agent New random enrollment password on the manager, revocation scheduled, enrollment window opened for the token's lifetime, bootstrap command printed
Enrollment window RADAR host sudo ./radar.sh enrollment open [--minutes N] \| close \| status Agent Management, Enrollment Window Opens, closes or reports the firewall window on port 1515, independently of a token

Onboarding sequence

  1. Mint. manager-mint-token.sh writes a new random password into the manager's authd.pass, restarts the manager so that authd reads it, records the expiry on the host and schedules the revocation, then opens the enrollment window for the same number of minutes (1 to 1440). Opening the window needs root; without it the script prints how to open it by hand. The script ends with the command to run on the endpoint, which the GUI extracts and shows separately.
  2. Bootstrap. On the endpoint, bootstrap-agent.sh checks the folder's catalog, scripts, collectors and helpers before it changes anything, installs and holds the pinned agent package, writes the manager address into ossec.conf, and enrolls with agent-auth, passing the token, the agent name and every requested group. It then installs the collectors of the groups that have one, starts the agent, and installs the whole active-response catalog. The agent receives each group's agent.conf through Wazuh's own group synchronisation.
  3. Revoke. When the token's lifetime ends, the revocation timer replaces the password with an undisclosed value and restarts the manager. If the timer did not run (for example after a host reboot), the next health check, or the next build-radar.sh against a running manager, does it. Minting a new token replaces the password immediately, so only the newest token is ever valid.

Groups

The groups an agent joins at enrollment are the ones the endpoint passes to agent-auth. The token is a shared enrollment password: it does not restrict which groups the endpoint may request, and the <group> argument of mint-token only shapes the printed command. The GUI mints for default, the selected scenario's group and, for scenarios listed under shared_scenarios in radar/config.yaml, radar_shared.

After enrollment, group membership is changed from the manager only:

  • Assign resolves the agent through the Wazuh API, by IP address first and then by name, and adds it to default, the scenario's group and, for shared scenarios, radar_shared. The result is also recorded in radar/fleet.yaml.
  • Unassign removes the agent from the scenario's own group only. Its default and radar_shared memberships stay.
  • Undoing a scenario (radar_deploy/manager-undo-scenario.sh, GUI Undo) removes every agent from the scenario's group, and from radar_shared once no other deployed shared scenario needs it (LARC-024, SWD-047).

Re-enrollment and removal

  • Re-running the bootstrap on an enrolled endpoint keeps the existing registration: "Duplicate agent name" from agent-auth is accepted when the endpoint has a key, and the scripts, catalog and collectors are refreshed.
  • Duplicate name without a key fails, with the hint to deregister the old agent first. The manager never overwrites an existing registration (purge=no).
  • Uninstall stops the agent, removes the collectors, the active-response dispatchers and /var/ossec/radar-agent, uninstalls the package and keeps a root-only copy of the agent key together with the manager address. A later bootstrap for the same agent name and manager restores that key, so the agent keeps its ID and groups. --purge-data removes all local state, the kept key included.
  • Deregistration deletes the agent through the Wazuh API (DELETE /agents), by default with purge, so that its name can be reused. --no-purge is available on the command line only; the GUI always purges. An endpoint whose agent is still running tries to enroll again, which only succeeds with a valid token while the window is open.

Webhook agent

The ad-webhook container is an agent too. When build-radar.sh (or the GUI Build) finds it without a key, it mints a 60-minute token for group default and passes it to the container's first start; later starts reuse the stored key.

Constraints

  • Minting and revoking each restart the manager, which briefly disconnects all agents: Wazuh's authd reads its password file only at start.
  • Opening, closing and querying the enrollment window need root on the RADAR host, because they manage an iptables rule. Without root, manager-harden-enrollment.sh skips the firewall step.
  • Only Linux endpoints with apt-get, yum or dnf are supported by the bootstrap and uninstall scripts; the manager-side controls apply to any agent.

See: docs/manual/radar_docs/radar-operations.md#agent-enrollment and docs/manual/radar_docs/radar-getting-started.md#3-onboard-an-endpoint.

2.21 RADAR GUI request and action flow LARC-040

This item describes how a request from the RADAR web interface travels through the GUI process (radar/gui/app.py) to the files, scripts and APIs that carry it out. The GUI adds no deployment logic of its own: configuration requests read and write the same files as the command line, and deployment actions run the same scripts and wazuh_api calls. The module design (access control details, credential store, file locking) is in SWD-041.

Request flow

  1. Access checks. Every request, page or API, passes three checks in order: the Host header must name an allowed host, the request must carry the login token (query parameter once, then the HttpOnly cookie) unless authentication is switched off, and a state-changing request must be JSON and not cross-site. A refused API request gets a JSON error; a refused page request plain text.
  2. Pages. The page routes (/, /active-responses, /connectors, /infrastructure, /deploy) render server-side templates with the data for the first render. Everything after that is a call to an API route from the page's script (radar/gui/static/).
  3. API. Each API group is served by one backend module, listed below. Configuration and credential routes answer in JSON; deployment actions answer with a text/plain stream.

2.22 RADAR deployment health check flow LARC-041

This item describes how a health check of a RADAR deployment runs: which components it reaches, in which order, and how the scenario selection and the registered manager nodes scope it. The check list of each stage and the output format are specified in SWD-040.

Entry points

Entry point Runs
radar/health-radar.sh [--scenario <name\|all>] [--agent-name n1,n2] The three stages below, in order, after loading radar/.env
radar/radar.sh health ... health-radar.sh with the same arguments
GUI, Deployment page, Status tab (/api/deploy/health) The same three stages directly, from radar/gui/orchestrator/deploy.py, streamed to the browser (LARC-040)

None of them needs root. They need access to the Docker daemon (stage 1 uses docker exec) and the Wazuh API and OpenSearch credentials from .env.

Flow

  1. Token revocation. Before checking anything, radar_deploy/manager-revoke-token.sh --if-expired revokes an enrollment token whose recorded expiry has passed (SWD-049). This is the only change a health check can make; it restarts the manager.
  2. Stage 1, manager containers (radar/radar_deploy/manager-health.sh). The manager nodes come from radar/infra.yaml through wazuh_api.cli manager-containers, primary node first; with no registered node the stage stops with a non-zero exit status. The webhook container is checked once. Then, for each node, the container state, the active-response and core configuration files, the scenario-specific runtime and enrichment files, and the reachability of OpenSearch and, when configured, DECIPHER from inside that container. Addresses are resolved at run time with wazuh_api.infra (SWD-050). Finally, for the anomaly scenarios that send to the webhook (log_volume, linux_resource_utilization), the webhook URL is probed from inside the indexer container.
  3. Stage 2, Wazuh API, OpenSearch and webhook (wazuh_api.cli manager-health-api, radar/wazuh_api/health.py). If the manager runs as a cluster, the daemon status and the scenario ossec.conf markers are checked per cluster node, as reported by the API; otherwise on the single manager. Then, for the selected scenarios: group configuration, decoder, rule and list files, and the agents that are members of all of the scenario's groups. Last, the OpenSearch cluster health (with the log_volume index template) and the webhook URL, both from the RADAR host.
  4. Stage 3, named agents (wazuh_api.cli agent-health), only when agent names are given: each agent's registration and connection status, and its membership of default and, unless all scenarios were selected, of the named scenario's group. No connection is made to the endpoint.

Scenario scoping

The scenario selection decides which scenario-dependent checks run. Checks without a scenario dependency always run.

Check Stage Runs when the selection includes

With --scenario all, the selection is every scenario listed in radar/config.yaml (wazuh_api.cli list-scenarios), whether or not it is deployed. Scenarios that are not deployed therefore report FAIL lines; to check a partial deployment, run one check per deployed scenario.

Results and exit status

Each stage prints its lines as it produces them, prefixed OK, WARN, FAIL or SKIP. A FAIL line does not change a stage's exit status: a stage exits non-zero only when it could not run (no registered manager node, or a Wazuh API error such as failed authentication). health-radar.sh stops at the first stage that exits non-zero, so the later stages are not run; the GUI's Status tab runs all three stages regardless.

  • The enrichment checks of stage 1 are gated on suspicious_login only, although geoip_detection uses the same GeoLite2 databases and its own web enrichment integration (SWD-040).
  • The decoder and rule files checked in stage 2 come from a table in radar/wazuh_api/health.py, not from radar/scenarios/; a file added to a scenario must be added there too to be checked.

4.5 C&C server deployment architecture LARC-034

This item describes how the command-and-control (C&C) server of IDPS-ESCAPE is deployed on one Docker host by RADAR: the containers, their ports and storage, the credentials and certificates they share, and the order in which radar/build-radar.sh brings them up. It implements SRS-001 (centralized C&C deployment), SRS-004 (agent management), SRS-011 and SRS-012 (event visualization in the dashboard), SRS-013 (agent status panel), SRS-016 (indexer credentials), SRS-024 (event querying through the indexer and Wazuh API), SRS-044 (platform-independent, containerised deployment), SRS-083 (component channels), SRS-084 (storage on the C&C host) and SRS-085 (fleet monitoring).

Deployment view

Containers

The indexer and Wazuh API ports are published on RADAR_MGMT_BIND_ADDRESS and the webhook on WEBHOOK_BIND_ADDRESS (both 0.0.0.0 by default, see radar/env.example). The RADAR GUI (radar/gui/) is not a container of the stack; it listens on 127.0.0.1:5000 and is reached through an SSH tunnel. The recommended host firewall rules for each port are listed in radar/README.md ("Security assumptions and recommendations").

The webhook is built only when a scenario is deployed; build-radar.sh --core-only brings up the three core containers alone. SONAR is not started by build-radar.sh; it is added as a compose overlay or started with sonar/sonar.sh.

The core compose file refuses to start when OS_PASS, WAZUH_AUTH_PASS or INDEXER_DASHBOARD_PASSWORD is unset, so the stack never runs with an empty password. credentials.py generates the passwords only for a fresh deployment, detected by the absence of the wazuh-indexer-data volume; on an existing deployment it leaves them unchanged and warns if stock Wazuh passwords are still in use. radar.sh rotate-credentials (radar_deploy/manager-rotate-credentials.sh) replaces them later.

Build sequence

build-radar.sh <scenario> or build-radar.sh --core-only:

  1. Loads .env, and stops if it is missing.
  2. If the manager container is not running:
  3. creates the certificates if none exist (manager-ensure-certs.sh);
  4. generates missing credentials and writes .radar-generated/ (python3 -m wazuh_api.credentials ensure);
  5. derives a compose overlay from volumes.yml for the services of the core compose file (python3 -m wazuh_api.cli core-volumes-overlay), creates the missing host directories with mode 0750, and seeds the archives ingest pipeline file;
  6. runs docker compose -f docker-compose.core.yml -f - up -d with that overlay.

If the manager is already running, it only revokes an expired enrollment token. 3. Registers the RADAR-built components in infra.yaml. 4. For a scenario: generates WEBHOOK_SHARED_SECRET if empty, resolves the manager address the webhook enrolls against, mints a 60-minute enrollment token unless the webhook is already enrolled, and builds and starts the webhook. 5. Waits for the Wazuh API, then hardens enrollment (radar_deploy/manager-harden-enrollment.sh): password-only enrollment, no purge of agent keys, the cluster key set from .env or generated, and the DOCKER-USER rule that drops traffic to port 1515 put back in place (radar_deploy/manager-enrollment-window.sh close, when run as root). 6. With --core-only, stops here. Otherwise it applies the scenario to every registered manager node (radar_deploy/manager-apply-scenario-all.sh) and deploys the scenario's agent-group configuration, decoders, rules and lists through the Wazuh API.

Agent management

Endpoints are onboarded with radar/radar-agent/bootstrap-agent.sh and a token minted on the C&C host (radar.sh mint-token, i.e. radar_deploy/manager-mint-token.sh), which also opens the enrollment window for the token's lifetime. Scenario groups are assigned with radar_deploy/manager-assign-agent-group.sh or python3 -m wazuh_api.cli assign-hosts-to-groups, which records the result in fleet.yaml; groups are removed with manager-unassign-agent-group.sh and agents deleted from the manager with manager-deregister-agent.sh. The same operations are available in the RADAR GUI.

Existing Wazuh installation

When RADAR is attached to an existing Wazuh installation, no core containers are created and no passwords are generated: the operator registers the existing manager nodes, indexer and dashboard in infra.yaml, enters their credentials in .env, and maps each manager's bind mounts in volumes.yml. Manager-side files are then written through those host paths and docker exec, so RADAR runs on the host of the manager containers. See: docs/manual/radar_docs/radar-getting-started.md#working-with-an-existing-wazuh-installation.
